# Переработка Flow работы с субагентами

## Контекст и цель

Сейчас параллельная работа субагентов (`Task`) в панели устроена так:

- `StreamsBar.tsx` рисует ряд чипов "STREAMS / main / agent:X" и кнопку
  "N agents running". Чипы кликабельны (`onPick` меняет `activeStream` в
  `App.tsx`), но `activeStream` нигде не используется для фильтрации —
  клик по чипу ничего не меняет в интерфейсе. Кнопка "N agents running"
  открывает боковую шторку `AgentsDrawer.tsx` со списком карточек
  "PARALLEL WORK".
- Карточка `TaskItem` (`kind: 'task'`) рендерится прямо в основной ленте
  (`Feed.tsx`), вперемешку с обычными сообщениями и вызовами инструментов
  главного потока.

Три проблемы, из-за которых просят переделать:

1. Чипы `StreamsBar` не работают — не делают ничего, кроме визуальной
   подсветки самих себя.
2. Пока агент работает, его карточка засоряет основную ленту — а должна
   быть в "своём треде", не мешая читать и продолжать общаться с главным
   потоком.
3. Нужен дропдаун вместо чипов: переключает **что видно в области
   вывода** — main или конкретный агент, — с честным статусом агента
   рядом с именем (не выдуманным).

Разведка по коду (webview + Kotlin-плагин) и эмпирическая проверка на
живом `claude` CLI показали, что честный статус "агент ждёт разрешения
или ответа" физически посчитать можно, но два места в текущем коде для
этого не готовы, а одно — просто сломано:

- Permission-запросы сейчас никак не привязаны к субагенту: Kotlin
  вытаскивает из hook-payload только `permission_mode`, `tool_name`,
  `tool_input`, `session_id`, хотя в сыром JSON от `claude` уже есть
  `agent_id` — Kotlin его просто не читает и не пересылает.
- Эмпирический тест (`claude -p` с реальным `Task`-вызовом, хук
  логировал сырой JSON) показал: `agent_id` из hook-payload **побайтово
  совпадает** с `task_id` из stream-json событий `task_started` /
  `task_progress` / `task_notification`, которые webview уже получает и
  уже использует как `TaskItem.id`. Отдельной таблицы соответствий не
  нужно — значения совпадают напрямую.
- Тот же тест выявил реальный баг: `noteSubagent` в `build.ts` ищет
  `TaskItem` по `event.parent_tool_use_id`, сравнивая его с `TaskItem.id`
  (`task_id`). Но на актуальной версии CLI (2.1.220) `Task` приходит
  только через `task_id`-канал (`task_started`/...), а не как
  `tool_use`-блок в потоке ассистента — поэтому `parent_tool_use_id`
  сообщений субагента (`toolu_...`) никогда не совпадает с `task_id`.
  `noteSubagent` сейчас молча ничего не находит: живое накопление "6
  последних строк" не работает. Заодно из-за этого же несовпадения
  `AskUserQuestion`, заданный субагентом, никогда не создаёт `AskItem` —
  весь блок уходит в `noteSubagent`, схлопывается в одну строку и
  теряется без вариантов ответа.
- В `task_started`/`task_progress`/`task_notification` уже есть **оба**
  идентификатора рядом: `task_id` и `tool_use_id` (вызов `Task`,
  породивший субагента — то же самое значение, что субагент указывает в
  своих `parent_tool_use_id`). Это и есть недостающее звено: `tool_use_id`
  из системного события — ключ, `task_id` из того же события — значение,
  дальше по этой карте `parent_tool_use_id` любого сообщения субагента
  превращается в правильный `task_id`.

Всё это укладывается в один проект: небольшая правка в Kotlin-плагине +
доработка редьюсера ленты + замена интерфейса стримов на дропдаун.

## Модель: main + треды агентов, дропдаун — это просто переключатель вида

Дропдаун не создаёт "отдельные чаты". Он переключает только то, что
показано в области вывода — как вкладки в отладчике. Поле ввода всегда
адресовано главному потоку, независимо от того, какая вкладка открыта
(при отправке с открытой вкладкой агента вид автоматически переключается
обратно на main — иначе пользователь может не увидеть свой же ответ).

## Данные

### `TaskItem` (`webview/src/feed/types.ts`)

Поле `detail: DetailLine[]` переименовывается и меняет смысл на
`log: DetailLine[]`:

```ts
export interface TaskItem {
  id: string
  kind: 'task'
  target: string
  meta: string
  duration: string
  percent: number
  log: DetailLine[]
  pending: boolean
}
```

- Во время работы — **накопление**, а не перезапись: каждый шаг
  субагента (текстовая реплика или `ToolName…` для `tool_use`-блока)
  добавляется в конец `log`. Кап — 300 строк; при переполнении старейшие
  строки уходят, а в начало списка подставляется одна синтетическая
  строка `{ text: '…N earlier steps trimmed', tone: 'dim' }` (по образцу
  уже существующего `detailFor`).
- По завершении `log` **не перезаписывается** финальным текстом — он
  просто дописывается туда же последней строкой (результат `Task`, как
  обычная запись с `tone: 'ok'`/`'bad'` в зависимости от того, была ли
  ошибка). Так вкладка агента после завершения показывает весь путь, а
  не только финальный ответ.
- Фоновый канал (`task_started`/`task_progress`/`task_notification`)
  работает по тем же правилам поверх `log` вместо точечной перезаписи
  одной строки.

### `PermItem` / `AskItem` (`webview/src/feed/types.ts`)

Оба получают новое опциональное поле:

```ts
export interface PermItem {
  id: string
  kind: 'perm'
  target: string
  meta: string
  command: string
  decision: 'once' | 'always' | 'deny' | null
  taskId?: string
}

export interface AskItem {
  id: string
  kind: 'ask'
  meta: string
  questions: AskQuestion[]
  taskId?: string
}
```

`taskId` не задан → решение принадлежит главному потоку (текущее
поведение). `taskId` задан → решение принадлежит конкретному агенту.

### Карта `tool_use_id → task_id` (`webview/src/feed/build.ts`)

Новое поле в состоянии редьюсера, например `taskByToolUseId:
Record<string, string>`. Заполняется в обработчике `task_started`:
`event.tool_use_id` (если есть) → `event.task_id`. Используется в двух
местах:

1. **`noteSubagent`** — вместо прямого сравнения `parent_tool_use_id ===
   TaskItem.id` сначала транслирует `parent_tool_use_id` через карту в
   `task_id`, затем ищет `TaskItem` по нему. Это чинит и накопление
   `log`, и обнаружение `AskUserQuestion` от субагента.
2. **`AskUserQuestion` от субагента** — сейчас `applyAgentEvent`
   безусловно отправляет события с `parent_tool_use_id` в `noteSubagent`,
   минуя `applyToolUse`/`readQuestions`. Меняем: если среди блоков
   сообщения субагента есть `tool_use` с `name === 'AskUserQuestion'` и
   `parent_tool_use_id` резолвится в реальный `task_id` — создаём
   `AskItem` (тем же `readQuestions`, что уже используется для главного
   потока) с `taskId` равным этому `task_id`, вместо строки в `log`.
   Остальные блоки сообщения по-прежнему идут в `log` через
   `noteSubagent`.

### Permission → `taskId`

- **Kotlin, `PermissionServer.kt`** (`decide()`): дополнительно читать
  `payload.string("agent_id")` (поле опционально — у permission-запросов
  главного потока его нет). Добавить в `data class Request` поле
  `agentId: String?`.
- **Kotlin, `ClaudePanel.kt::askPermission()`**: положить `agentId` в
  JSON, уходящий в webview, только если оно не пустое.
- **`webview/src/protocol.ts`**: в варианте `{ type: 'permission', ... }`
  добавить `agentId?: string`.
- **`webview/src/feed/build.ts`**: при создании `PermItem` — `taskId:
  message.agentId` (значения совпадают с `task_id` напрямую, маппинг не
  нужен — подтверждено эмпирически).

## Статус агента — производное значение, не новое поле

```ts
type AgentStatus = 'running' | 'done' | 'needs-input'

function statusOf(task: TaskItem, items: FeedItem[]): AgentStatus {
  if (!task.pending) return 'done'
  const blocked = items.some(
    (item) =>
      (item.kind === 'perm' && item.taskId === task.id && item.decision === null) ||
      (item.kind === 'ask' && item.taskId === task.id && !answeredAsks.has(item.id)),
  )
  return blocked ? 'needs-input' : 'running'
}
```

(`answeredAsks` — то же множество отвеченных id, что уже ведёт
`useCardState`, просто используется и для вопросов от субагентов.)

`main` в дропдауне получает статус по той же логике, но с `taskId ===
undefined` вместо `task.id`, и `pending` заменяется на `panel.status ===
'running'`.

Никакого отдельного статуса "error" не вводим — ошибка субагента, как и
сейчас, видна текстом (`tone: 'bad'`) в его логе.

## Интерфейс

### Удаляется целиком

- `webview/src/components/StreamsBar.tsx` + связанный CSS-блок.
- `webview/src/components/AgentsDrawer.tsx` + связанный CSS-блок.
- `drawerOpen`/`activeStream`-как-неиспользуемое-состояние и их проводка
  в `App.tsx` (взамен приходит новое, работающее состояние — см. ниже).
- Рендер `case 'task'` в `Feed.tsx` / `ItemView` — карточка агента больше
  никогда не показывается инлайн в основной ленте. `FeedRowItem`
  расширяется: `Exclude<FeedItem, TodoItem | AskItem | PermItem |
  TaskItem>`.

Существующие селекторы `buildStreams`/`buildAgents` в `App.tsx`
заменяются одним селектором для `StreamSwitcher` — он строит список
пунктов из `panel.items`, применяет `statusOf` и отфильтровывает
`hiddenTaskIds` (см. ниже).

### Новый компонент `StreamSwitcher`

Один дропдаун в нативном IDE-стиле (лейбл + текущее значение + шеврон,
как штатный `Theme:`-селектор JetBrains) на месте прежнего `StreamsBar`.

- **Виден только когда за сессию был хотя бы один агент.** До первого
  `Task` — не рендерится вообще (`return null`), места не занимает.
- Список: `main` всегда первым пунктом, дальше агенты в порядке запуска.
- Каждая строка: цветная точка + короткий статусный лейбл + имя агента
  (`target`) + `meta` (то же короткое описание задачи, что уже есть у
  `TaskItem`, обрезанное до одной строки). Цвет точки: акцентный — RUNNING,
  серо-зелёный (`--acc-ok`) — DONE, предупреждающий (`--acc-warn`, в тон
  панели разрешений) — NEEDS INPUT.
- Клик по пункту меняет **только** локальный "какая вкладка открыта
  сейчас" стейт — без побочных эффектов на отправку сообщений.

### Жизненный цикл пачки агентов

Показываются агенты только текущей "пачки" — набора `Task`, запущенных
в рамках ещё не до конца обработанного пользовательского обращения к
main (включая случай, когда ответ на текущее обращение ещё не пришёл, а
пользователь тем временем поставил в очередь следующее сообщение —
благодаря существующему механизму `Queue` фактическая отправка нового
сообщения назад в модель гарантированно происходит только после того,
как весь текущий ход, включая все параллельные `Task`, полностью
завершится).

- Реализация — ephemeral-состояние в `App.tsx` (не в `build.ts`,
  durable-лог `panel.items` не трогаем): множество `id` завершённых
  задач, которые нужно скрыть из дропдауна, например `hiddenTaskIds:
  Set<string>`.
- В момент фактической отправки нового сообщения в main (та же точка,
  что уже шлёт очередь/ввод) — все текущие агенты со статусом `done`
  добавляются в `hiddenTaskIds`. Агент, который почему-то всё ещё
  `pending` в этот момент (в норме недостижимо благодаря `Queue`, но
  проверка — просто защитный код), в `hiddenTaskIds` не попадает и
  остаётся виден, пока не завершится сам.
- `StreamSwitcher` и подсчёт "агент запускался хоть раз" фильтруют
  `TaskItem` через `hiddenTaskIds`. Когда после фильтра агентов не
  остаётся — дропдаун снова скрывается (как до первого запуска).
- Если в момент отправки была открыта вкладка агента, который эта
  отправка скрывает, — выбор автоматически возвращается на `main`.

### Область вывода

- Открыт `main` → сегодняшняя `Feed` без изменений в поведении (только
  без карточек `task`, `todo`, `ask`, `perm` — как и раньше).
- Открыт агент → новый вид: шапка (тип агента `target`, `meta`,
  `duration`, `percent`) и под ней — весь `log` этого `TaskItem`,
  отрендеренный тем же визуальным языком строк, что сейчас использует
  `TaskCard` (`DetailLine` → строка с цветом по `tone`). Технически —
  переиспользование текущей внутренней разметки `TaskCard.tsx`
  (шапка + список деталей), но всегда в развёрнутом виде и как
  самостоятельный экран, а не карточка внутри чужой ленты.

### Панели `PermissionPanel` / `AskPanel` над полем ввода

Показывают не "самое свежее нерешённое во всей сессии", а то, что
относится к **сейчас открытой** вкладке:

- `main` открыт → показывается свежий нерешённый `PermItem`/`AskItem` с
  `taskId === undefined` (как сейчас).
- Открыт агент X → показывается свежий нерешённый `PermItem`/`AskItem` с
  `taskId === X.id`. Раньше это было не нужно (данные вообще не
  различали, откуда пришёл запрос), теперь появляется впервые: решение,
  адресованное конкретному субагенту, не блокирует весь интерфейс — оно
  ждёт в его собственной вкладке. Статус `needs-input` в дропдауне — это
  сигнал "загляни туда".

Эвристика `awaitingPermission`/`lastPendingId` в `Feed.tsx` (подсветка
"эта карточка ждёт разрешения" среди инструментов **главного** потока)
остаётся как есть — она относится только к `toolGroup`-элементам главной
ленты, `task` из неё уже выбывает по другой причине (карточка вообще не
рендерится в `Feed`).

## Границы (что не трогаем)

- `TaskListPanel` (список `TodoWrite`) остаётся общим для главного
  потока, как сейчас — субагенты собственный todo-list не показывают,
  никаких признаков того, что это где-то нужно, не найдено.
- Формат `AgentSystemEvent`, `AgentAssistantEvent` и остальных типов
  протокола, не упомянутых выше, — без изменений.
- `ClaudeSettings.kt` (`WATCHED_TOOLS`, сам механизм `PreToolUse`-хука) —
  без изменений: `AskUserQuestion` как шёл вне hook-канала (обычным
  `tool_use` в потоке ассистента), так и идёт.

## Проверка

- `webview/src/harness/scenarios/cards.ts`: существующий сценарий
  `multiple-agents` (два параллельных `Task`) — обновить/расширить так,
  чтобы один из двух агентов на определённом чекпоинте запрашивал
  permission, а другой продолжал работать. Это единственный сценарий,
  который реально проверяет статус `needs-input` и то, что панель
  разрешения не перекрывает главный поток, пока открыт не тот таб.
- Отдельный чекпоинт/сценарий на исчезновение пачки: агенты завершились
  → отправлено следующее сообщение в main → дропдаун пуст/скрыт.
- `pnpm tsc --noEmit` и `pnpm vitest run` в `webview/`.
- Kotlin-часть — сборкой плагина (`./scripts/sandbox.sh`) и живой
  проверкой permission-запроса от субагента в песочнице (не только в
  харнессе, поскольку харнесс не проходит через реальный
  `PermissionServer`).
