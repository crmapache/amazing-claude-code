# Харнесс сценариев для ревью ленты webview-панели

## Контекст и цель

После правок в ленте (сворачиваемая группа вызовов инструментов и всё
остальное, что там уже есть: список задач, план, вопросы, разрешения,
субагенты, обрыв сессии и т.д.) единственный способ увидеть, как это
реально выглядит и работает - поднять полную песочницу IDE (gradle) и
руками довести настоящего агента до нужного состояния. Это медленно и
плохо воспроизводимо: чтобы снова увидеть редкий сценарий (обрыв сессии
посреди вызова, несколько параллельных агентов), его нужно каждый раз
пересоздавать вручную.

Цель: локальная страница-харнесс, которая по клику на кнопку мгновенно
разыгрывает конкретный сценарий (пачку вызовов инструментов, список
задач, план на согласование и т.д.) в НАСТОЯЩЕМ, ничем не изменённом
интерфейсе панели - без запуска IDE и без настоящего агента. Страница не
должна становиться отдельной, самостоятельно поддерживаемой копией
интерфейса: весь рендер идёт тем же кодом, что и в реальном плагине,
поэтому она не может разойтись с ним сама по себе.

## Область действия

**Входит:** новая dev-only страница с кнопками сценариев, библиотека из 18
сценариев (см. ниже), минимальная точка внедрения в `App.tsx` для
имитации отправки сообщения пользователем.

**Не входит:** страница никак не участвует в сборке и поставке самого
плагина (не должна использовать данные из сборки, шипящейся в IDE);
никакого настоящего бэкенда/агента; никаких новых тестовых
библиотек/фреймворков; не переделываем ничего в уже существующих
компонентах ленты, кроме одной точечной правки в `App.tsx`.

## Как открывается

Отдельная точка входа `webview/harness.html` рядом с существующим
`webview/index.html`. Vite по умолчанию включает в `vite build` (то, что
гоняет gradle и кладёт в ресурсы плагина - `build.gradle.kts:122-156`)
только объявленный в конфиге вход; лишние html-файлы в него не попадают,
если явно не прописать их в `build.rollupOptions.input`. Мы туда их и не
прописываем. Зато `vite dev` (dev-сервер, запускается уже существующей
командой `pnpm dev` в `webview/`, порт 5173 фиксирован в
`vite.config.ts:16-19`) отдаёт вообще все `.html`-файлы проекта как
обычный статический сервер - значит `harness.html` открывается локально
по адресу `http://localhost:5173/harness.html`, но никогда не попадает в
собранный `dist` и, соответственно, никогда не попадает в сам плагин.
Никаких правок `vite.config.ts` или `build.gradle.kts` не требуется.

## Архитектура

### Настоящий интерфейс без изменений + оверлей сценариев

`webview/src/harness/harness.tsx` - точка входа для `harness.html`,
по структуре зеркало `main.tsx`. Сам держит состояние «какой запуск сейчас
играет» (`runId`, активный сценарий) и рендерит два соседних элемента:

```
<App key={runId} />
<ScenarioToolbar activeId={activeId} onRun={...} />
```

Отдельный React-контекст не нужен - состояние запуска нужно только этой
одной точке монтирования, обычного `useState` в `harness.tsx` достаточно.

`App` (`webview/src/App.tsx`) импортируется как есть, без единого
изменения в самом компоненте (кроме точки внедрения ниже) - тот же код,
что грузится в реальном плагине. `ScenarioToolbar` - новый, полностью
отдельный компонент со своим CSS-модулем; ничего общего с `feed.module.css`
не переиспользует специально, чтобы не путать стили ленты со стилями
самого харнесса.

### Как события попадают в ленту

`App` уже подписывается на сообщения оболочки через `subscribe()` из
`webview/src/bridge.ts` - это единственная точка, откуда в реальности
приходят события IDE (`init`, `sessions`, `agent` с вложенным
`AgentEvent`, и т.д. - полный список в `webview/src/protocol.ts`).
`subscribe()` кладёт переданный обработчик в `window.__accReceive`. Плеер
сценария вызывает `window.__accReceive?.(message)` для каждого шага
сценария напрямую - `bridge.ts` не трогаем вообще, инъекция идёт через уже
существующий, ничем не изменённый канал. Никакой параллельной "теневой"
системы доставки событий не создаём.

`send()` (исходящие сообщения от панели к IDE) в харнессе просто
складываются в очередь и никуда не уходят (`bridge.ts:16-27`,
`isBridgeReady()` в браузере без моста всегда `false`) - это уже так
устроено сегодня, никаких изменений не требуется.

### Сообщение пользователя - единственная точка правки в App.tsx

Карточка `kind: 'user'` в ленте появляется только через локальный
`dispatch({ kind: 'prompt', ... })` внутри `submit` (`App.tsx:520-559`),
который читает текст из состояния поля ввода (`draft`). Это не сообщение
"снаружи" - его нельзя воспроизвести через `window.__accReceive`.

Правка: `submit` получает необязательный параметр с текстом,
подставляемым вместо `composePrompt(draft)`, если он передан (существующие
вызовы `submit()` без аргумента не меняют поведение). Рядом заводится один
`useEffect`, который в dev-сборке кладёt в `window.__accHarnessSend` тонкую
обёртку над этим `submit`. Условие - `import.meta.env.DEV`: Vite
статически подставляет туда `false` в продакшен-сборке, и весь блок
устраняется как мёртвый код при `vite build` - в собранном плагине этого
кода физически не будет. Это единственная строка в реальном коде
интерфейса, которая вообще знает о существовании харнесса.

Флаг `import.meta.env.DEV` относится ко всей dev-сборке, а не именно к
`harness.html` - значит `window.__accHarnessSend` окажется определён и
при обычном открытии `index.html` через `pnpm dev` (не только на странице
харнесса). Это не проблема: в продакшен-сборке (то, что реально попадает в
плагин) хука нет в принципе, а лишняя, никем не вызываемая функция на
`window` при обычной разработке безвредна - отдельно ограничивать её
именно харнессом смысла нет.

### Проигрывание сценария

`webview/src/harness/player.ts`. Сценарий - упорядоченный список шагов:

```ts
type ScenarioStep =
  | { kind: 'user'; text: string }               // через window.__accHarnessSend
  | { kind: 'shell'; message: ShellMessage }      // через window.__accReceive
  | { kind: 'agent'; event: AgentEvent }           // сахар над shell: {type:'agent', sessionId, event}
  | { kind: 'wait'; ms: number }

interface Scenario {
  id: string
  title: string
  category: 'grouping' | 'cards' | 'system' | 'combined'
  steps: ScenarioStep[]
}
```

Плеер идёт по шагам по порядку: `user`/`shell`/`agent` выполняются сразу,
`wait` - настоящая пауза (раз договорились про тайминги как в живом
чате). Текстовые ответы разбиваются на несколько кусочков и уходят как
серия `stream_event`/`content_block_delta` (тот же формат, что и у
настоящего потокового ответа - см. `applySystem`/`stream_event` в
`build.ts`), с небольшими паузами между кусочками - так виден настоящий
эффект печатающегося текста, а не мгновенное появление целиком.

Общий для всех сценариев старт (`init` → подтверждение входа → список
сессий) вынесен в один хелпер `bootstrapSteps()`, чтобы не повторять его в
каждом сценарии - каждый сценарий начинается с него и продолжает своими
шагами.

Плеер даёт `cancel()` - прерывает оставшиеся запланированные таймеры,
нужно на случай клика по другому сценарию посреди проигрывания текущего.

### Сброс между сценариями

По решению (см. дизайн выше) - клик по кнопке всегда начинает разговор
заново, не дописывает в текущий. Механизм: `ScenarioToolbar` держит
счётчик запуска (`runId`) и меняет `key` у `<App />` - React полностью
размонтирует и заново монтирует всё дерево `App`, разом стирая все его
внутренние состояния (ленту, черновик, список сессий и т.д.), без
необходимости вручную сбрасывать что-либо самим. После ремонта плеер
дожидается, пока свежий `App` заново подпишется через `subscribe()`
(`window.__accReceive` снова определён), и только тогда начинает
скармливать шаги нового сценария.

Кнопка активного/только что запущенного сценария подсвечивается в
`ScenarioToolbar`, чтобы было видно, что сейчас на экране.

## Список сценариев

Группы соответствуют категориям в типе `Scenario.category`.

**grouping - про саму фичу группировки вызовов**
1. Одиночный вызов инструмента - без рамки группы.
2. Пачка из 5-10 вызовов подряд - живой текущий вызов с тикающим
   таймером, в конце «N tools · время», разворачивается по клику.
3. Та же пачка, но с «разрывом» между внутренними шагами (без текста
   между вызовами) - группа не должна рваться.
4. Мысль модели (`thinking`) вперемешку с обычными вызовами в одной
   группе, включая мысль ПОСЛЕ того, как группа уже закрылась (именно
   этот случай был багом, найденным финальным ревью).
5. Текст между двумя вызовами - должен создавать две отдельные группы.

**cards - остальные карточки ленты**
6. Список задач (`TodoWrite`).
7. План на согласование (`ExitPlanMode`) + кнопка «одобрить».
8. Вопрос с вариантами (`AskUserQuestion`) + ответ.
9. Запрос разрешения на выполнение - карточка вызова показывает «waiting
   for you», а не «running», пока разрешение не выдано.
10. Вызов субагента (`Task`) с прогресс-баром и деталями.
11. Фоновый субагент от скилла (`system`-события `task_started` /
    `task_progress` / `task_notification`, без обычного `tool_use`).
12. Несколько параллельно работающих агентов - шапка со стримами.

**system - служебные состояния**
13. Обрыв сессии посреди работы (`processExited`) - crash-баннер и
    прерванный вызов внутри незавершённой группы.
14. Сжатие контекста (`compact_boundary`).
15. Ошибка хода (`is_error` в `result`).
16. `/clear` - разговор стёрт (`conversation_reset`).
17. Ответ с богатым markdown (код-блоки, списки, жирный текст).

**combined**
18. «Всё сразу» - один длинный реалистичный ход, смешивающий несколько
    типов карточек подряд (похоже на скриншот, с которого начался весь
    разговор про эту фичу).

## Структура файлов

- `webview/harness.html` - точка входа, аналог `index.html`.
- `webview/src/harness/harness.tsx` - монтирование `App` + `ScenarioToolbar`,
  логика `runId`/ремонта.
- `webview/src/harness/ScenarioToolbar.tsx` + `harness.module.css` -
  панель кнопок, сгруппированная по категориям.
- `webview/src/harness/player.ts` - проигрывание шагов, тайминги,
  `cancel()`.
- `webview/src/harness/events.ts` - хелперы построения `AgentEvent`/
  `ShellMessage` (по образцу `toolUseEvent`/`toolResultEvent`/`textEvent`
  из `webview/src/feed/build.test.ts`, но для харнесса свои, тестовый файл
  не трогаем), `bootstrapSteps()`, хелпер разбивки текста на потоковые
  кусочки.
- `webview/src/harness/scenarios/` - по файлу на категорию
  (`grouping.ts`, `cards.ts`, `system.ts`, `combined.ts`) + `index.ts`,
  собирающий общий список для тулбара.
- `webview/src/App.tsx` - точечная правка: необязательный параметр у
  `submit`, один `useEffect` с `window.__accHarnessSend` под
  `import.meta.env.DEV`.

## Границы

- Харнесс не пытается точно воспроизвести бэкенд или реального агента -
  сценарии просто подсовывают правдоподобные, протокольно корректные
  события.
- Никакой персистентности/сохранения кастомных сценариев - только то, что
  зашито в код.
- Автотестов на сам харнесс не пишем (это инструмент для ручного
  визуального ревью, а не часть продукта) - достаточно, что `tsc --noEmit`
  и сборка dev-сервера проходят чисто.
- Мобильная/адаптивная вёрстка страницы не важна - её открывают в обычном
  окне браузера при разработке.

## Проверка

- `tsc --noEmit` по всему `webview/` (харнесс - часть той же TS-программы,
  ошибки в нём тоже должны ловиться).
- Ручная visual-проверка: поднять `pnpm dev`, пройтись по всем 18 кнопкам,
  убедиться что каждая доигрывает до конца без ошибок в консоли браузера
  и рисует ожидаемую карточку.
- Отдельно проверить, что `vite build` (тот же вызов, что использует
  gradle) не включает `harness.html` и код харнесса в `dist` - размер и
  список файлов `dist` до/после появления харнесса не должны отличаться
  по составу (кроме, собственно, кода самого фичи ленты).
