# Сворачиваемая группа вызовов инструментов в ленте

## Контекст и цель

Сейчас в ленте webview-панели каждый вызов инструмента (Bash, Read, Grep,
Edit, Write, Web, MCP, «мысль» модели) — отдельная, всегда видимая строка
(`ToolItem`, рисуется `ToolCard`). Когда Клод за один ход вызывает
инструменты десятками подряд (типичный случай при исследовании кода), лента
превращается в стену одинаковых строк, за которой не видно сути хода.

Цель: подряд идущие вызовы обычных инструментов сворачивать в одну карточку.
Пока работа идёт — карточка по умолчанию свёрнута и показывает только
текущий вызов с живым таймером. Когда ход завершён — карточка остаётся
свёрнутой в истории и показывает «N вызовов · время»; по клику разворачивается
в привычный список, где каждую карточку внутри по-прежнему можно раскрыть
отдельно (дифф, вывод команды и т.п.).

## Область действия

**Входит в группу:** любой вызов, который сегодня рисуется как `ToolItem` —
это все чипы `THINK/READ/GREP/EDIT/WRITE/BASH/WEB/MCP/TOOL`, включая блоки
«мысли» модели.

**Не входит, прерывает группу и остаётся отдельной видимой карточкой, как
сейчас:** `TodoWrite` (список задач), `Task`/`Agent` (запуск субагента),
`ExitPlanMode` (план), `AskUserQuestion` (вопросы), запрос разрешения,
текстовый ответ, сообщение пользователя, checkpoint/compact/meta/crash.

**Одиночный вызов** (Клод сделал ровно один вызов подряд, дальше — текст или
другой не-инструмент) визуально остаётся ровно таким, как сегодня: без рамки
группы, без дополнительной стрелочки-заголовка. Обёртка группы появляется
только когда вызовов действительно два и больше — то есть ровно там, где
сегодня возникает стена карточек.

## Модель данных

В `webview/src/feed/types.ts` добавляется новый вид элемента ленты:

```ts
export interface ToolGroupItem {
  id: string
  kind: 'toolGroup'
  tools: ToolItem[]
  /** Есть ли внутри хотя бы один ещё не завершённый вызов. */
  pending: boolean
  /** Точное время от первого вызова до последнего результата; пока pending — тикает. */
  duration: string
}
```

В объединении `FeedItem` элемент `ToolItem` на верхнем уровне заменяется на
`ToolGroupItem`. Сам `ToolItem` не удаляется — он остаётся как тип дочерних
элементов внутри `tools`, и рендерится существующим `ToolCard` без изменений.

## Логика сборки ленты (`webview/src/feed/build.ts`)

Вводится единая точка добавления вызова инструмента в ленту (на замену
прямого `push` для tool-блоков и для псевдо-инструмента `THINK`):

- Если последний элемент `state.items` — `ToolGroupItem`, новый вызов
  дописывается в его `tools`, группа помечается `pending: true`.
- Иначе создаётся новый `ToolGroupItem` с этим единственным вызовом внутри.
  Идентификатор группы можно вывести из id первого дочернего вызова
  (`g-<id первого tool>`), чтобы не заводить отдельный счётчик. Идентификаторы
  самих дочерних вызовов не меняются: как и сегодня, это `block.id` для
  настоящего вызова инструмента и `i-<seq>` для псевдо-инструмента `THINK`.
- Важно: решение «дописать или начать новую» смотрит только на то, чем был
  **последний элемент ленты**, а не на то, `pending` группа или уже
  разрешилась. Между внутренними шагами одного агентского хода группа вызовов
  может на мгновение стать полностью разрешённой (все текущие вызовы
  вернули результат), а затем тут же продолжиться следующим вызовом без
  единого текстового блока между ними — это тот самый непрерывный «взрыв» из
  27 вызовов на скриншоте, и он должен остаться одной группой. Разрывает
  цепочку только появление НЕ-инструмента между вызовами (текст, todo, план,
  вопрос, задача субагента, сообщение пользователя и т.д.) — оно естественно
  становится новым «последним элементом», и следующий вызов инструмента уже
  откроет новую группу.
- Время начала группы фиксируется в `state.startedAt` под её собственным id
  (аналогично тому, как уже фиксируется время начала одиночного
  `tool`/`task`), в момент создания группы — не при первом вызове, а именно
  при создании обёртки, чтобы не потерять точку отсчёта, если первый
  дочерний вызов успеет разрешиться раньше, чем начнётся второй.

Обработка результата (`applyToolResults`) для вызова, лежащего внутри
группы: находит нужный дочерний `tool` внутри `tools` того элемента, что уже
делает сейчас, обновляет его как раньше, затем пересчитывает
`pending = tools.some(t => t.pending)` у родительской группы. В момент, когда
группа переходит из `pending: true` в `false`, её `duration` фиксируется как
точная разница `now - startedAt[group.id]`, запись из `startedAt` удаляется.

Тик длительности (`tickDurations`) и обработка обрыва сессии
(`applyProcessExited`) должны спускаться и внутрь `tools` группы — сегодня
они проверяют только элементы верхнего уровня `kind === 'tool' | 'task'`,
после изменения им нужно дополнительно обходить дочерние вызовы внутри
`toolGroup`, обновляя каждому свою длительность/статус прерывания, и следом
пересчитывать агрегат (`pending`, `duration`) самой группы.

## Отображение

Новый компонент `ToolGroupCard` (`webview/src/components/items/`):

- Если `tools.length === 1` — рендерит напрямую соответствующий `ToolCard`
  без какой-либо дополнительной обёртки; открытие/закрытие детали остаётся
  завязано на id самого вызова, как сегодня.
- Если `tools.length > 1`:
  - **Пока `pending`:** заголовок показывает чип и цель последнего (текущего)
    вызова, плюс тикающее время из `duration` группы, плюс счётчик
    вложенных вызовов. Обновляется на каждый новый вызов внутри группы.
  - **Когда `!pending`:** заголовок сворачивается в нейтральную строку вида
    «N tools · время» (формулировка count+duration; конкретную вёрстку и
    микротекст можно уточнить при реализации, ориентируясь на терминологию,
    уже принятую в статус-строке — «tools», не «tool calls»).
  - По клику (используется существующий `cards.isOpen`/`cards.toggle` по id
    группы — по умолчанию закрыто, ничего нового заводить не нужно)
    разворачивается в список дочерних `ToolCard`, каждая карточка внутри
    сохраняет собственное независимое раскрытие деталей.

`Feed.tsx` получает новый `case 'toolGroup'` в `ItemView`. Вычисление
`lastPendingId` (кому из ожидающих сейчас вызовов нужно показать «waiting for
you» вместо «running», пока висит неотвеченный запрос разрешения) должно
теперь заглядывать и внутрь групп: собирать кандидатов не только среди
вызовов верхнего уровня `tool`/`task`, но и разворачивая `tools` каждой
`toolGroup`. Найденный id пробрасывается вниз тем же способом, что и
сегодня — до конкретной дочерней карточки, и до заголовка группы, если
«ожидающий» вызов — тот самый текущий/последний.

## Сопутствующая правка

`App.tsx: streamStatus` сейчас считает `panel.items.filter(item => item.kind
=== 'tool').length` — то есть вызовы за ВЕСЬ чат, хотя подпись обещает «this
turn». После этого изменения подсчёт стоит брать из хвостовой открытой
группы (`items.at(-1)`, если это `toolGroup` и она `pending` — берём
`tools.length`, иначе 0) — тем самым и подпись станет правдой, без
дополнительной логики.

## Границы (что не трогаем)

- Карточки `TodoWrite`/`Task`/`Plan`/`Ask`/`Permission` — без изменений.
- Внешний вид и поведение отдельного `ToolCard` внутри развёрнутого списка —
  без изменений.
- Ограничение/виртуализация числа вызовов внутри развёрнутого списка не
  вводится — показываются все, как и сегодня.
- `StreamsBar`/`AgentsDrawer` группировки не касаются, они устроены вокруг
  `TaskItem`, который в группу не входит.

## Проверка

- Расширить `webview/src/feed/build.test.ts` кейсами на уровне редьюсера: два
  и более подряд идущих вызова инструмента собираются в одну `toolGroup` с
  корректной агрегированной длительностью и `pending`, причём не рвутся на
  паузе между внутренними шагами хода без текста между ними; одиночный вызов
  (прерванный текстом или концом потока) остаётся в данных `toolGroup` с
  `tools.length === 1` (для рендер-прохождения насквозь); блок `THINK`
  встраивается в общую цепочку группы наравне с обычными вызовами; текстовый
  блок между двумя вызовами инструментов разрывает цепочку на две отдельные
  группы; обрыв сессии (`processExited`) корректно закрывает все ещё не
  завершённые вызовы внутри открытой группы и саму группу.
- Всплытие «ожидания разрешения» на нужный вложенный вызов (`lastPendingId` в
  `Feed.tsx`) — логика уровня рендера, не редьюсера, автотестом не покрывается
  (см. следующий пункт про компонентные тесты) — проверяется внимательной
  реализацией и, при необходимости, визуально через песочницу IDE.
- `tsc --noEmit` и `vitest run` в `webview/`.
- Компонентных тестов на React-рендер в репозитории сегодня нет (нет
  `@testing-library` в зависимостях) — заводить их ради этой задачи не
  будем, это отдельная тема. Полноценная визуальная проверка — через
  песочницу IDE (`scripts/sandbox.sh` / gradle), по запросу.
