# Релиз плагина

Запуск `/deploy` - это и есть разрешение на коммит, пуш и публикацию: проектное
правило «коммиты только с явного разрешения» этой командой и снимается. Ничего
не переспрашивай, доводи до опубликованной версии.

Останавливайся молча только там, где идти дальше нельзя (см. «Когда стоп»).

**Субагентов не запускать** - ни `cp-committer`, ни любых других. Текст коммита и
пункты CHANGELOG пишутся из знания того, что было сделано в этой сессии; агент
вхолодную вычитает тот же дифф заново и напишет хуже.

**Вывод пользователю - по скиллу `human-output`:** коротко, что выпущено и куда.

## Arguments

$ARGUMENTS

Пусто - поднимаем патч (0.7.9 → 0.7.10). `minor` / `major` - соответствующую
часть. Точная версия (`0.8.0`) - берём как есть.

## Шаг 1. Контекст (один вызов)

```bash
echo "== branch =="; git branch --show-current; \
echo "== version =="; grep '^version' gradle.properties; \
echo "== status =="; git status --short; \
echo "== unreleased commits =="; git log --oneline "$(git log -1 --format=%H --grep='^chore: bump version')"..HEAD; \
echo "== diff =="; git diff --stat; \
echo "== secrets present =="; grep -c '^export ACC_PUBLISH_TOKEN=' .env
```

В релиз войдёт всё сразу: незакоммиченные правки **и** коммиты после прошлого
bump. Про них и пишется CHANGELOG.

`.env` дальше не читай ничем: ни целиком, ни выборочно. Проверка наличия -
только счётчиком строк, как выше (правила в `CLAUDE.md`, раздел про секреты).

## Шаг 2. Проверки

```bash
cd webview && pnpm tsc --noEmit && pnpm vitest run; cd ..
./gradlew test --console=plain
```

Упало - стоп: сломанную версию в стор не отправляют.

## Шаг 3. Версия и CHANGELOG

1. `gradle.properties`: `version = X.Y.Z`.
2. `CHANGELOG.md`: новый раздел сразу под `## [Unreleased]`:
   `## [X.Y.Z] - YYYY-MM-DD` (дата локальная, `date +%F`).
3. Внизу файла: в строке `[Unreleased]` подменить прошлую версию на новую и
   добавить строку сравнения для новой - ровно как у предыдущих версий.

Раздел обязан называться точно как версия в `gradle.properties`: сборка берёт в
описание обновления именно его, а не найдя - `Unreleased` (см. `changeNotes` в
`build.gradle.kts`).

**Как писать пункты** (стиль задан прошлыми релизами, посмотри соседние разделы):

- Английский, по пункту на изменение, простым списком без подзаголовков.
- «Fixed: <что видел человек> ... <почему так было и что теперь>». Сначала
  симптом его словами, потом причина - одним-двумя предложениями.
- Про поведение, а не про код: ни имён файлов, ни классов, ни функций.
- Тире не ставить, только обычный дефис.
- Изменение, которое человек не заметит (рефакторинг, тесты), в список не идёт.

## Шаг 4. Коммиты и пуш

Два коммита, как в прошлых релизах:

1. Правки по сути - `fix(область): ...` / `feat(область): ...` с телом, которое
   объясняет причину поломки, а не перечисляет файлы. Только если в рабочем
   дереве есть незакоммиченные правки кода; чужие неотслеживаемые файлы, не
   относящиеся к работе, не добавляй - скажи о них в конце.
2. `chore: bump version to X.Y.Z` - `gradle.properties` и `CHANGELOG.md`.

Затем `git push origin main`.

## Шаг 5. Публикация

```bash
source .env && ./gradlew publishPlugin --console=plain
```

Без `--info` и `--debug`, без `env`/`printenv` до или после: в окружении лежат
токен и ключ подписи. Сам вывод задачи секретов не печатает - не расширяй его.

Задача сама собирает, подписывает и загружает архив. `BUILD SUCCESSFUL` -
версия ушла на модерацию, в списке обновлений появится через минуты-часы.

## Когда стоп

- Ветка не `main` - релизы идут только с неё.
- Проверки из шага 2 упали.
- `ACC_PUBLISH_TOKEN` в `.env` не найден - публиковать нечем.
- Версия в `gradle.properties` уже описана разделом в `CHANGELOG.md`: её,
  похоже, уже выпустили. Скажи об этом вместо второй публикации того же номера.
