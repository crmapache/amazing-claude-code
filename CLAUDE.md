# Amazing Claude Code — заметки для работы с проектом

Плагин для JetBrains IDE: нативная чат-панель для Claude Code внутри IDE
(`webview/` — React/TS-интерфейс панели, Kotlin-код плагина — в `src/`).

## Харнесс — песочница для быстрого ревью интерфейса

В `webview/src/harness/` живёт отдельная dev-only страница
(`webview/harness.html`, открывается через `pnpm dev` в `webview/` по адресу
`http://localhost:5173/harness.html`), которая проигрывает готовые
сценарии ленты (пачка вызовов инструментов, список задач, план, вопрос,
разрешение, субагенты, обрыв сессии и т.д.) без реального агента и без
IDE.

**Главный принцип: харнесс рендерит настоящий, ничем не изменённый
компонент `App` (`webview/src/App.tsx`)** — сценарии просто подсовывают
ему события через ту же точку входа, через которую в реальности приходят
сообщения от IDE. Из этого следует главное для работы:

- Харнесс сам по себе — **не отдельная копия интерфейса**, которую нужно
  чинить отдельно от настоящего приложения. Это одно и то же дерево
  компонентов.
- Когда я присылаю лог из харнесса (см. ниже) и говорю, что поправить —
  правь исходники самого интерфейса (`webview/src/components/`,
  `webview/src/feed/`, `webview/src/App.tsx` и т.д.), а не что-то внутри
  `webview/src/harness/`. Правка в реальном коде **автоматически** чинит
  и харнесс, и настоящую панель в IDE — они в буквальном смысле один и
  тот же код, ничего вручную синхронизировать не нужно.
- Трогать `webview/src/harness/` стоит, только если проблема в самом
  сценарии (неточно описал шаг, не тот текст, не та пауза) или в
  механике плеера/навигации по чекпоинтам — а не в том, как выглядит или
  ведёт себя сама лента.
- После правки — проверить в браузере тем же сценарием/чекпоинтом, на
  котором был баг (`pnpm dev` в `webview/`, если ещё не запущен), плюс
  прогнать `pnpm tsc --noEmit` и `pnpm vitest run` в `webview/`.

**Как я обычно присылаю баг:** в карточке чекпоинтов есть кнопка
«Скопировать лог» — она копирует в буфер сценарий, режим (авто/шаги) и
текущий чекпоинт. Я вставляю это тебе в сообщение вместе с описанием, что
не так — по этим трём строчкам сразу понятно, какой сценарий и какой
именно шаг смотреть.

## Запуск тестового WebStorm с уже открытым плагином

Когда прошу «подними песочницу», «запусти тестовый WebStorm», «глянь
живьём в IDE» — это про **реальный плагин в реальной IDE** (не про
харнесс из браузера, это разные способы проверки).

Команда:

```
./scripts/sandbox.sh
```

Что она делает:
- Гасит предыдущий запущенный экземпляр песочницы, если он ещё открыт
  (иначе каждый перезапуск плодил бы новое окно поверх старого).
- Собирает плагин и поднимает **отдельную, отдельно настроенную копию
  WebStorm** с этим плагином — не трогает мою основную рабочую IDE.
- Сразу открывает в ней `sandbox-project/` и саму панель плагина —
  ничего искать в интерфейсе не нужно.
- Лог сборки/запуска — в `build/sandbox.log`, если что-то пошло не так.

Запускается это долго (сборка + старт целой IDE), поэтому не глушить
процесс раньше времени и не считать зависшим — просто подождать. Закрыть
можно в любой момент обычным закрытием окна тестовой IDE.

Если нужно проверять правки в webview без пересборки плагина на каждый
чих — можно поднять `pnpm dev` в `webview/` и передать его адрес
песочнице:

```
./gradlew runIde -PopenProject=sandbox-project -PwebviewDevUrl=http://localhost:5173/
```

Тогда панель внутри тестовой IDE грузит интерфейс прямо с dev-сервера, и
правки в `webview/src/` видны сразу после сохранения, без пересборки
плагина целиком.

## Git — коммиты только с явного разрешения

Не создавай git-коммиты в этом проекте без явного разрешения на каждый
конкретный коммит — включая коммиты, которые обычно случаются «сами
собой» как часть процесса (например каждая завершённая задача при
subagent-driven execution). Я хочу сам посмотреть diff перед тем, как
что-то закоммитится.

Как это применять на практике:
- Правки в рабочем дереве (в том числе через субагентов-имплементеров)
  делать можно свободно — ограничение только на сам `git commit`.
- Если процесс/скилл предполагает коммит как часть шага (ревью задачи,
  правка по фидбеку ревьюера и т.д.) — довести код до готового
  состояния, прогнать проверки, но остановиться перед `git commit` и
  спросить.
- Не откатывай и не трогай уже сделанные раньше коммиты из-за этого
  правила — оно только на будущее.

## Секреты в `.env` — никогда не выводить содержимое целиком

В корне лежит `.env` с `ACC_PUBLISH_TOKEN`, `ACC_PRIVATE_KEY`,
`ACC_PRIVATE_KEY_PASSWORD`, `ACC_CERTIFICATE_CHAIN` — токен и ключ подписи для
публикации в JetBrains Marketplace. Ключ и сертификат — многострочные
PEM-блоки, а не пары `КЛЮЧ=значение`. Разовая попытка замаскировать вывод
самодельным `sed`/`grep` по шаблону `КЛЮЧ=` один раз уже привела к тому, что
весь PEM-блок (без `=` внутри строк) прошёл маскировку насквозь и целиком
утёк в чат — только через глупую самоуверенность, что «одна команда с виду
безобидна».

Правила железно, без импровизации на месте:
- Никогда не читать `.env` целиком и никаким инструментом — ни `cat`/`head`,
  ни `Read`, ни `sed`/`grep` с последующим показом результата. Не пытаться
  маскировать его содержимое самостоятельно: нет гарантии, что маскировка
  учла все форматы значений в файле, а PEM-блоки такую гарантию ломают
  систематически, не как исключение.
- Проверить, что переменная вообще задана, не читая значение, можно только
  так: `grep -c '^export ИМЯ_ПЕРЕМЕННОЙ=' .env` — считает строки, ничего не
  печатает. Если не уверен, что метод не покажет значение — не проверяй
  файл вообще, а спроси меня напрямую.
- Значения секретов из `.env` (токен публикации, приватный ключ,
  сертификат) нигде не печатать и не выводить в чат — ни напрямую, ни
  через отладочный вывод команды. Сами переменные ты можешь передать
  Gradle через `source .env`: команда их только читает как окружение
  процесса, не показывает.
- Финальный `source .env && ./gradlew publishPlugin` — теперь твоя
  задача, а не моя. Запускай без `--info`/`--debug` (там может
  засветиться окружение) и без вывода `env`/`printenv` до или после —
  сам вывод publishPlugin секретов не печатает, но не расширяй его.
