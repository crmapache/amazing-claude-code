# Amazing Claude Code — заметки для работы с проектом

Плагин для JetBrains IDE: нативная чат-панель для Claude Code внутри IDE
(`webview/` — React/TS-интерфейс панели, Kotlin-код плагина — в `src/`).

## Монорепа: три JS-пакета под одним `pnpm install`

В корне лежит `pnpm-workspace.yaml` с тремя пакетами: `webview/` (панель, телефонный клиент,
харнесс), `relay/` и `feedback-service/`. Отсюда:

- один `pnpm install` в корне поднимает все, локфайл тоже один — корневой;
- `pnpm -r build` и `pnpm -r test` прогоняют все пакеты, `pnpm build:webview` / `pnpm dev:relay` /
  `pnpm dev:feedback` и прочие корневые скрипты — по одному;
- Gradle ставит зависимости только панели (`pnpm install --filter ./webview` из корня): собирать
  плагин, попутно вытягивая зависимости сервера, который в плагин не входит, незачем.

Внутри пакетов всё как было: `cd webview && pnpm dev`, `cd relay && pnpm build` работают.

## Харнесс — песочница для быстрого ревью интерфейса

В `webview/src/harness/` живёт отдельная dev-only страница
(`webview/harness.html`, открывается через `pnpm dev` в `webview/` по адресу
`http://localhost:5173/harness.html`), которая проигрывает готовые
сценарии ленты (пачка вызовов инструментов, список задач, план, вопрос,
разрешение, субагенты, обрыв сессии и т.д.) без реального агента и без
IDE.

**Главный принцип: харнесс рендерит настоящий, ничем не изменённый
компонент `App` (`webview/src/App.tsx`)** — сценарии просто подсовывают
ему события через ту же точку входа, через которую в реальности приходят
сообщения от IDE. Из этого следует главное для работы:

- Харнесс сам по себе — **не отдельная копия интерфейса**, которую нужно
  чинить отдельно от настоящего приложения. Это одно и то же дерево
  компонентов.
- Когда я присылаю лог из харнесса (см. ниже) и говорю, что поправить —
  правь исходники самого интерфейса (`webview/src/components/`,
  `webview/src/feed/`, `webview/src/App.tsx` и т.д.), а не что-то внутри
  `webview/src/harness/`. Правка в реальном коде **автоматически** чинит
  и харнесс, и настоящую панель в IDE — они в буквальном смысле один и
  тот же код, ничего вручную синхронизировать не нужно.
- Трогать `webview/src/harness/` стоит, только если проблема в самом
  сценарии (неточно описал шаг, не тот текст, не та пауза) или в
  механике плеера/навигации по чекпоинтам — а не в том, как выглядит или
  ведёт себя сама лента.
- После правки — проверить в браузере тем же сценарием/чекпоинтом, на
  котором был баг (`pnpm dev` в `webview/`, если ещё не запущен), плюс
  прогнать `pnpm tsc --noEmit` и `pnpm vitest run` в `webview/`.

**Как я обычно присылаю баг:** в карточке чекпоинтов есть кнопка
«Скопировать лог» — она копирует в буфер сценарий, режим (авто/шаги) и
текущий чекпоинт. Я вставляю это тебе в сообщение вместе с описанием, что
не так — по этим трём строчкам сразу понятно, какой сценарий и какой
именно шаг смотреть.

### Картинки для страницы плагина снимаются тем же харнессом

Скриншоты в JetBrains Marketplace — это кадры харнесса, а не отдельные макеты. Как устроено:

- **Что на кадре** — сценарии категории «Frames for the listing» в
  `webview/src/harness/scenarios/showcase.ts`. Каждый — один чекпоинт, оставляющий панель в готовом,
  «фотогеничном» состоянии; сквозь все кадры идёт один выдуманный проект (`nimbus-checkout`, ветка с
  PR), чтобы набор читался как один рабочий день. Правишь содержимое кадра — правишь этот файл.
- **Как снимается** — `?shot=<id>` в харнессе (`harness.tsx`) убирает свою обвязку и отдаёт панели всё
  окно, а `window.__accShotReady` говорит камере, что лента уже собрана. Сама камера —
  `scripts/screenshots.mjs`, инструкция по запуску в его шапке; Playwright намеренно не в зависимостях
  репозитория.
- Размер кадра — 1200×800 CSS при dpr 2, то есть PNG 2400×1600 (маркетплейс просит от 1200×760 и
  одинаковых пропорций у всех картинок).

## Запуск тестового WebStorm с уже открытым плагином

Когда прошу «подними песочницу», «запусти тестовый WebStorm», «глянь
живьём в IDE» — это про **реальный плагин в реальной IDE** (не про
харнесс из браузера, это разные способы проверки).

Команда:

```
./scripts/sandbox.sh
```

Что она делает:
- Гасит предыдущий запущенный экземпляр песочницы, если он ещё открыт
  (иначе каждый перезапуск плодил бы новое окно поверх старого).
- Собирает плагин и поднимает **отдельную, отдельно настроенную копию
  WebStorm** с этим плагином — не трогает мою основную рабочую IDE.
- Сразу открывает в ней `sandbox-project/` и саму панель плагина —
  ничего искать в интерфейсе не нужно.
- Лог сборки/запуска — в `build/sandbox.log`, если что-то пошло не так.

Запускается это долго (сборка + старт целой IDE), поэтому не глушить
процесс раньше времени и не считать зависшим — просто подождать. Закрыть
можно в любой момент обычным закрытием окна тестовой IDE.

Если нужно проверять правки в webview без пересборки плагина на каждый
чих — можно поднять `pnpm dev` в `webview/` и передать его адрес
песочнице:

```
./gradlew runIde -PopenProject=sandbox-project -PwebviewDevUrl=http://localhost:5173/
```

Тогда панель внутри тестовой IDE грузит интерфейс прямо с dev-сервера, и
правки в `webview/src/` видны сразу после сохранения, без пересборки
плагина целиком.

## Удалённый доступ: три части одного кода

Фича «ответить агенту с телефона» живёт в трёх местах, и они намеренно делят один код, а не
повторяют друг друга:

- **`src/main/kotlin/.../claude/`** — ядро сессий. `ClaudeSessionHub` (сервис уровня проекта)
  владеет разговорами, ведёт журнал событий с порядковыми номерами и рассылает их подписчикам.
  Панель — один из подписчиков, телефон — другой. Разговоры переживают закрытие панели и умирают
  вместе со вкладкой чата.
- **`src/main/kotlin/.../remote/`** — сетевой агент, конверты, криптография, привязка устройств.
- **`relay/`** — маленький сервер (Node + TypeScript), который сводит IDE и телефон. Отдельный пакет
  workspace под Apache-2.0 (у плагина Elastic-2.0, и хостить его чужими руками она запрещает —
  подробности в `relay/README.md`). Лежит здесь до выделения в свой репозиторий, но самодостаточен:
  общего кода с панелью нет, вынос — это `git subtree split`, а не распутывание.
- **`webview/src/mobile/`** — клиент для телефона. **Третья точка входа** рядом с панелью и
  харнессом.

Главное правило то же, что и про харнесс: **мобильный клиент — не копия интерфейса**. Он рендерит
те же карточки ленты и гоняет тот же `feed/` — правка в общем исходнике чинит оба экрана сразу.
Если правишь ленту, правь `webview/src/feed/` и `webview/src/components/items/`, а не мобильную
обёртку. Отличается только плотность, и она переключается токенами (`[data-acc-density='touch']`
в `tokens.css`), а не вторым набором стилей.

Что легко сломать, не заметив:

- **Перечень разрешённого с телефона** (`remote/RemoteCommands.kt`). Добавил сообщение в
  `webview/src/protocol.ts` — `RemoteCommandsTest` упадёт, пока не решишь про него явно. Так и
  задумано: канал к агенту эквивалентен запуску команд на рабочей машине.
- **Проектные факты телефону пересылаются по белому списку** (`RemoteFeed.projectFact`). Композер на
  телефоне рисуется из четырёх сообщений - `project`, `usage`, `commandHints`, `files`, - и они не
  относятся ни к какому разговору, поэтому обычное правило подписки их выбрасывало. Список именно
  разрешающий: `init` в него не входит и входить не должен - он несёт рабочий каталог, а путь наружу не
  уходит (см. ниже). Список файлов там же режется по бюджету: кадр релея ограничен 256 КБ, а
  переросший кадр не обрезается, а выбрасывается целиком.
- **Путь проекта наружу не уходит.** Открытый проект едет под `locationHash`, закрытый — под хэшем
  пути, а сам путь остаётся в `RemoteAgent.recents`. Он же и список того, что вообще можно открыть с
  телефона: ключ, который никому не отдавали, не открывает ничего, поэтому запрос не может назвать
  произвольный каталог.
- **Список на телефоне присылают, а не спрашивают.** `ClaudeSessionHub.onInventoryChanged` дёргается,
  когда меняется статус разговора, ожидание человека или набор вкладок; телефон опрашивает раз в 25
  секунд только чтобы доказать, что линия жива. Забыть про push — вернуть «плашка не показывает, что
  работа идёт», ради чего это и сделано.
- **Телефону отдаётся конец разговора, а не весь журнал.** Очередь наружу (`RemoteOutbox`) держит
  2000 кадров и 8 МБ, а журнал одной вкладки — ровно столько же: отдать журнал целиком значило
  переполнить очередь, а переполненная очередь выбрасывается вся, и длинный чат на телефоне открывался
  пустым. Бюджет живёт в `ClaudeSessionHub.CatchUp`, и в ту же сторону работают два правила рядом:
  строки проигрываемого транскрипта (`replay`) наружу не идут вовсе — по окончании телефону отдают
  готовый хвост; а сигнал «переспроси» после переполнения адресуется каждому устройству отдельно
  (`RemoteAgent.resyncFrames`), иначе о потере никто не узнает.
- **Разговор опознаётся парой «проект + id», а не одним id.** Первая вкладка каждого проекта у IDE
  называется `main`, поэтому поиск по одному `sessionId` находил чужую вкладку: на телефоне это был
  чужой заголовок и чужое имя проекта над открытым чатом. См. `chatKey` в `webview/src/mobile` и
  `RemoteFeed.wantedBy` на стороне плагина.
- **Ответ на запрос и лента ходят разными дорогами.** Лента — по подписке (`deliver`), ответ на
  вопрос устройства (список прошлых разговоров) — через `SessionClient.answer`: он не относится ни к
  какому разговору, и по правилам подписки ему просто некуда идти.
- **Время на телефоне — чужое.** Всё, что лента отмеряет (начало хода, старт вызова, пауза перед
  повтором запроса), проставлено часами машины с IDE: телефон применяет журнал, подставляя в редьюсер
  метку `at` вместо своего «сейчас». Считать разницу против `Date.now()` телефона — вычитать одни часы
  из других, и при спешащей IDE счётчик «Claude is thinking» начинал ход с минуса. Поправка живёт в
  `webview/src/mobile/clock.ts` и раздаётся вниз контекстом `hooks/useNow`; калибруется по `at` в
  инвентаре (`RemoteAgent.inventoryBody`) — журнальные метки для этого не годятся, они говорят «когда
  случилось», а не «сколько сейчас». Пишешь на телефоне что-то, что вычитает время, — бери `useNow`,
  а не `Date.now`.
- **Очередь сообщений живёт в IDE, а не в окне** (`claude/SessionQueue.kt`). Раньше это было состояние
  React внутри экрана - своё у панели и второе у телефона. На столе это почти работает, на телефоне нет:
  страницу в кармане браузер выгружает без предупреждения, и сообщение пропадало - не отправлено и нигде
  не ждёт. Теперь список держит хаб, отдаёт его целиком сообщением `queue` (живьём, **не в журнал** -
  это то, что разговор скажет, а не то, что сказал; плюс копия в `attach` для подключившегося) и
  запускает первое из очереди в `sendStatus`, когда ход закончился. Та же единственная проверка «идёт
  ход» не пускает сообщение внутрь `/compact`: компакт - обычный ход, а написанное в идущий ход CLI
  чаще всего молча теряет (см. `PromptDelivery`). Порядок переставляется по идентификаторам, а не по
  индексам: на список смотрят два окна.
- **Формат конверта** описан трижды: `remote/Frame.kt`, `relay/src/wire/frame.ts`,
  `webview/src/core/frame.ts`. Меняешь — меняй везде, иначе стороны перестают понимать друг друга.
- **Вывод ключей** (`remote/Hkdf.kt` и `webview/src/core/crypto.ts`) проверен против векторов
  RFC 5869. Это единственное, что гарантирует совпадение половин, — они не проверяются друг о друга.

### Проверить всю цепочку живьём

```
cd relay && pnpm build && PORT=8080 RELAY_STATIC_DIR="" node dist/index.js
./gradlew runIde -PopenProject=sandbox-project -PremoteRelay=ws://localhost:8080
cd webview && pnpm vite -c vite.mobile.config.ts   # телефонный клиент на :5174
```

Флаг `-PremoteRelay` включает удалённый доступ только для этого запуска песочницы — в обычной IDE
он выключен, пока человек не включит его сам.

Второй клиент без сети и криптографии (для отлова гонок двух клиентов):

```
./gradlew runIde -PopenProject=sandbox-project -PlocalBridge=true
```

Адрес с одноразовым токеном пишется в лог IDE.

### Релей уже развёрнут

Публичный релей живёт на своём сервере (OVH + Coolify, приложение `acc-relay`), адрес —
`wss://relay.mzpizote.com`. Это и есть значение по умолчанию в плагине, так что включённый в панели
удалённый доступ соединяется с ним без настройки. Railway больше не используется.

Кода релея в GitHub нет, поэтому автодеплоя у него тоже нет: исходники лежат на сервере в
`/root/apps/acc-relay`, образ собирается там же и кладётся в локальный реестр. Как выкатывать —
по шагам в `relay/README.md`; общие правила по серверу — в скилле `infra`.

Телефонный клиент раздаёт сам релей: он собирается из `webview/`, копируется в `relay/public/` и
уезжает вместе с образом. **`relay/public/` намеренно игнорируется в корневом `.gitignore`, а не в
`relay/.gitignore`** — выгрузка каталога наружу уважает ignore-файлы внутри него, и правило там
выкинуло бы клиента из образа. Как деплоить — по шагам в `relay/README.md`.

Телефон звонит на тот релей, откуда загрузили клиента, а не на адрес, записанный при паре
(`relayAddress` в `webview/src/mobile/link.ts`). Поэтому переезд релея не просит всех пересопрягаться
— только перезагрузить страницу.

Ключи VAPID для пушей лежат в переменных сервиса и в `secrets/relay-vapid.env` (каталог `secrets/`
в `.gitignore`). В чат их не выводить.

Иконки телефонного клиента генерируются из логотипа плагина: `python3 scripts/mobile-icons.py`.
Отдельно нарисованных копий нет — правится логотип, перегоняются иконки.

## Аргументы запуска обязаны пережить чужую оболочку

Плагин не всегда запускает CLI сам. На Windows npm ставит его батником (`claude.cmd`), платформа
исполняет батник через `cmd.exe /c`, а батник передаёт полученное дальше через `%*`. И то и другое
построчно: перевод строки внутри аргумента заканчивает команду на этом месте, и весь хвост командной
строки до настоящего CLI не доезжает — молча, без ошибки, потому что с точки зрения `cmd` всё в порядке.

Так и потерялся `--resume`: единственным многострочным аргументом был брифинг
(`ClaudeLaunch.PANEL_BRIEFING`), и он стоит в середине командной строки. Разговор, открытый из истории,
поднимался пустым — панель рисовала свой реплей, а агент за ним не помнил ничего и писал в собственный
транскрипт. На macOS это не воспроизводится вовсе, а на Windows пряталось за настройками человека:
потерянные `--model`, `--effort` и `--permission-mode` совпали с тем, что у него стояло в
`~/.claude/settings.json`.

Отсюда правило: **в аргументах запуска нет ни переводов строки, ни кавычек** (кавычка так же
закрывает для `cmd` закавыченный кусок). Держит это `ClaudeLaunchTest`, а не аккуратность:
многострочный текст пишется в исходнике абзацами и схлопывается в строку на выходе
(`ClaudeLaunch.oneLine`). Вторая страховка — в `ClaudeSession.rememberConversation`: если процесс
поднялся под другим id, чем просили продолжить, это пишется в `DiagnosticsLog` и уезжает в отчёт.

## Правки ходят в обе стороны: буферы на диск, диск в IDE

Агент читает файлы с диска и про открытый редактор ничего не знает. IDE записывает буферы, когда фокус
уходит из приложения, а переход из редактора в нашу панель приложение не меняет - поэтому обычное
«поправил строку, не сохранил, попросил Claude» кончалось тем, что агент работал по старому тексту, а его
правка выглядела как откат чужой работы. Теперь перед ходом панель сохраняет сама
(`editor/UnsavedEdits.kt`).

- **Место одно - `ClaudeSessionHub.prompt`.** Через него идут и панель, и телефон, и отложенная очередь,
  и ответ на вопрос агента, так что отдельных веток не нужно. Второй вызов - перед командой через «!»
  (`ProjectCatalog.runShellCommand`): она читает тот же диск, и `git diff` сразу после правки должен
  показать эту правку.
- **Сохраняются файлы только этого проекта** - под его корнем или в его контенте. «Все документы IDE»
  означало бы записать чужое окно с другим проектом, которого агент всё равно не видит.
- **Ожидание ограничено двумя секундами.** Ждёт тот поток, который принёс сообщение, а для телефона это
  поток релея: модальный диалог в IDE держал бы его сколько угодно, и вместе с ним - все остальные
  разговоры на линии. Ход, начатый на секунду раньше, - это один файл, прочитанный по-старому; линия,
  не вернувшаяся никогда, - это удалённый доступ до похода к машине.
- **В диагностический буфер уходит только число сохранённого.** Имён файлов там быть не может - буфер
  уезжает наружу с отчётом (см. `DiagnosticsLog`).

### Обратная сторона: файлы перечитываются после правок агента

IDE держит свою картину диска и обновляет её, когда фокус возвращается в приложение или когда до
изменения доберётся её наблюдатель за файлами. Человек, отвечающий агенту из панели, приложение не
покидает, а наблюдатель настолько надёжен, насколько надёжна файловая система под проектом - сетевой
диск, симлинк, сотня файлов за ход, и он опаздывает или молчит. На экране в этот момент старый текст.
Поэтому поток агента читается второй раз - на предмет «что перечитать» (`editor/AgentEdits.kt`,
`editor/DiskRefresh.kt`).

- **Считается результат инструмента, а не намерение.** Между «агент просит Edit» и «файл изменился»
  стоит человек с разрешением: перечитать по запросу - значит перечитать до правки, а после самой
  правки уже никто не попросит.
- **Команда через оболочку файлов не называет** (`git checkout`, форматтер, свой скрипт), поэтому после
  неё и в конце хода IDE просят оглядеться целиком - тем же способом, что при возврате фокуса. Не чаще
  раза в две секунды, и не выбрасывая последний запрос, а откладывая: самый важный - последний, после
  конца хода уже ничего не спросит. Упавшая команда считается тоже: половина скрипта - это ровно тот
  случай, когда диск разошёлся с картиной IDE.
- **Перечитывается только то, что IDE и так знает.** Незнакомый файл - это файл, который она никому не
  показывает; тащить его в свою картину мира потому, что агент что-то читал в `/tmp`, незачем. Новый
  файл - другое дело: его находит пересчёт детей в знакомой папке.
- **Пачками, но без сдвига срока.** Правки идут очередями, каждый обход диска стоит денег, а пачка,
  которую отодвигает каждый новый файл, ушла бы в конец хода.

## Пока собирается иероглиф, клавиатура не наша

Поле ввода отбирает у браузера клавиши: Enter отправляет, Tab и стрелки ходят по подсказке, стрелки вверх
и вниз листают историю, Escape останавливает ход, цифры отвечают на разрешение. Ровно эти же клавиши
принадлежат методу ввода, пока он собирает символ: Enter подтверждает кандидата, Tab и стрелки ходят по
списку кандидатов, цифры выбирают из него, Escape выбрасывает недописанный символ. Отобранная у него
клавиша - это чип файла посреди корейского слова и остановленный ход в ответ на «нет, не этот иероглиф».

- **Признак берётся с события, а не из своей памяти** (`isComposing` у клавиши, `isComposingEvent` у
  правки поля). Композиция, оборванная уходом фокуса, не присылает события конца: запомненное «идёт набор»
  осталось бы поднятым навсегда - поле, которое больше не отправляет, и Escape, который больше не
  останавливает, без единого способа это вылечить, кроме перезагрузки панели.
- **Правило действует и поверх панели, а не только в поле** (`App`, `AskPanel`, `useDigitHotkey`).
  Escape поле гасит у себя (`stopPropagation`), а Shift+Tab до него не доходит вовсе - там окно-обработчик
  единственная защита. Карточку вопроса и цифровые хоткеи сегодня держит ещё и «в поле есть черновик», но
  это тонкая нитка: она рвётся, стоит перестать докладывать наружу недописанные символы.
- **Пока символ не дописан, поле не перестраивается** - ни зачистка опустевшего поля, ни превращение
  команды в чип. Браузер держит недописанный символ в собственном узле, и подмена узла вырывает символ из
  рук вместе с окном кандидатов. **Но наружу состояние докладывается как обычно**: именно по нему соседи
  понимают, что клавиша занята.
- **Конец композиции доделывает отложенное сам** (`handleCompositionEnd`), потому что обычного события
  правки после него не будет: Chromium присылает последнее ещё ВНУТРИ композиции и закрывает её молча.
  Синхронно, а не отложенно: человек подтверждает кандидата первым Enter и отправляет вторым, и отложенный
  проход встретил бы второй Enter с черновиком, который панель ещё считает пустым.
- **Это не только про азиатские языки.** Удержание буквы на маке и мёртвые клавиши европейских раскладок
  открывают меню акцентов тем же механизмом - там цифрами выбирают букву.
- Проверить: `scripts/composer-input.mjs` (инструкция в шапке файла). Половина прогона - обычный набор без
  всякого метода ввода: отправка, перенос строки, история, отмена, подсказка, чипы, Escape и цифры должны
  вести себя ровно как раньше.

## Кнопка «улучшить промпт»: отдельный запуск, а не ход в разговоре

Звёздочка слева от скрепки переписывает черновик в поле ввода. Живёт в трёх местах:
`webview/src/feed/improve.ts` (капсулы ↔ текст), `Composer`/`App` (кнопка, состояние, отмена),
`claude/PromptImprover.kt` (сам запуск).

- **Переписывает отдельный `claude -p`, а не текущий разговор.** Ход в разговоре попал бы в его
  транскрипт как чужой вопрос, и считала бы его та модель и тот effort, что стоят у вкладки: переписать
  строчку на Opus с максимальным усилием дороже и дольше, чем её отправить. Отдельный запуск заодно не
  требует своего API-ключа - это тот же вход, через который работает панель.
- **Запуск нарочно голый, и каждый флаг зачем-то нужен.** `--tools ""` - без инструментов (иначе это
  агент: полезет читать файлы, спросит разрешение, которое некому дать, и встанет до таймаута).
  `--safe-mode` - без CLAUDE.md, хуков, скиллов и стилей: «всегда отвечай по-русски» в личном CLAUDE.md
  превращало английский черновик в русский промпт. `--strict-mcp-config` без своего конфига - без MCP-серверов: их
  описания инструментов и есть основная цена такого запуска (замерено на этой машине: 70k токенов против
  500 на само дело). `--no-session-persistence` - переписывание не разговор, и в `/resume` ему нечего
  делать.
- **Обещание про язык держит не `--safe-mode`, а фраза в системном промпте.** `language` в
  `~/.claude/settings.json` - настройка, а не кастомизация, поэтому safe-mode её оставляет, и CLI
  превращает её в системное «всегда отвечай по-русски»: с этой настройкой английский черновик
  возвращался русским промптом три раза из трёх - ровно та жалоба, что есть у конкурента. Снять её можно
  было и грубо (`--setting-sources` без источников), но в том же файле живут `apiKeyHelper` и ключ, и
  кнопка, ломающая человеку вход ради его языка, меняет одну поломку на большую. Поэтому настройке
  отвечают, а не выбрасывают её: этот запуск никому не отвечает, значит правило про язык ответов к нему
  не относится, а какой язык нужен - решают инструкции, которые человек волен переписать.
- **Модель - Opus на низком усилии, запасная Sonnet.** Замерено на одних и тех же черновиках: Haiku
  отпадает по всем статьям сразу - 28 секунд на низком усилии и 49 на среднем, потому что тратит три-пять
  тысяч токенов размышлений на переписывание одной фразы, и выходит дороже всех. Sonnet отвечает за две
  секунды и обычно прав, но именно он подхалтуривает: выписал путь к файлу рядом с маркером, который этот
  файл и обозначает, и повторился внутри двух предложений. Opus отвечает за три и не делает ни того, ни
  другого. Усилие выше низкого не покупает ничего: на Sonnet ответ не меняется вовсе, на Opus включается
  размышление (шесть секунд) и начинают появляться требования, которых в черновике не было, - ровно то,
  чему инструкции больше всего сопротивляются. Запасная модель нужна потому, что сильная кончается первой:
  окно лимита, потраченное на разговор, не должно уносить с собой кнопку.
- **Повторное нажатие переписывает исходник заново, а не свой же ответ** (`App.improveSources`). Переписывать
  переписанное - значит плыть: каждый проход добавляет своего, и к третьему сообщение уже про другое. Поэтому
  второе нажатие - это ещё одна попытка над тем же исходником, ровно то, что человек имеет в виду, нажимая
  кнопку второй раз. Исходник забывается, как только к полю притронулись руками: отредактированный результат
  снова стал собственным черновиком, и лезть за него - выбросить эту правку. Отличить свою запись в поле от
  человеческой помогает флажок на время самой записи: поле рапортует наружу и то, и другое одинаково. Видно
  это в тултипе - он меняется на «Another take, from what you wrote», пока в поле лежит нетронутый ответ.
- **Отвергнутые варианты едут вместе с запросом** (`rejected` в `protocol.ts`, «TURNED DOWN» в
  `PromptImprover.body`). Нажатие поверх ответа - это и есть «не то», и молча выбрасывать это значит бросать
  те же кости против тех же слов: второй ответ выходил почти тем же предложением, и кнопка выглядела
  сломанной. Теперь модели показывают всё, мимо чего человек прошёл, и просят зайти с другой стороны -
  проверено живьём, три нажатия дают три по-настоящему разных формулировки. Хранится не больше четырёх
  последних: чем старше попытка, тем меньше она говорит о том, чего хотят сейчас. Блок стоит ПОСЛЕ инструкций
  и собирается плагином, а не входит в редактируемый текст: это факт про конкретное нажатие, а не правило
  переписывания, и он обязан работать и с чужими инструкциями.
- **Ни один символ написанного человеком не едет аргументом** - всё уходит в stdin (`ClaudeCli.feed`).
  Причина та же, что у `--resume` выше: перевод строки или кавычка обрывают команду на Windows. Поэтому
  и инструкции, которые человек волен переписать, идут в stdin, а аргументом (`--system-prompt`) едет
  только неизменяемая однострочная рамка без кавычек.
- **Капсулы не теряются, потому что уезжают маркерами.** Каждый чип заменяется на `[[1]]`, `[[2]]`, рядом
  едет строчка «что это такое», и ответ разбирается обратно по тому же списку. Маркер можно переставить -
  ради этого кнопку и жмут, - но нельзя потерять: чего в ответе не оказалось, дописывается чипом в конец
  сообщения. Повторённый маркер срабатывает один раз (второй копии картинки не бывает), выдуманный номер
  вычёркивается. Слэш-команда в начале не переписывается вовсе: она говорит, куда идёт сообщение, и
  возвращается на своё место как была.
- **Результат кладётся в поле через сам композер** (`Composer.registerApply`), а не в черновик панели:
  только так он становится шагом истории отмен, и Cmd+Z возвращает собственные слова. Если за те
  секунды, что шёл ответ, черновик изменился (сообщение ушло, дописали руками), ответ выбрасывается с
  объяснением над полем: вернуть отправленное сообщение в опустевшее поле хуже, чем не сделать ничего.
- **Инструкции живут в настройках IDE** (`ClaudePreferences.improveInstructions`), пустые значат
  встроенный текст. На экране встроенный текст стоит плейсхолдером, а не значением: сохранённый
  значением, он стал бы копией, и следующая его правка в плагине не доехала бы ни до кого, кто однажды
  открывал этот экран.
- **Телефону это пока запрещено** (`RemoteCommands`): кнопки там нет, а дверь открывают, когда в неё есть
  чему пройти. По сути дверь узкая - запуск без инструментов, без разговора и без записи на диск.
- **Поле пересобирается ещё и на смену раскладки** (`Composer.fillField`). Каждая раскладка рисует поле в
  своей разметке, поэтому переключение отдаёт совершенно новый пустой contentEditable, а обычный эффект
  смотрит на неизменившиеся токены и оставляет его пустым. Потеряно при этом ничего не было - Send
  отправлял написанное, - чем и было хуже потери: черновик пропадал с экрана, его нельзя было ни прочитать,
  ни поправить, и он возвращался только тем, что его отправляли вслепую. Сторожит не «раскладка
  изменилась», а «под какую раскладку поле собрано»: на первом рендере поле уже наполнил обычный эффект, и
  второй проход поставил бы каретку в панель, по которой ещё никто не щёлкал.
- **Пока идёт переписывание, звёздочки мигают по очереди, а не крутятся** (`acc-sparkle-twinkle`). Кручение
  было первой попыткой и было неверным дважды: четырёхлучевая звезда, вращающаяся вокруг своего центра,
  читается как плохо нарисованный спиннер, а маленькая при этом моталась вокруг большой и всё качалось.
  Мигание - это то, что звёздочка делает по своей природе: каждая в свой черёд разгорается и подрастает,
  иконка не сходит с места, и на четырнадцати пикселях это единственное различимое движение. Масштабируется
  каждая вокруг СВОЕГО центра - за это отвечает `transform-box: fill-box`, без него обе раздувались бы в
  сторону левого верхнего угла кадра.
- Проверить без IDE: харнесс - звёздочка есть в любом сценарии с лентой, ответ выдумывает плеер
  (`player.ts`), маркеры в нём нарочно переставляются, каждое следующее нажатие даёт другой зачин (плеер
  считает присланные отвергнутые варианты), а каждый третий запуск падает, чтобы полоска с ошибкой тоже
  была видна.

## Вопрос человеку ждёт столько, сколько нужно

Разрешение, план и вопрос с вариантами держат ход, пока человек не ответит. Ни таймера, ни автоответа
нет ни у панели, ни у CLI - и это обещание, а не случайность: у конкурента на ответ даётся пять минут,
после чего агент отвечает себе сам, и в отзыве это выглядело как «отошёл от стола, вернулся - важные
файлы удалены».

Проверено на CLI 2.1.247, разбором бинарника и живым прогоном с тем же способом запуска, что у плагина:
запрос `can_use_tool` уходит без срока и ждёт хоста сколько угодно (семь минут без ответа - ничего не
произошло, команда не выполнилась). Два механизма автоответа в CLI есть, и оба до панели не достают:

- **`askUserQuestionTimeout`** («Question auto-continue timeout» в `/config`) - автопродолжение вопроса
  «теми ответами, что уже выбраны». По умолчанию `never`, живёт в терминальном интерфейсе (обратный
  отсчёт, «нажмите любую клавишу, чтобы остаться») и сам себя выключает, когда ответить может кто-то
  снаружи. Панель - именно этот «кто-то»: вопрос уезжает к ней по каналу разрешений, и переменная
  `CLAUDE_AFK_TIMEOUT_MS`, выставленная нарочно, на него не подействовала.
- **`dialogExpiry`** (по умолчанию 5 минут) - срок жизни запроса `request_user_dialog`, и только для
  хостов, которые объявили, какие диалоги умеют. Панель не объявляет ни одного, а незнакомый подтип
  запроса получает честный отказ сразу (`PermissionChannel.Incoming.Unsupported`) - молчание там
  остановило бы ход навсегда.

Отсюда правило: **в пути разрешений не заводить таймеров.** Записи о заданных вопросах уходят только
вместе с процессом, который их задал (`ClaudeSession.awaitingPermission` чистится на stop, на смерть
процесса и на `/clear`), а `SessionPermissions.forgetUnanswerable` выбрасывает лишь то, чего этот
процесс уже не ждёт.

### Обратная сторона: вопрос могут отозвать, и это надо показать

CLI умеет забирать вопрос назад - присылает `control_cancel_request` с номером запроса. Случается это
по-настоящему: Stop, нажатый над висящей карточкой, отменяет вопрос вместе с ходом; то же делает хук,
успевший принять решение, пока панель уже спрашивают.

- **Отозванный вопрос не отвечают.** Ответ на него CLI выбрасывает («Ignoring can_use_tool
  control_response»), а карточка к тому времени уже нарисовала бы решение, которого никто не исполнял.
  Поэтому это `Incoming.Withdrawn` - новость, а не запрос; ответом (`Unsupported`) закрывается только
  незнакомый **подтип**.
- **Строка проверяется отдельной подстрокой.** `"control_cancel_request"` не содержит
  `"control_request"`, и до правки новость об отзыве проваливалась мимо разбора канала в разбор ленты.
- **Карточка закрывается «отозванной», а не «решённой».** Разрешение и вопрос с вариантами просто
  снимаются с экрана (в ленте их и не рисуют - они живут закреплёнными над полем ввода), а план
  остаётся: текст плана всё ещё стоит читать, и потерять его из-за остановленного хода - потеря
  человека. У плана пропадают кнопки и появляется строчка о том, что агент перестал ждать
  (`PlanCard.withdrawn`), а фильтр ленты убирает только по-настоящему решённые планы.
- **Слово одно на три стороны:** `SessionPermissions.WITHDRAWN`, `'withdrawn'` в `protocol.ts`,
  `planDecisionOf` в `useCardState.ts`. Последнее - потому что раньше план читался как «approve, иначе
  keepPlanning», и отзыв молча превратился бы в «отправили на доработку»: карточка исчезла бы из ленты.
- **Ждёт ли разговор человека - считается там же.** Пока запись жива, `awaitsYou` держит и строку
  состояния, и точку на вкладке, и плашку в списке на телефоне; отзыв обязан её снять, иначе разговор
  вечно обещает решение, которого больше нет.
- Проверить без IDE: харнесс, сценарии «A permission the agent takes back» и «A plan the agent takes
  back».

## Прошлый разговор открывается с конца, а не целиком

Чат из истории приезжает в панель **хвостом** (`ClaudeHistory.opening`), остальное подгружается
страницами по метке над лентой. До этого в панель уходил весь транскрипт сразу, и на Windows чат из
истории открывался пустым: файл рабочего дня — десятки мегабайт, он уезжал десятками пачек по мегабайту,
каждую приходилось резать на куски и склеивать уже в странице, а потерянный кусок уносил с собой всю
пачку из двухсот сообщений — молча, `JSON.parse` спотыкался на склейке. На macOS проходило, на Windows
канал в страницу уже нет.

Что из этого следует и что легко сломать:

- **Граница живёт в общем редьюсере, а не в каждом экране** (`oldestEventUuid`, `reachedStart`,
  `earlierPages` в `PanelState`; `historyPage` в `feed/build.ts`). Телефон умел это раньше панели и
  держал у себя вторую копию — теперь копия одна, и правка чинит оба экрана. Появится третий экран —
  ему не понадобится третье понимание «что выше этого».
- **Опознаётся по `uuid` строки транскрипта, а не по номеру.** Живой журнал и файл на диске не имеют
  общей нумерации: журнал подмешивает статусы и разрешения, которых на диске нет вовсе, — счётчик
  разъезжается на первом же изменении статуса.
- **`cursor` в `replayFinished` имеет три значения, и `null` — не то же, что его отсутствие.** Строка —
  это шов, `null` — «начало уже на экране», отсутствие — «про границу ничего не сказано, не трогай её».
  Последнее и есть телефон: реплей ему не пересылается вовсе (`RemoteFeed.isReplayLine`), у него своя
  граница из собственного хвоста.
- **Страница читается окном, а не файлом** (`ClaudeHistory.windowOf`): один проход, в памяти — страница
  плюс небольшой запас. Запас нужен, потому что нарезка может шагнуть выше, чтобы страница начиналась со
  строки, которую следующий запрос сможет назвать. Окно, обрезанное ровно по размеру, шагать некуда.
- **Размер страницы зависит от того, кто спросил** (`ClaudeHistory.earlier`, `hub.isLocal`).
  Телефонная страница обязана пролезть в кадр релея (256 КБ), панельная — нет. Одна на двоих была бы
  меньшей из двух, и чтение длинного чата на столе превратилось бы в череду нажатий.
- **Пачка в страницу ограничена весом, а не только числом сообщений** (`batchOf` в `WebviewHost`).
  Ограничения по числу хватало для живой работы и не хватало ни для чего крупного.
- **Куски нумерованы, и потеря больше не молчит.** Мост в странице проверяет порядок и разбор, а о
  провале сообщает обратно (`channelLoss` → `DiagnosticsLog`). Сообщение перечислено в `DENIED`
  (`RemoteCommands`) — оно про дорогу между IDE и её собственной панелью, и телефону там сказать нечего.
- **Позицию чтения держит `Feed`, а не экран** (проп `earlierPages`). Страница встаёт выше всего, что на
  экране, а браузер хранит прокрутку числом: без поправки читаемые строки прыгают вниз на высоту
  загруженного. Признак — счётчик отвеченных страниц, а не рост ленты: метка над лентой сохраняет свою
  личность, и по росту «загрузили выше» не отличить от «пришёл ответ ниже».
- Проверить без IDE: харнесс, сценарий «system» → чекпоинт про конец реплея. Метка над лентой там
  нажимается, страницы выдумывает сам плеер (`harness/player.ts`), третья приходит без курсора — на ней
  метка исчезает.

## Статистика и ачивки: одна книга на всю машину

Вкладка «Statistics» и экран ачивок за ней собирают цифры в трёх местах, и границы между ними
намеренные:

- **`src/main/kotlin/.../stats/`** - сбор и правила. `StatsCollector` (один на проект, живёт в
  `ClaudeSessionHub.stats`) слушает поток агента, сообщения, решения по разрешениям, вкладки и
  пишет всё в `StatsLedger` - сервис уровня приложения, у которого один JSON-файл на всю машину
  (общий каталог JetBrains, чтобы WebStorm и IntelliJ считали в одну книгу). Единица хранения -
  `DayRecord`: день одного проекта, только счётчики, суммы и максимумы. Любой диапазон на вкладке -
  это арифметика над днями, поэтому переключение 7/30/всё не ходит в IDE.
- **Вкладка считает всю машину, а не открытый проект.** Панели уезжают дни, уже сложенные по всем
  проектам (`StatsSnapshot.daysTogether`), и по ним же считаются ачивки. Счётчики складываются,
  максимумы берутся по большему, а минуты **объединяются, а не суммируются**: два проекта, работавшие
  в одну минуту, потратили одну минуту жизни. Сумма проектных минут ровно этим и врала - день в 2 часа
  показывался как 4. По проектам осталась одна карточка «WHERE THE HOURS WENT», и она рисуется из
  минут, которые проекты несут отдельно от дней; её строки законно складываются в больше, чем длится
  день. Пятичасовое окно лимита - тоже про аккаунт, а не про проект: считается по множеству окон.
- **Из IDE едет не только следующая планка, но и взятая** (`line` в `AchievementState`, `Achievements.Definition.lineOf`). Без неё панель знала только «сколько ещё до следующей», и оба места, где это видно, врали: полоска прогресса заполнялась от нуля (на IV она почти полная всегда), а «earned lately» подписывала тир текущим значением - «10 hours · III» над «7h 23m» читается как обещание, которое не выполнено, хотя третья планка стоит на шести часах, а имя ачивки - это пятая. Правишь лестницы - не забывай, что панель теперь считает прогресс между двумя планками.
- **Планки ачивок калиброваны под агента, а не под человека с клавиатурой.** Пятый тир - примерно год
  плотной работы, первый - первые дни. Считать «нормальным» темпом ~4000 строк и ~1000 команд в день:
  на прежних планках («тысяча строк», «десять файлов за ход», «пять MCP») экран заполнялся за два дня.
  Ладдеры про привычку (серии, выходные, недели) не трогать - они и так медленные. Двигаешь планку -
  поднимай `Achievements.RULES_VERSION` и вписывай id в `RECALIBRATED`: при следующем запуске книга
  разово забудет взятые тиры этих ачивок и заработает их заново. Иначе на экране останется пятый тир
  против планки, которой больше нет.
- **Ступеней у ачивки столько, сколько линий в её лестнице** (`Achievements.Definition.steps` → `steps` в
  сообщении `statistics` → пипсы на карточке). Пять - у большинства, но не догма: у вехи одна, у «Thanks»
  две (звезда на GitHub и отзыв на странице плагина - других способов сказать спасибо в плагине нет).
  Короткая лестница, пройденная целиком, красится верхним тиром: «сделано» есть «сделано», сколько бы
  линий на это ни ушло. Тест каталога читает `Achievements.kt` и падает, если стороны разошлись в числе
  ступеней. Двигаешь лестницу - смотри `RECALIBRATIONS`: забывается только то, что переехало после версии,
  записанной в книге, а не весь список разом.
- **Имя ачивки - имя, а не планка; подпись - что меряют, а не сколько надо** (`catalogue.ts`). Под именем
  и так стоит цифра против цели, а рядом с ним - римский тир, поэтому «Tier V wants 60» и «30 active days»
  в подписи повторяли то, что уже видно, а имя-число («10 hours» над «7h52/8h») читалось как невыполненное
  обещание: это третья линия из пяти, а имя взято с пятой. Цепочки по одной метрике (часы в панели, строки)
  различаются титулами, а не числом, - тест каталога держит имена уникальными и запрещает слово «tier» в
  подписи. Веха - одна планка: одна полоса вместо пяти, без римской цифры, и в общем счёте шагов она стоит
  единицей, а не пятёркой.
- **Правила ачивок - в Kotlin (`Achievements.kt`), слова и иконки - в TS
  (`webview/src/stats/catalogue.ts`).** Связаны по id, и тест с каждой стороны читает файл другой
  стороны: добавил ачивку в одном месте - оба теста красные, пока не добавишь во втором. Момент
  получения тира записывается в IDE, а не в панели: тир, взятый с телефона ночью, должен получить
  свою дату и без открытой панели.
- **Подпись в угловых скобках - не модель** (`StatsCollector.isRealModel`). CLI подписывает `<synthetic>`
  свои собственные ответы: прерванный ход, неизвестную команду, текст ошибки API. Принять её за модель -
  значит и завести в карточке строку, которой никто не запускал, и отнять ход у той модели, что реально
  работала до прерывания. Лента панели отбрасывает те же метки (`realModel` в `feed/build.ts`), а книга
  чистится при чтении файла, а не разово при старте: файл общий на машину, и соседняя IDE со старым
  плагином записала бы их снова.
- **Что легко сломать.** Каждая метрика обязана только расти (счётчик, сумма, максимум) - иначе тир
  придётся отбирать, а это не про ачивки. Строки replay не считаются вовсе (прошлое уже посчитано).
  Пути на диск не пишутся: проект - это имя плюс хэш, файлы в дне - короткие хэши. Сообщения
  `statistics` и `stat` в `RemoteCommands` запрещены для телефона: книга - про всю машину, а не про
  один разговор. Что считает только панель (чипы в сообщении, сердечко, руки на клавиатуре) - она и
  сообщает через `stat`; всё остальное IDE видит сама и там же считает.
- **Одна ачивка делится отдельно** (кнопка на карточке, `PosterOptions.width` и `heading`). Дорога та же,
  что у целого экрана: клонируется живой узел карточки. Отличий два - ширина (целый экран требует 900 px
  под четыре плитки, одна карточка на такой ширине выглядит ошибкой) и шапка: у карточки логотип и имя
  плагина сверху с фразой от первого лица, у экрана - марка внизу. Кнопка стоит в верхнем ряду карточки
  и держит своё место всегда, иначе при наведении имя прыгало бы вбок; из снимка она вырезается по `SKIP`,
  а `data-hover` с клона снимается руками - указатель в момент нажатия стоит на карточке, и её подсветка
  уехала бы в картинку.
- **Картинка «поделиться» - это сам экран, а не второй его рисунок**
  (`webview/src/stats/poster.ts`). Кнопка в шапке клонирует живой узел вкладки, разворачивает у клона
  прокрутку, кладёт рядом подпись с логотипом и «plugin for <IDE>» и рисует всё это в canvas через
  SVG `foreignObject`. Отсюда три вещи, которые ломаются молча: внутрь `foreignObject` не попадают ни
  правила страницы (они собираются в свой `<style>`), ни переменные с `:root` (они пишутся на обёртку
  явно); а всё, чему на картинке не место, помечается атрибутом `SKIP` - иначе кнопка «поделиться»
  окажется на своём же снимке. Ширина снимка не меньше 900 px: в узкой панели плитки встают в одну
  колонку, и картинка выходит нечитаемой.
- **Скачивания в JCEF нет.** Ссылка с `download` внутри панели молча не делает ничего, поэтому
  байты уезжают в IDE сообщением `saveImage`, а файл пишет `webview/ImageDownloads.kt` - в папку
  загрузок, с уведомлением «Показать в Finder». Имя оттуда - только имя: разделители и точки в начале
  срезаются (`safeName`), папку выбирает плагин. Телефону `saveImage` запрещён.
- Проверить живьём без IDE: харнесс, сценарии «Statistics: a summer of work» и «Statistics: the
  second day» - они шлют готовое сообщение `statistics` и открывают вкладку. Кнопку «поделиться» там
  тоже можно нажать: харнесс играет роль оболочки и скачивает картинку браузером (`player.ts`).

## Обратная связь: обещание, которое держится тестом

Кнопка-облачко рядом с сердечком открывает экран «Feedback» в боковом меню: тип обращения, текст,
необязательная почта, вложения и галочка «приложить отладочные логи». Живёт это в трёх местах, как и
удалённый доступ:

- **`webview/src/components/Feedback.tsx`** — кнопка (три варианта под три раскладки композера), сама
  форма и второй экран с предпросмотром отчёта. Состояние формы держит `App.tsx`, а **не** сам экран:
  уход в предпросмотр размонтирует экран, и написанное пропало бы.
- **`src/main/kotlin/.../feedback/`** — `DiagnosticsLog` (кольцевой буфер технических событий),
  `FeedbackReport` (сборка отчёта), `FeedbackEnvironment` (версии), `FeedbackAttachments` (выбранные
  файлы), `FeedbackSender` (первый настоящий HTTP-запрос плагина), `FeedbackDesk` (координатор, живёт в
  `ClaudePanel`).
- **`feedback-service/`** — приёмник на своём сервере (`feedback.mzpizote.com`), пересылает в телеграм.
  Отдельный сервис, а не роут в релее: релей самодостаточен, под Apache-2.0 и готовится к выносу, а
  приёмник с токеном чужого бота был бы мёртвым грузом в каждой чужой копии. Как деплоить — в
  `feedback-service/README.md`.

Что легко сломать, не заметив:

- **Обещание «в отчёт не попадает приватное» держится `FeedbackReportTest`, а не аккуратностью.** Журнал
  разговора — это весь разговор: промпты, ответы, содержимое прочитанных файлов, пути. Из него не
  копируется ничего: каждая запись разбирается на форму (тип события, имя инструмента, размер в байтах,
  успех, тайминг), и строка отчёта пишется из этих фактов. Поля читаются по белому списку — незнакомое
  поле не попадает в отчёт по умолчанию. Имена файлов — короткими хэшами (тот же digest, что в
  статистике). Меняешь отчёт — этот тест главный.
- **В `DiagnosticsLog` нельзя класть содержимое.** Соблазн в одной строке: `ClaudePanel` при незнакомом
  сообщении логирует в `idea.log` весь JSON от панели, включая текст промпта. В буфер идут только тип и
  длина — буфер уезжает наружу, `idea.log` нет.
- **Панели не отдаются пути к файлам.** Выбранное держит IDE, панель знает `id`, имя и размер; при
  отправке она называет `id`. Поэтому она не может назвать файл, который человек не выбирал, и путь не
  может утечь с экрана, который отправляет данные наружу.
- **Сообщения фидбэка обрабатываются в `ClaudePanel`, а не в `SessionCommands`.** До `ClaudePanel`
  сетевой клиент не доходит физически — это гарантия помимо списка. В `RemoteCommands` они всё равно
  перечислены в `DENIED`, иначе `RemoteCommandsTest` красный.
- **В compact-раскладке кнопка стоит в ряду инструментов, а не рядом с сердечком.** Три селектора делят
  тот ряд и не сжимаются меньше своего текста (`.selectorAuto`), так что вторая кнопка выдавливает
  сердечко за край — ровно в тех узких панелях, ради которых compact и выбирают.
- **`PRIVACY.md` — часть фичи, а не документация о ней.** Там перечислено, что именно едет в отчёте;
  добавил в отчёт новое — правь и его, иначе страница начинает врать.
- **Ключ и адрес приёмника переопределяются для проверки**: `-PfeedbackUrl=http://localhost:8081` и
  `-PfeedbackKey=…` у `runIde`. Общий секрет в плагине — замедлитель против сканеров, а не защита: он
  лежит в открытом бинарнике, и в `feedback-service/README.md` это сказано прямо.
- Проверить форму без IDE: харнесс отвечает на сообщения фидбэка сам (`harness/player.ts`) — отдаёт
  образец отчёта, выдуманные файлы и каждую третью отправку роняет, чтобы был виден путь с ошибкой.

## Новогодний слой: три украшения и одно окно в календаре

С 24 декабря по 3 января панель наряжается: гирлянда одной строкой под шапкой, снег над лентой и
ледяная кнопка Send. Больше ничего — ни настройки, ни уровней, ни экрана в боковом меню.

- **Ворота — `webview/src/holiday.ts`**, и они целиком в панели, а не в IDE. Панель рисуется JCEF на той
  же машине, где идёт IDE, так что её `new Date()` — это и есть календарь IDE; скос часов, ради которого
  живёт `hooks/useNow.ts`, — проблема телефона, а телефон не наряжается. `hooks/useHoliday.ts` пересчитывает
  ответ на границе суток: тул-виндоу открывают один раз и оставляют, и панель, прочитавшая календарь при
  монтировании, встретила бы 24-е неукрашенной.
- **`HOLIDAY_OVERRIDE` перед релизом обязан стоять в `auto`, и это держит тест, а не память.** Это
  единственный включатель темы; `'on'` и `'off'` нужны, чтобы посмотреть слой в песочнице и в харнессе
  в обычный августовский день. Забыть его в `'on'` — выпустить вечную зиму, в `'off'` — декабрь без
  зимы, и больше ничто бы этого не поймало: с включённой темой панель работает нормально, просто
  наряжена в июле. Поэтому же сам ключ передаётся в `holidayUnder` параметром: у константы компилятор
  сузил бы тип до текущего значения и объявил две ветки из трёх недостижимыми.
- **Украшения кладутся в `App.tsx`, а не в `Feed`.** Лента общая с телефоном
  (`mobile/screens/Thread.tsx`), и всё, повешенное в `Feed`, поехало бы на экран, у которого своя шапка
  и свой композер.
- **Гирлянда стоит в потоке первым ребёнком `.content`, а не абсолютом поверх `.panel`.** При боковых
  раскладках `.panel` — грид, а `.railColumn` занимает всю его высоту: полоса поперёк панели
  перечеркнула бы чипы model/effort/mode. Снег — абсолютный слой внутри `.body` (он уже `relative` и уже
  красит фон ленты), `pointer-events: none` обязателен: лента — выделяемый текст.
- **Снег падает и пропадает — сугроб на нижней кромке пробовали и сняли.** Копящийся слой закрывает
  разговор, а украшение, которое приходится обчитывать, перестаёт быть украшением. Если идея вернётся:
  расти надо `transform`-ом блока во всю высоту, а не высотой короткого блока — `height` раскладывает
  ленту заново каждый кадр.
- **Лёд не трогает `Run` и `Queue`** (`[data-holiday] .send:not(.sendRun):not(.sendQueued):not(:disabled)`
  в `composer.module.css`). Оранжевая `Run` означает «уйдёт в твою оболочку» — это смысл, а не
  украшение; кнопка очереди делит класс с Send и намеренно нейтральна; у выключенной свой приглушённый вид.
- **Keyframes живут в `holiday.module.css` рядом со своими классами** — по той же причине, что описана в
  шапке `shell.module.css`: CSS-модуль переименовывает имена анимаций вместе с классами. Заодно весь слой
  снимается одним файлом.
- Проверить без IDE: харнесс, любой сценарий с лентой — он рендерит настоящий `App`, так что украшения
  видны сразу, включая ледяную кнопку.

## Git — коммиты только с явного разрешения

Не создавай git-коммиты в этом проекте без явного разрешения на каждый
конкретный коммит — включая коммиты, которые обычно случаются «сами
собой» как часть процесса (например каждая завершённая задача при
subagent-driven execution). Я хочу сам посмотреть diff перед тем, как
что-то закоммитится.

Как это применять на практике:
- Правки в рабочем дереве (в том числе через субагентов-имплементеров)
  делать можно свободно — ограничение только на сам `git commit`.
- Если процесс/скилл предполагает коммит как часть шага (ревью задачи,
  правка по фидбеку ревьюера и т.д.) — довести код до готового
  состояния, прогнать проверки, но остановиться перед `git commit` и
  спросить.
- Не откатывай и не трогай уже сделанные раньше коммиты из-за этого
  правила — оно только на будущее.

## Секреты в `.env` — никогда не выводить содержимое целиком

В корне лежит `.env` с `ACC_PUBLISH_TOKEN`, `ACC_PRIVATE_KEY`,
`ACC_PRIVATE_KEY_PASSWORD`, `ACC_CERTIFICATE_CHAIN` — токен и ключ подписи для
публикации в JetBrains Marketplace. Ключ и сертификат — многострочные
PEM-блоки, а не пары `КЛЮЧ=значение`. Разовая попытка замаскировать вывод
самодельным `sed`/`grep` по шаблону `КЛЮЧ=` один раз уже привела к тому, что
весь PEM-блок (без `=` внутри строк) прошёл маскировку насквозь и целиком
утёк в чат — только через глупую самоуверенность, что «одна команда с виду
безобидна».

Правила железно, без импровизации на месте:
- Никогда не читать `.env` целиком и никаким инструментом — ни `cat`/`head`,
  ни `Read`, ни `sed`/`grep` с последующим показом результата. Не пытаться
  маскировать его содержимое самостоятельно: нет гарантии, что маскировка
  учла все форматы значений в файле, а PEM-блоки такую гарантию ломают
  систематически, не как исключение.
- Проверить, что переменная вообще задана, не читая значение, можно только
  так: `grep -c '^export ИМЯ_ПЕРЕМЕННОЙ=' .env` — считает строки, ничего не
  печатает. Если не уверен, что метод не покажет значение — не проверяй
  файл вообще, а спроси меня напрямую.
- Значения секретов из `.env` (токен публикации, приватный ключ,
  сертификат) нигде не печатать и не выводить в чат — ни напрямую, ни
  через отладочный вывод команды. Сами переменные ты можешь передать
  Gradle через `source .env`: команда их только читает как окружение
  процесса, не показывает.
- Финальный `source .env && ./gradlew publishPlugin` — теперь твоя
  задача, а не моя. Запускай без `--info`/`--debug` (там может
  засветиться окружение) и без вывода `env`/`printenv` до или после —
  сам вывод publishPlugin секретов не печатает, но не расширяй его.

Вся процедура релиза (проверки, версия, CHANGELOG, коммиты, пуш,
публикация) живёт в скилле `/deploy` — правила выше он соблюдает, отдельно
их пересказывать не нужно.
