# Amazing Claude Code GUI - заметки для работы с проектом

Плагин для JetBrains IDE: нативная чат-панель для Claude Code внутри IDE
(`webview/` — React/TS-интерфейс панели, Kotlin-код плагина — в `src/`).

## Монорепа: три JS-пакета под одним `pnpm install`

В корне лежит `pnpm-workspace.yaml` с тремя пакетами: `webview/` (панель, телефонный клиент,
харнесс), `relay/` и `feedback-service/`. Отсюда:

- один `pnpm install` в корне поднимает все, локфайл тоже один — корневой;
- `pnpm -r build` и `pnpm -r test` прогоняют все пакеты, `pnpm build:webview` / `pnpm dev:relay` /
  `pnpm dev:feedback` и прочие корневые скрипты — по одному;
- Gradle ставит зависимости только панели (`pnpm install --filter ./webview` из корня): собирать
  плагин, попутно вытягивая зависимости сервера, который в плагин не входит, незачем.

Внутри пакетов всё как было: `cd webview && pnpm dev`, `cd relay && pnpm build` работают.

## Харнесс — песочница для быстрого ревью интерфейса

В `webview/src/harness/` живёт отдельная dev-only страница
(`webview/harness.html`, открывается через `pnpm dev` в `webview/` по адресу
`http://localhost:5173/harness.html`), которая проигрывает готовые
сценарии ленты (пачка вызовов инструментов, список задач, план, вопрос,
разрешение, субагенты, обрыв сессии и т.д.) без реального агента и без
IDE.

**Главный принцип: харнесс рендерит настоящий, ничем не изменённый
компонент `App` (`webview/src/App.tsx`)** — сценарии просто подсовывают
ему события через ту же точку входа, через которую в реальности приходят
сообщения от IDE. Из этого следует главное для работы:

- Харнесс сам по себе — **не отдельная копия интерфейса**, которую нужно
  чинить отдельно от настоящего приложения. Это одно и то же дерево
  компонентов.
- Когда я присылаю лог из харнесса (см. ниже) и говорю, что поправить —
  правь исходники самого интерфейса (`webview/src/components/`,
  `webview/src/feed/`, `webview/src/App.tsx` и т.д.), а не что-то внутри
  `webview/src/harness/`. Правка в реальном коде **автоматически** чинит
  и харнесс, и настоящую панель в IDE — они в буквальном смысле один и
  тот же код, ничего вручную синхронизировать не нужно.
- Трогать `webview/src/harness/` стоит, только если проблема в самом
  сценарии (неточно описал шаг, не тот текст, не та пауза) или в
  механике плеера/навигации по чекпоинтам — а не в том, как выглядит или
  ведёт себя сама лента.
- После правки — проверить в браузере тем же сценарием/чекпоинтом, на
  котором был баг (`pnpm dev` в `webview/`, если ещё не запущен), плюс
  прогнать `pnpm tsc --noEmit` и `pnpm vitest run` в `webview/`.

**Как я обычно присылаю баг:** в карточке чекпоинтов есть кнопка
«Скопировать лог» — она копирует в буфер сценарий, режим (авто/шаги) и
текущий чекпоинт. Я вставляю это тебе в сообщение вместе с описанием, что
не так — по этим трём строчкам сразу понятно, какой сценарий и какой
именно шаг смотреть.

### Картинки для страницы плагина снимаются тем же харнессом

Скриншоты в JetBrains Marketplace — это кадры харнесса, а не отдельные макеты. Как устроено:

- **Что на кадре** — сценарии категории «Frames for the listing» в
  `webview/src/harness/scenarios/showcase.ts`. Каждый — один чекпоинт, оставляющий панель в готовом,
  «фотогеничном» состоянии; сквозь все кадры идёт один выдуманный проект (`nimbus-checkout`, ветка с
  PR), чтобы набор читался как один рабочий день. Правишь содержимое кадра — правишь этот файл.
- **Как снимается** — `?shot=<id>` в харнессе (`harness.tsx`) убирает свою обвязку и отдаёт панели всё
  окно, а `window.__accShotReady` говорит камере, что лента уже собрана. Сама камера —
  `scripts/screenshots.mjs`, инструкция по запуску в его шапке; Playwright намеренно не в зависимостях
  репозитория.
- Размер кадра — 1200×800 CSS при dpr 2, то есть PNG 2400×1600 (маркетплейс просит от 1200×760 и
  одинаковых пропорций у всех картинок).

## Запуск тестового WebStorm с уже открытым плагином

Когда прошу «подними песочницу», «запусти тестовый WebStorm», «глянь
живьём в IDE» — это про **реальный плагин в реальной IDE** (не про
харнесс из браузера, это разные способы проверки).

Команда:

```
./scripts/sandbox.sh
```

Что она делает:
- Гасит предыдущий запущенный экземпляр песочницы, если он ещё открыт
  (иначе каждый перезапуск плодил бы новое окно поверх старого).
- Собирает плагин и поднимает **отдельную, отдельно настроенную копию
  WebStorm** с этим плагином — не трогает мою основную рабочую IDE.
- Сразу открывает в ней `sandbox-project/` и саму панель плагина —
  ничего искать в интерфейсе не нужно.
- Лог сборки/запуска — в `build/sandbox.log`, если что-то пошло не так.

Запускается это долго (сборка + старт целой IDE), поэтому не глушить
процесс раньше времени и не считать зависшим — просто подождать. Закрыть
можно в любой момент обычным закрытием окна тестовой IDE.

Если нужно проверять правки в webview без пересборки плагина на каждый
чих — можно поднять `pnpm dev` в `webview/` и передать его адрес
песочнице:

```
./gradlew runIde -PopenProject=sandbox-project -PwebviewDevUrl=http://localhost:5173/
```

Тогда панель внутри тестовой IDE грузит интерфейс прямо с dev-сервера, и
правки в `webview/src/` видны сразу после сохранения, без пересборки
плагина целиком.

## Удалённый доступ: три части одного кода

Фича «ответить агенту с телефона» живёт в трёх местах, и они намеренно делят один код, а не
повторяют друг друга:

- **`src/main/kotlin/.../claude/`** — ядро сессий. `ClaudeSessionHub` (сервис уровня проекта)
  владеет разговорами, ведёт журнал событий с порядковыми номерами и рассылает их подписчикам.
  Панель — один из подписчиков, телефон — другой. Разговоры переживают закрытие панели и умирают
  вместе со вкладкой чата.
- **`src/main/kotlin/.../remote/`** — сетевой агент, конверты, криптография, привязка устройств.
- **`relay/`** — маленький сервер (Node + TypeScript), который сводит IDE и телефон. Отдельный пакет
  workspace под Apache-2.0 (у плагина Elastic-2.0, и хостить его чужими руками она запрещает —
  подробности в `relay/README.md`). Лежит здесь до выделения в свой репозиторий, но самодостаточен:
  общего кода с панелью нет, вынос — это `git subtree split`, а не распутывание.
- **`webview/src/mobile/`** — клиент для телефона. **Третья точка входа** рядом с панелью и
  харнессом.

Главное правило то же, что и про харнесс: **мобильный клиент — не копия интерфейса**. Он рендерит
те же карточки ленты и гоняет тот же `feed/` — правка в общем исходнике чинит оба экрана сразу.
Если правишь ленту, правь `webview/src/feed/` и `webview/src/components/items/`, а не мобильную
обёртку. Отличается только плотность, и она переключается токенами (`[data-acc-density='touch']`
в `tokens.css`), а не вторым набором стилей.

Что легко сломать, не заметив:

- **Перечень разрешённого с телефона** (`remote/RemoteCommands.kt`). Добавил сообщение в
  `webview/src/protocol.ts` — `RemoteCommandsTest` упадёт, пока не решишь про него явно. Так и
  задумано: канал к агенту эквивалентен запуску команд на рабочей машине.
- **Проектные факты телефону пересылаются по белому списку** (`RemoteFeed.projectFact`). Композер на
  телефоне рисуется из четырёх сообщений - `project`, `usage`, `commandHints`, `files`, - и они не
  относятся ни к какому разговору, поэтому обычное правило подписки их выбрасывало. Список именно
  разрешающий: `init` в него не входит и входить не должен - он несёт рабочий каталог, а путь наружу не
  уходит (см. ниже). Список файлов там же режется по бюджету: кадр релея ограничен 256 КБ, а
  переросший кадр не обрезается, а выбрасывается целиком.
- **Путь проекта наружу не уходит.** Открытый проект едет под `locationHash`, закрытый — под хэшем
  пути, а сам путь остаётся в `RemoteAgent.recents`. Он же и список того, что вообще можно открыть с
  телефона: ключ, который никому не отдавали, не открывает ничего, поэтому запрос не может назвать
  произвольный каталог.
- **Список на телефоне присылают, а не спрашивают.** `ClaudeSessionHub.onInventoryChanged` дёргается,
  когда меняется статус разговора, ожидание человека или набор вкладок; телефон опрашивает раз в 25
  секунд только чтобы доказать, что линия жива. Забыть про push — вернуть «плашка не показывает, что
  работа идёт», ради чего это и сделано.
- **Телефону отдаётся конец разговора, а не весь журнал.** Очередь наружу (`RemoteOutbox`) держит
  2000 кадров и 8 МБ, а журнал одной вкладки — ровно столько же: отдать журнал целиком значило
  переполнить очередь, а переполненная очередь выбрасывается вся, и длинный чат на телефоне открывался
  пустым. Бюджет живёт в `ClaudeSessionHub.CatchUp`, и в ту же сторону работают два правила рядом:
  строки проигрываемого транскрипта (`replay`) наружу не идут вовсе — по окончании телефону отдают
  готовый хвост; а сигнал «переспроси» после переполнения адресуется каждому устройству отдельно
  (`RemoteAgent.resyncFrames`), иначе о потере никто не узнает.
- **Разговор опознаётся парой «проект + id», а не одним id.** Первая вкладка каждого проекта у IDE
  называется `main`, поэтому поиск по одному `sessionId` находил чужую вкладку: на телефоне это был
  чужой заголовок и чужое имя проекта над открытым чатом. См. `chatKey` в `webview/src/mobile` и
  `RemoteFeed.wantedBy` на стороне плагина.
- **Ответ на запрос и лента ходят разными дорогами.** Лента — по подписке (`deliver`), ответ на
  вопрос устройства (список прошлых разговоров) — через `SessionClient.answer`: он не относится ни к
  какому разговору, и по правилам подписки ему просто некуда идти.
- **Время на телефоне — чужое.** Всё, что лента отмеряет (начало хода, старт вызова, пауза перед
  повтором запроса), проставлено часами машины с IDE: телефон применяет журнал, подставляя в редьюсер
  метку `at` вместо своего «сейчас». Считать разницу против `Date.now()` телефона — вычитать одни часы
  из других, и при спешащей IDE счётчик «Claude is thinking» начинал ход с минуса. Поправка живёт в
  `webview/src/mobile/clock.ts` и раздаётся вниз контекстом `hooks/useNow`; калибруется по `at` в
  инвентаре (`RemoteAgent.inventoryBody`) — журнальные метки для этого не годятся, они говорят «когда
  случилось», а не «сколько сейчас». Пишешь на телефоне что-то, что вычитает время, — бери `useNow`,
  а не `Date.now`.
- **Очередь сообщений живёт в IDE, а не в окне** (`claude/SessionQueue.kt`). Раньше это было состояние
  React внутри экрана - своё у панели и второе у телефона. На столе это почти работает, на телефоне нет:
  страницу в кармане браузер выгружает без предупреждения, и сообщение пропадало - не отправлено и нигде
  не ждёт. Теперь список держит хаб, отдаёт его целиком сообщением `queue` (живьём, **не в журнал** -
  это то, что разговор скажет, а не то, что сказал; плюс копия в `attach` для подключившегося) и
  запускает первое из очереди в `sendStatus`, когда ход закончился. Та же единственная проверка «идёт
  ход» не пускает сообщение внутрь `/compact`: компакт - обычный ход, а написанное в идущий ход CLI
  чаще всего молча теряет (см. `PromptDelivery`). Порядок переставляется по идентификаторам, а не по
  индексам: на список смотрят два окна.
- **Тег проверяется раньше окна повторов, а не наоборот** (`DeviceSessions.open`, `link.ts`). Счётчик
  лежит в открытом заголовке, и тот, кто везёт кадр, волен его выдумать: сдвинутое до расшифровки окно
  выкидывало потом каждый настоящий кадр молча. По той же причине `open` отвечает тремя исходами, а не
  «тело или null» - повтор после реконнекта это нормальная работа релея, и просить из-за него новые
  ключи значит жечь ECDH на ровном месте.
- **Новые ключи ждут доказательства, а живые продолжают работать** (`DeviceSessions.offer`). Хендшейк
  идёт в открытую - он и существует, чтобы завести ключ, - поэтому «это я, я потерял ключи» может
  сказать кто угодно. Доказательство одно: кадр, запечатанный новыми ключами. Отсюда же ограничение на
  частоту рукопожатий с обеих сторон (`volume.allow("sessionInit")` в плагине, `handshakeBudget` на
  телефоне): у телефона его не было вовсе, и чужой `sessionStale` гонял его по ECDH сколько угодно.
- **Тип кадра - под тегом, и пуш запечатывается как пуш.** AAD собирается из фактического заголовка, а
  не из константы; `RemoteAgent.notify` зовёт `seal(..., type = TYPE_PUSH)`, релей отдаёт push-службе
  ВЕСЬ кадр, а не тело. До этого три половины пути не сходились: воркер на телефоне брал начало
  шифртекста за заголовок и не открывал ничего никогда.
- **Долгоживущий ключ телефона не хранится, а считается заново** (`longLivedAuth` в `core/crypto.ts`).
  Байты в IndexedDB - копия устройства, которую может унести всё, что выполнится на странице; статический
  ключ браузер использует, но наружу не отдаёт. Значения `salt`, метки и длины трогать нельзя: агент
  держит свою копию в keychain и второй раз её не выводит, так что расхождение - это тихо умершие
  спаренные телефоны.
- **`?relay=` работает только в dev-сборке.** Ссылку присылают, а этот параметр решает, с каким сервером
  говорит телефон.
- **У релея есть потолки, и они не декоративные:** `maxPayload` у сокета (иначе библиотека держит 100 МБ
  до того, как кто-то посмотрит на размер), потолок тела у `/v1/push/subscribe`, число сокетов на
  звонящего и общее, число подписок, TTL у заметок mailbox. Заметка о переполнении хранит КОПИЮ адреса:
  `parse` отдаёт виды в исходный буфер, и шестнадцать байт держали весь кадр целиком.
- **Подписка на пуши принимается только для адреса с живым сокетом**, а эндпоинт - только https и только
  хосты push-служб. Релей не может знать, кто с кем спарен, но кадр в чужую сторону он слать умеет: без
  этих двух проверок любой желающий заставлял его ходить POST'ом куда угодно и растить память.
- **Формат конверта** описан трижды: `remote/Frame.kt`, `relay/src/wire/frame.ts`,
  `webview/src/core/frame.ts`. Меняешь — меняй везде, иначе стороны перестают понимать друг друга.
- **Вывод ключей** (`remote/Hkdf.kt` и `webview/src/core/crypto.ts`) проверен против векторов
  RFC 5869. Это единственное, что гарантирует совпадение половин, — они не проверяются друг о друга.

### Проверить всю цепочку живьём

```
cd relay && pnpm build && PORT=8080 RELAY_STATIC_DIR="" node dist/index.js
./gradlew runIde -PopenProject=sandbox-project -PremoteRelay=ws://localhost:8080
cd webview && pnpm vite -c vite.mobile.config.ts   # телефонный клиент на :5174
```

Флаг `-PremoteRelay` включает удалённый доступ только для этого запуска песочницы — в обычной IDE
он выключен, пока человек не включит его сам.

Второй клиент без сети и криптографии (для отлова гонок двух клиентов):

```
./gradlew runIde -PopenProject=sandbox-project -PlocalBridge=true
```

Адрес с одноразовым токеном пишется в лог IDE.

### Релей уже развёрнут

Публичный релей живёт на своём сервере (OVH + Coolify, приложение `acc-relay`), адрес —
`wss://relay.mzpizote.com`. Это и есть значение по умолчанию в плагине, так что включённый в панели
удалённый доступ соединяется с ним без настройки. Railway больше не используется.

Кода релея в GitHub нет, поэтому автодеплоя у него тоже нет: исходники лежат на сервере в
`/root/apps/acc-relay`, образ собирается там же и кладётся в локальный реестр. Как выкатывать —
по шагам в `relay/README.md`; общие правила по серверу — в скилле `infra`.

Телефонный клиент раздаёт сам релей: он собирается из `webview/`, копируется в `relay/public/` и
уезжает вместе с образом. **`relay/public/` намеренно игнорируется в корневом `.gitignore`, а не в
`relay/.gitignore`** — выгрузка каталога наружу уважает ignore-файлы внутри него, и правило там
выкинуло бы клиента из образа. Как деплоить — по шагам в `relay/README.md`.

Телефон звонит на тот релей, откуда загрузили клиента, а не на адрес, записанный при паре
(`relayAddress` в `webview/src/mobile/link.ts`). Поэтому переезд релея не просит всех пересопрягаться
— только перезагрузить страницу.

Ключи VAPID для пушей лежат в переменных сервиса и в `secrets/relay-vapid.env` (каталог `secrets/`
в `.gitignore`). В чат их не выводить.

Иконки телефонного клиента генерируются из логотипа плагина: `python3 scripts/mobile-icons.py`.
Отдельно нарисованных копий нет — правится логотип, перегоняются иконки.

## Аргументы запуска обязаны пережить чужую оболочку

Плагин не всегда запускает CLI сам. На Windows npm ставит его батником (`claude.cmd`), платформа
исполняет батник через `cmd.exe /c`, а батник передаёт полученное дальше через `%*`. И то и другое
построчно: перевод строки внутри аргумента заканчивает команду на этом месте, и весь хвост командной
строки до настоящего CLI не доезжает — молча, без ошибки, потому что с точки зрения `cmd` всё в порядке.

Так и потерялся `--resume`: единственным многострочным аргументом был брифинг
(`ClaudeLaunch.PANEL_BRIEFING`), и он стоит в середине командной строки. Разговор, открытый из истории,
поднимался пустым — панель рисовала свой реплей, а агент за ним не помнил ничего и писал в собственный
транскрипт. На macOS это не воспроизводится вовсе, а на Windows пряталось за настройками человека:
потерянные `--model`, `--effort` и `--permission-mode` совпали с тем, что у него стояло в
`~/.claude/settings.json`.

Отсюда правило: **в аргументах запуска нет ни переводов строки, ни кавычек** (кавычка так же
закрывает для `cmd` закавыченный кусок). Держит это `ClaudeLaunchTest`, а не аккуратность:
многострочный текст пишется в исходнике абзацами и схлопывается в строку на выходе
(`ClaudeLaunch.oneLine`). Вторая страховка — в `ClaudeSession.rememberConversation`: если процесс
поднялся под другим id, чем просили продолжить, это пишется в `DiagnosticsLog` и уезжает в отчёт.

## Правки ходят в обе стороны: буферы на диск, диск в IDE

Агент читает файлы с диска и про открытый редактор ничего не знает. IDE записывает буферы, когда фокус
уходит из приложения, а переход из редактора в нашу панель приложение не меняет - поэтому обычное
«поправил строку, не сохранил, попросил Claude» кончалось тем, что агент работал по старому тексту, а его
правка выглядела как откат чужой работы. Теперь перед ходом панель сохраняет сама
(`editor/UnsavedEdits.kt`).

- **Место одно - `ClaudeSessionHub.prompt`.** Через него идут и панель, и телефон, и отложенная очередь,
  и ответ на вопрос агента, так что отдельных веток не нужно. Второй вызов - перед командой через «!»
  (`ProjectCatalog.runShellCommand`): она читает тот же диск, и `git diff` сразу после правки должен
  показать эту правку.
- **Сохраняются файлы только этого проекта** - под его корнем или в его контенте. «Все документы IDE»
  означало бы записать чужое окно с другим проектом, которого агент всё равно не видит.
- **Ожидание ограничено двумя секундами.** Ждёт тот поток, который принёс сообщение, а для телефона это
  поток релея: модальный диалог в IDE держал бы его сколько угодно, и вместе с ним - все остальные
  разговоры на линии. Ход, начатый на секунду раньше, - это один файл, прочитанный по-старому; линия,
  не вернувшаяся никогда, - это удалённый доступ до похода к машине.
- **В диагностический буфер уходит только число сохранённого.** Имён файлов там быть не может - буфер
  уезжает наружу с отчётом (см. `DiagnosticsLog`).

### Обратная сторона: файлы перечитываются после правок агента

IDE держит свою картину диска и обновляет её, когда фокус возвращается в приложение или когда до
изменения доберётся её наблюдатель за файлами. Человек, отвечающий агенту из панели, приложение не
покидает, а наблюдатель настолько надёжен, насколько надёжна файловая система под проектом - сетевой
диск, симлинк, сотня файлов за ход, и он опаздывает или молчит. На экране в этот момент старый текст.
Поэтому поток агента читается второй раз - на предмет «что перечитать» (`editor/AgentEdits.kt`,
`editor/DiskRefresh.kt`).

- **Считается результат инструмента, а не намерение.** Между «агент просит Edit» и «файл изменился»
  стоит человек с разрешением: перечитать по запросу - значит перечитать до правки, а после самой
  правки уже никто не попросит.
- **Команда через оболочку файлов не называет** (`git checkout`, форматтер, свой скрипт), поэтому после
  неё и в конце хода IDE просят оглядеться целиком - тем же способом, что при возврате фокуса. Не чаще
  раза в две секунды, и не выбрасывая последний запрос, а откладывая: самый важный - последний, после
  конца хода уже ничего не спросит. Упавшая команда считается тоже: половина скрипта - это ровно тот
  случай, когда диск разошёлся с картиной IDE.
- **Перечитывается только то, что IDE и так знает.** Незнакомый файл - это файл, который она никому не
  показывает; тащить его в свою картину мира потому, что агент что-то читал в `/tmp`, незачем. Новый
  файл - другое дело: его находит пересчёт детей в знакомой папке.
- **Пачками, но без сдвига срока.** Правки идут очередями, каждый обход диска стоит денег, а пачка,
  которую отодвигает каждый новый файл, ушла бы в конец хода.

## Android Studio: на версию позади и без встроенного браузера

Нижняя граница совместимости — 261 (2026.1), и стоит она там ради Android Studio: её стабильный канал
(Quail) — это сборка 261, а IDE, до которой плагин не дотягивается по номеру, не показывает его в своём
маркетплейсе вовсе. Пока граница была 262, для Android Studio плагина просто не существовало.

Двигать её ещё ниже не надо. 253 — это две версии дрейфа API и отдельная большая проверка, а текущая
стабильная Android Studio уже здесь и обновляется сама.

Ломалось два места, и оба стоит помнить:

- **Интерфейс обработчика ресурсов у JCEF разной формы в разных IDE.** С 2026.2 он требует семь методов
  (`open`, `read`, `skip` сверх старых четырёх), а типов из их сигнатур — двух колбэков и `LongRef` — в
  2026.1 нет ни одного. Класс, называющий отсутствующий тип в своей сигнатуре, там не грузится: верификатор
  зовёт это NoSuchClassError, и панель не поднимается совсем. Назвать только старые четыре тоже нельзя —
  против 2026.2 такой класс недоделан и не компилируется. Поэтому обработчик собирается через
  `java.lang.reflect.Proxy` по тому интерфейсу, который есть в запущенной IDE (`WebviewResources`), и
  разбирается по именам методов. Один архив подходит обеим формам, а следующее изменение этого интерфейса
  не надо будет предугадывать. `LongRef` заполняется по имени метода, а не через тип — назвать тип и значит
  сломать всё заново.
- **В Android Studio нет встроенного браузера.** Java-обвязка JCEF в ней лежит (`intellij.libraries.jcef.jar`),
  а нативной части — `libjcef.dylib`, Chromium, вспомогательных процессов — нет нигде в бандле, поэтому
  `JBCefApp.isSupported()` отвечает «нет», и панель показывала свою заглушку «в этой IDE нет браузера».
  Лечится не нами: JetBrains публикуют браузер обычным плагином маркетплейса (`com.intellij.modules.jcef`,
  сборки под 261 и 262, с нативом внутри). Поэтому зависимость в `plugin.xml` **обязательная, а не
  необязательная**: обязательная заставляет IDE поставить браузер вместе с нами, необязательная поставилась
  бы молча и оставила мёртвую панель.

  Это касается только Android Studio: обычные JetBrains-IDE на 261 браузер находят у себя (верификатор
  против WebStorm 2026.1 не жалуется вовсе), так что предложение доставить его увидит именно её
  пользователь. Это и есть рекомендация самих JetBrains: объявлять эту зависимость можно начиная с
  2025.3.1, а с 2026.2 браузер встроен везде.

Что легко сломать, не заметив:

- **Верификатор всегда будет писать «missing mandatory dependency» против Android Studio.** Он ищет
  браузер среди встроенных плагинов целевой IDE и сдаётся; настоящая IDE спрашивает у маркетплейса и
  получает ответ (проверено тем же resolver'ом, которым пользуется сама Android Studio). Поэтому
  `MISSING_DEPENDENCIES` убран из `failureLevel` — иначе задача падала бы на ней вечно, ровно из-за того,
  что и позволяет там работать. Против WebStorm 2026.1 и 2026.2 вердикт чистый, «Compatible».
- **`EXPERIMENTAL_API_USAGES` тоже убран, и ровно из-за одного вызова** — взятия write-intent-блокировки
  перед сохранением редакторов (`UnsavedEdits`). В 261 весь этот механизм помечен экспериментальным, замены
  нет, а без блокировки сохранение документов падает.
- **Проверять надо против самой Android Studio, а не против «рекомендованного набора».** Её там нет и не
  будет: Google собирает её из своей ветки и публикует не там, где верификатор ищет IDE. Поэтому в
  `pluginVerification` она названа явно — самым ранним стабильным Quail (2026.1.1.8): что ломается, ломается
  против самой ранней сборки, которую мы обещаем.

Проверить живьём:

```
./gradlew runInstalledIde -PideHome="/Users/max/Applications/Android Studio.app" \
  -PidePlugins=build/extra-plugins/jcef-plugin-261.zip -PopenProject=sandbox-project
```

`-PideHome` запускает уже установленную на машине IDE с этой сборкой плагина (обычная песочница поднимает
ту, против которой собирались, — то есть ровно ту, где ничего не может сломаться). `-PidePlugins` кладёт
рядом распакованные или запакованные плагины: браузер в 261 надо поставить, а не предполагать, и положить
его в песочницу руками нельзя — подготовка песочницы вычищает всё, чего не клала сама. Архив браузера
берётся с маркетплейса (плагин 31360, сборка под 261 и вашу платформу).

Быстрая проверка совместимости без скачивания гигабайтов:
`./gradlew verifyPlugin -PverifyIde="/Users/max/Applications/Android Studio.app"`.

## Пока собирается иероглиф, клавиатура не наша

Поле ввода отбирает у браузера клавиши: Enter отправляет, Tab и стрелки ходят по подсказке, стрелки вверх
и вниз листают историю, Escape останавливает ход, цифры отвечают на разрешение. Ровно эти же клавиши
принадлежат методу ввода, пока он собирает символ: Enter подтверждает кандидата, Tab и стрелки ходят по
списку кандидатов, цифры выбирают из него, Escape выбрасывает недописанный символ. Отобранная у него
клавиша - это чип файла посреди корейского слова и остановленный ход в ответ на «нет, не этот иероглиф».

- **Признак берётся с события, а не из своей памяти** (`isComposing` у клавиши, `isComposingEvent` у
  правки поля). Композиция, оборванная уходом фокуса, не присылает события конца: запомненное «идёт набор»
  осталось бы поднятым навсегда - поле, которое больше не отправляет, и Escape, который больше не
  останавливает, без единого способа это вылечить, кроме перезагрузки панели.
- **Правило действует и поверх панели, а не только в поле** (`App`, `AskPanel`, `useDigitHotkey`).
  Escape поле гасит у себя (`stopPropagation`), а Shift+Tab до него не доходит вовсе - там окно-обработчик
  единственная защита. Карточку вопроса и цифровые хоткеи сегодня держит ещё и «в поле есть черновик», но
  это тонкая нитка: она рвётся, стоит перестать докладывать наружу недописанные символы.
- **Пока символ не дописан, поле не перестраивается** - ни зачистка опустевшего поля, ни превращение
  команды в чип. Браузер держит недописанный символ в собственном узле, и подмена узла вырывает символ из
  рук вместе с окном кандидатов. **Но наружу состояние докладывается как обычно**: именно по нему соседи
  понимают, что клавиша занята.
- **Конец композиции доделывает отложенное сам** (`handleCompositionEnd`), потому что обычного события
  правки после него не будет: Chromium присылает последнее ещё ВНУТРИ композиции и закрывает её молча.
  Синхронно, а не отложенно: человек подтверждает кандидата первым Enter и отправляет вторым, и отложенный
  проход встретил бы второй Enter с черновиком, который панель ещё считает пустым.
- **Это не только про азиатские языки.** Удержание буквы на маке и мёртвые клавиши европейских раскладок
  открывают меню акцентов тем же механизмом - там цифрами выбирают букву.
- Проверить: `scripts/composer-input.mjs` (инструкция в шапке файла). Половина прогона - обычный набор без
  всякого метода ввода: отправка, перенос строки, история, отмена, подсказка, чипы, Escape и цифры должны
  вести себя ровно как раньше.

## Поле ввода не уезжает от строки, в которой пишут

Поле ограничено по высоте и прокручивается внутри себя, а браузер не всегда сам показывает каретку -
поэтому после каждой правки панель подводит поле к строке с кареткой (`scrollCaretIntoView` в
`composerDom.ts`). Дальше начинается то, что ломается молча.

- **Каретка не всегда умеет себя измерить.** Стоя на ПУСТОЙ строке, Chromium не отдаёт для неё ни одного
  прямоугольника (проверено живьём в панели), и то же самое бывает на границе между узлами. Раньше пустой
  прямоугольник читался как «значит, каретка в самом конце» - верно для пустой последней строки и неверно
  для любой пустой строки в середине. А сообщение, написанное списком, из пустых строк наполовину и
  состоит: перенос строки в середине такой простыни бросал поле в её конец, и следующая нажатая клавиша
  бросала снова.
- **Строка меряется соседним символом**, а не догадкой: он лежит ровно на той строке, которая нужна.
  Сначала символ после каретки, потом перед - на конце перенесённой по ширине строки это две разные
  строки, и пишут в ту, что впереди.
- **Не измерилось совсем - поле не трогают.** Каретка, которую не удалось найти, не говорит о том, где
  она; догадка о её месте стоит человеку места, в котором он писал.
- **Сколько прокрутить - отдельное правило с тестом** (`caretScrollShift`, `composerDom.test.ts`): вниз с
  запасом, вверх - с поправкой на непрозрачную полоску, которая закрывает первые пиксели поля. Строка под
  ней не видна, значит она не на экране.
- Проверить без IDE: харнесс, любой сценарий с лентой - набрать в поле список с пустыми строками между
  пунктами, прокрутить поле вверх, поставить каретку в середину и перенести строку. Поле обязано остаться
  на месте. Обратная проверка - каретка в самом конце, поле прокручено вверх: перенос строки обязан
  показать новую строку.

## Настройки живут за одной кнопкой, а не в корне меню

Корень бокового меню - семь строк в трёх группах: «этот проект» (история, статистика, MCP, плагины),
«устройства» (удалённый доступ) и «сам плагин» (настройки, обратная связь). Звуки, режим по умолчанию,
раскладка поля ввода, поведение вставки, улучшение промпта, голос и язык стоят за строкой «Settings»: все
они - одно и то же (предпочтение, выставленное один раз), и список, который начинается с просьбы
прочитать десять пунктов, никто не читает.

- `parentOf` в `SideMenu.tsx` водит шаг назад с этих экранов не в корень, а в настройки - Escape и
  стрелка «назад» обязаны совпадать с тем, откуда пришли. Список экранов один - `SETTINGS_SCREENS`.
- Сам экран настроек (`SettingsScreen`) переиспользует ту же строку `Row`, что и корень, вместе со
  значениями справа: «7 on», «Auto», «Custom». Второй раскладки для этих строк нет.
- «Settings» стоит в группе «сам плагин» рядом с «обратной связью», потому что обе про плагин, а не про
  работу в нём.
- **Удалённый доступ - такая же строка, как остальные, а не карточка.** Раньше это была плашка с рамкой,
  бейджем и целым предложением про состояние - три строки высотой в списке, где каждая вторая запись
  укладывается в одну. Предложение живёт на экране за строкой, где под него есть место; наверху остаётся
  само состояние, и стоит оно справа - там же, где у соседей счётчики. Поэтому `RemoteSummary` несёт
  только слово и тон, без `hint`.
- **Цвет иконки у этой строки не прибит, в отличие от всех остальных** (`TONE_ICON` в `SideMenu.tsx`).
  Тинт был у карточки, и потерять его целиком значило бы получить строку, которая молчит, пока её не
  прочитают: зелёный квадратик против серого отвечает «включено ли» через всю панель.
- **Точка у значения красится из компонента, а не из CSS** (`ValueTone`, `.rowValueDot`). Таких значений
  два: MCP, когда подняты все серверы, и удалённый доступ всегда - у него значение и есть состояние.
- **Подпись и заголовок строки - всегда одна строка с многоточием.** «Relay unreachable» шире прочих
  значений и сталкивало описание на второй ряд: список, где одна строка выше остальных, читается как
  сломанная - ровно в том состоянии, ради которого в него и смотрят. То же самое делала с «History» узкая
  панель. Правило то же, что у подсказки в шапке меню, и по той же причине.

## Реклама в панели: две карточки, обе в конце своего экрана

Под группой «сам плагин», между ней и версией, живёт карточка «FROM THE AUTHOR»: другой продукт автора
(Snakein) с картинкой, подписью и одним выходом - в браузер (`SideMenu.tsx` плюс блок `menu.author` в
словарях). Вторая стоит в самом низу экрана голосового ввода и зовёт в notastream - диктовку в любое окно
машины (`VoiceInput.tsx` плюс блок `voice.promo`). Разметка у них одна на двоих - `AuthorCard.tsx`.

- **Она нарочно не похожа на строку меню.** Любая строка выше ведёт куда-то внутрь панели, и реклама в
  той же одежде, что «История», - это реклама, притворяющаяся частью плагина. Поэтому карточка, а не
  `Row`: свои классы (`author*` в `sideMenu.module.css`), своя рамка, кнопка со скриншотом внутри.
- **Место - последнее и после всего.** Меню открывают ради истории, MCP и настроек; всё это стоит выше,
  и до карточки долистывают уже те, кому нечего больше делать в меню. У второй карточки то же правило и
  свой довод: дочитавший экран диктовки до конца уже решил, что говорить лучше, чем печатать.
- **Карточка одна, а мест два** (`AuthorCard`). Вторая копия этой разметки разошлась бы с первой на первой
  же правке любой из них; сердечко в конце текста - проп, потому что просьба о поддержке есть только у
  первой.
- **Наружу ведёт `openExternal`, а не `<a href>`.** У страницы нет своего браузера, адрес отдаётся
  оболочке (`onOpenLink` в пропах, `openLink` в `App`) - той же дорогой, что ссылка на PR. В харнессе это
  `window.open` у плеера, так что нажатие проверяется без IDE.
- **К адресу пришиты utm-метки, и `utm_campaign` у карточек разный** (`side-menu` и `voice-input`).
  Реклама в панели - это вопрос «стоит ли она места», а у вопроса должен быть ответ по каждому месту
  отдельно; umami на стороне сайта их читает.
- **Имена продуктов не переводятся и в словарях их нет** (`AUTHOR_PRODUCT` в `SideMenu.tsx`,
  `DICTATION_PRODUCT` в `VoiceInput.tsx`). Имя одинаково на
  всех десяти языках, и лежащее в словаре оно потребовало бы исключения в `SHARED_WITH_ENGLISH` на девять
  языков вместо константы в одну строку. Заголовок, текст и подпись под именем переводятся как обычно.
- **Картинка снята под тот размер, в котором её показывают.** Панель шириной `min(350px, 100%)` даёт
  картинке 303 CSS-пикселя, файл - 608 пикселей шириной, то есть ровно 2x. Формат webp (`-q 94 -m 6
  -sharp_yuv -f 80 -sns 100`, 11.5 КБ): у этого баннера тёмный градиент во весь кадр, и обычный q90 сыпал
  на нём блоками. Меняешь картинку - пересчитай под ту же ширину, а не клади исходник с сайта: 660×198
  RGBA из макета весит 81 КБ, то есть в семь раз больше при том же экране. Второй баннер снят с самого
  сайта (кадр 1216×364 из шапки, уменьшенный вдвое) и сжат теми же ключами - 12.4 КБ.
- **Высота у карточки фиксированная (88px, `object-fit: cover`).** Баннер широкий, и оставленный со своими
  пропорциями он забирал бы треть последнего экрана меню под рекламу.
- Проверить без IDE: харнесс, любой сценарий с лентой - меню за бургером, карточка в самом низу; вторая -
  «Settings» → «Voice input», тоже в самом низу. Языки - `?lang=` в адресе; в узкой панели (меньше 350)
  подпись под именем схлопывается многоточием, и так и надо.

## Кнопка «улучшить промпт»: отдельный запуск, а не ход в разговоре

Звёздочка слева от скрепки переписывает черновик в поле ввода. Живёт в трёх местах:
`webview/src/feed/improve.ts` (капсулы ↔ текст), `Composer`/`App` (кнопка, состояние, отмена),
`claude/PromptImprover.kt` (сам запуск).

- **Переписывает отдельный `claude -p`, а не текущий разговор.** Ход в разговоре попал бы в его
  транскрипт как чужой вопрос, и считала бы его та модель и тот effort, что стоят у вкладки: переписать
  строчку на Opus с максимальным усилием дороже и дольше, чем её отправить. Отдельный запуск заодно не
  требует своего API-ключа - это тот же вход, через который работает панель.
- **Запуск нарочно голый, и каждый флаг зачем-то нужен.** `--tools ""` - без инструментов (иначе это
  агент: полезет читать файлы, спросит разрешение, которое некому дать, и встанет до таймаута).
  `--safe-mode` - без CLAUDE.md, хуков, скиллов и стилей: «всегда отвечай по-русски» в личном CLAUDE.md
  превращало английский черновик в русский промпт. `--strict-mcp-config` без своего конфига - без MCP-серверов: их
  описания инструментов и есть основная цена такого запуска (замерено на этой машине: 70k токенов против
  500 на само дело). `--no-session-persistence` - переписывание не разговор, и в `/resume` ему нечего
  делать.
- **Обещание про язык держит не `--safe-mode`, а фраза в системном промпте.** `language` в
  `~/.claude/settings.json` - настройка, а не кастомизация, поэтому safe-mode её оставляет, и CLI
  превращает её в системное «всегда отвечай по-русски»: с этой настройкой английский черновик
  возвращался русским промптом три раза из трёх - ровно та жалоба, что есть у конкурента. Снять её можно
  было и грубо (`--setting-sources` без источников), но в том же файле живут `apiKeyHelper` и ключ, и
  кнопка, ломающая человеку вход ради его языка, меняет одну поломку на большую. Поэтому настройке
  отвечают, а не выбрасывают её: этот запуск никому не отвечает, значит правило про язык ответов к нему
  не относится, а какой язык нужен - решают инструкции, которые человек волен переписать.
- **Модель - Opus на низком усилии, запасная Sonnet.** Замерено на одних и тех же черновиках: Haiku
  отпадает по всем статьям сразу - 28 секунд на низком усилии и 49 на среднем, потому что тратит три-пять
  тысяч токенов размышлений на переписывание одной фразы, и выходит дороже всех. Sonnet отвечает за две
  секунды и обычно прав, но именно он подхалтуривает: выписал путь к файлу рядом с маркером, который этот
  файл и обозначает, и повторился внутри двух предложений. Opus отвечает за три и не делает ни того, ни
  другого. Усилие выше низкого не покупает ничего: на Sonnet ответ не меняется вовсе, на Opus включается
  размышление (шесть секунд) и начинают появляться требования, которых в черновике не было, - ровно то,
  чему инструкции больше всего сопротивляются. Запасная модель нужна потому, что сильная кончается первой:
  окно лимита, потраченное на разговор, не должно уносить с собой кнопку.
- **Повторное нажатие переписывает исходник заново, а не свой же ответ** (`App.improveSources`). Переписывать
  переписанное - значит плыть: каждый проход добавляет своего, и к третьему сообщение уже про другое. Поэтому
  второе нажатие - это ещё одна попытка над тем же исходником, ровно то, что человек имеет в виду, нажимая
  кнопку второй раз. Исходник забывается, как только к полю притронулись руками: отредактированный результат
  снова стал собственным черновиком, и лезть за него - выбросить эту правку. Отличить свою запись в поле от
  человеческой помогает флажок на время самой записи: поле рапортует наружу и то, и другое одинаково. Видно
  это в тултипе - он меняется на «Another take, from what you wrote», пока в поле лежит нетронутый ответ.
- **Назад к своим словам ведёт видимая кнопка над полем, а не Cmd+Z** (`App.restoreDraft`, `improveBack`
  в `composer.module.css`). Именно кнопка, а не плашка с фразой и кнопкой внутри: новости здесь нет, есть
  только то, что можно нажать, - а плашку читают как сообщение и ищут в ней действие. Плашка осталась там,
  где она честна: у провалившегося переписывания, где сначала предложение, а возврат - в конце его. Отмена в поле работала и раньше, но её не видно, а главное - она не про то:
  история отмен обнуляется на смене вкладки (ушёл в соседний чат и вернулся - возвращать уже нечем), а после
  трёх нажатий шагает по вариантам по одному, тогда как человеку нужен свой исходник. Поэтому исходник
  держит панель (`before` в `ImproveSource`) и переносит его из нажатия в нажатие ровно так же, как сам
  запрос: возврат ведёт к написанному руками, сколько бы вариантов между ним и полем ни стояло. Само
  нажатие идёт через композер, то есть остаётся шагом истории отмен - отвергнутый вариант в одном Cmd+Z,
  ничего не выбрасывается насовсем.
- **Возврат живёт ровно столько, сколько правило про повторное нажатие**: тронул поле руками - уходит и он,
  и память об отвергнутых вариантах (`onTokensChange`). Предлагать возврат поверх собственной правки значило
  бы обещать её выбросить. А сам возврат отвергнутое, наоборот, помнит (`improveTakenBack`): забрать свои
  слова обратно - самый ясный способ сказать «не то», и следующее нажатие обязано унести это с собой.
- **Поле говорит, ОТКУДА пришла правка, и три источника не равны** (`DraftEdit` в `feed/types.ts`). Рукой -
  человек ушёл от написанного, цепочка кончается. Шаг по собственной истории поля (Cmd+Z над вариантом) -
  наоборот, возвращение к написанному: цепочка стоит, меняется только «что сейчас на экране»
  (`improveShown`). Перенумерация подписей у картинок вообще не правка - её не считают ни за то, ни за
  другое, и она же двигает метку летящего запроса, иначе пришедший ответ отвергается как «черновик
  изменился». Раньше все три приходили одинаково, и Cmd+Z по привычке молча стирал память об отвергнутых
  вариантах: следующее нажатие переписывало ответ модели как свой черновик - ровно то, чему цепочка и
  мешает.
- **Всё, что кладёт токены в черновик мимо поля, обязано закрыть цепочку само** (цитата из ленты -
  `onQuote`). Поле о такой правке не узнаёт, а возврат остаётся на экране и уносит с собой только что
  добавленную цитату.
- **Ошибка и возврат делят одну строку над полем.** Второе нажатие может провалиться, пока в поле стоит
  первый вариант, - тогда верно и то, и другое сразу, а две плашки над полем в низкой панели дороже одной.
  Без ошибки строка сжимается по ширине слов: полоса во всю панель в форме предупреждения, сообщающая, что
  всё хорошо, читалась бы как «что-то сломалось» - каждое нажатие.
- **Правила цепочки лежат в `feed/improve.ts` (`ImproveSource`), а не в `App`**, потому что ломаются молча:
  и «переписываем исходник, а не свой ответ», и «возврат ведёт к исходнику» видно на экране только тогда,
  когда уже неправильно. Обе держит тест.
- **Отвергнутые варианты едут вместе с запросом** (`rejected` в `protocol.ts`, «TURNED DOWN» в
  `PromptImprover.body`). Нажатие поверх ответа - это и есть «не то», и молча выбрасывать это значит бросать
  те же кости против тех же слов: второй ответ выходил почти тем же предложением, и кнопка выглядела
  сломанной. Теперь модели показывают всё, мимо чего человек прошёл, и просят зайти с другой стороны -
  проверено живьём, три нажатия дают три по-настоящему разных формулировки. Хранится не больше четырёх
  последних: чем старше попытка, тем меньше она говорит о том, чего хотят сейчас. Блок стоит ПОСЛЕ инструкций
  и собирается плагином, а не входит в редактируемый текст: это факт про конкретное нажатие, а не правило
  переписывания, и он обязан работать и с чужими инструкциями.
- **Ни один символ написанного человеком не едет аргументом** - всё уходит в stdin (`ClaudeCli.feed`).
  Причина та же, что у `--resume` выше: перевод строки или кавычка обрывают команду на Windows. Поэтому
  и инструкции, которые человек волен переписать, идут в stdin, а аргументом (`--system-prompt`) едет
  только неизменяемая однострочная рамка без кавычек.
- **Капсулы не теряются, потому что уезжают маркерами.** Каждый чип заменяется на `[[1]]`, `[[2]]`, рядом
  едет строчка «что это такое», и ответ разбирается обратно по тому же списку. Маркер можно двигать по
  тексту - ради этого кнопку и жмут, - но не через другой маркер и не терять: порядок вложений тот, в
  котором их положил человек («сначала было, потом стало»), и он часть смысла, а чего в ответе не оказалось,
  дописывается чипом в конец сообщения. Картинка называется своей подписью с экрана («Image #6»), а не
  словами «изображение из буфера»: два скриншота подряд - обычное дело для этой кнопки, а различает их
  только подпись, потому что сами байты наружу не едут. Повторённый маркер срабатывает один раз (второй копии картинки не бывает), выдуманный номер
  вычёркивается. Слэш-команда в начале не переписывается вовсе: она говорит, куда идёт сообщение, и
  возвращается на своё место как была.
- **Результат кладётся в поле через сам композер** (`Composer.registerApply`), а не в черновик панели:
  только так он становится шагом истории отмен, и Cmd+Z возвращает собственные слова. Если за те
  секунды, что шёл ответ, черновик изменился (сообщение ушло, дописали руками), ответ выбрасывается с
  объяснением над полем: вернуть отправленное сообщение в опустевшее поле хуже, чем не сделать ничего.
- **Инструкции живут в настройках IDE** (`ClaudePreferences.improveInstructions`), пустые значат
  встроенный текст. На экране встроенный текст стоит плейсхолдером, а не значением: сохранённый
  значением, он стал бы копией, и следующая его правка в плагине не доехала бы ни до кого, кто однажды
  открывал этот экран.
- **Телефону это пока запрещено** (`RemoteCommands`): кнопки там нет, а дверь открывают, когда в неё есть
  чему пройти. По сути дверь узкая - запуск без инструментов, без разговора и без записи на диск.
- **Поле пересобирается ещё и на смену раскладки** (`Composer.fillField`). Каждая раскладка рисует поле в
  своей разметке, поэтому переключение отдаёт совершенно новый пустой contentEditable, а обычный эффект
  смотрит на неизменившиеся токены и оставляет его пустым. Потеряно при этом ничего не было - Send
  отправлял написанное, - чем и было хуже потери: черновик пропадал с экрана, его нельзя было ни прочитать,
  ни поправить, и он возвращался только тем, что его отправляли вслепую. Сторожит не «раскладка
  изменилась», а «под какую раскладку поле собрано»: на первом рендере поле уже наполнил обычный эффект, и
  второй проход поставил бы каретку в панель, по которой ещё никто не щёлкал.
- **Пока идёт переписывание, звёздочки мигают по очереди, а не крутятся** (`acc-sparkle-twinkle`). Кручение
  было первой попыткой и было неверным дважды: четырёхлучевая звезда, вращающаяся вокруг своего центра,
  читается как плохо нарисованный спиннер, а маленькая при этом моталась вокруг большой и всё качалось.
  Мигание - это то, что звёздочка делает по своей природе: каждая в свой черёд разгорается и подрастает,
  иконка не сходит с места, и на четырнадцати пикселях это единственное различимое движение. Масштабируется
  каждая вокруг СВОЕГО центра - за это отвечает `transform-box: fill-box`, без него обе раздувались бы в
  сторону левого верхнего угла кадра.
- Проверить без IDE: харнесс - звёздочка есть в любом сценарии с лентой, ответ выдумывает плеер
  (`player.ts`), маркеры в нём нарочно переставляются, каждое следующее нажатие даёт другой зачин (плеер
  считает присланные отвергнутые варианты), а каждый третий запуск падает, чтобы полоска с ошибкой тоже
  была видна. Возврат смотреть там же: нажать дважды подряд и вернуться - в поле обязан оказаться свой
  первый черновик, а не первый вариант.

## Слэш-команды панель находит сама, до первого сообщения

Список в подсказке поля - это два источника: имена, которые агент называет в `system:init` (то есть уже
после отправки первого сообщения), и файлы, которые панель читает с диска сама
(`ClaudeCommandHints.scan`). Второй источник существует именно ради первых минут: человек, только что
поставивший плагин, набирает «/» и обязан увидеть команды своего проекта.

- **Файл без frontmatter - это команда.** CLI запускает такой файл как есть (проверено живьём), а скан
  раньше выбрасывал его целиком - вместе с именем, ради которого подсказка и нужна. Теперь отсутствие
  описания даёт пустую подсказку, а не отказ.
- **Подпапка - часть имени, а не тайник.** `.claude/commands/demo/deep/twice.md` CLI зовёт
  `/demo:deep:twice`, по двоеточию на уровень (проверено по `slash_commands` живого агента, а не по
  документации). Обход рекурсивный, с потолком глубины - от закольцованного симлинка.
- **Диск читается независимо от плагинов.** Список установленных плагинов - отдельный запуск `claude`,
  который может не подняться или не уложиться в срок, и раньше одна такая осечка уносила с собой команды
  самого проекта: подсказка молчала до первого `system:init`. Теперь `refreshCommandHints` шлёт результат
  дважды - сперва диск, потом его же с плагинами.
- **Первое найденное имя выигрывает**, и порядок скана - это порядок старшинства у CLI: проект, потом
  личные команды, потом плагины.

## Панель говорит на десяти языках

Английский, 简体中文, Русский, Українська, Español, Português (Brasil), Deutsch, Français, 日本語, 한국어. Живёт это в
`webview/src/i18n/`: `en.ts` - источник правды, остальные девять объявлены как `Dict`, то есть `typeof en`.

- **Английский вшит, остальные девять подгружаются.** `en.ts` едет в бандле - он и запасной вариант, и то,
  что рисуется до того, как язык вообще станет известен; за остальными ходит `import()` из `LOADERS`
  (`i18n/index.ts`). Ничего на экране этого не ждёт: и панель, и телефон по устройству начинают с
  английского - язык приезжает в `init` и фактом с релея, то есть уже после первой отрисовки, - так что
  загрузка укладывается в паузу, которая и так была. Статический список всех десяти остался ровно один и
  только для тестов (`i18n/all.ts`); импорт его из кода экрана возвращает в оба бандла ~90 КБ gzip слов,
  которые никто не прочитает, - на телефоне это около 40% первой загрузки.
- **Полноту держит компилятор, а не внимательность.** Пропущенный ключ, лишний ключ, функция не с той
  сигнатурой - это красный `tsc`, а не забытая строчка. Всё, чего типы не видят, ловит `i18n.test.ts`:
  пустые значения, остатки `TODO`, и главное - **строка, совпавшая с английской**. Совпадение допускается
  только записанным исключением с перечислением языков (`SHARED_WITH_ENGLISH`): «Plan» по-французски и есть
  «Plan», но это ничего не говорит про японский. Устаревшее исключение тест тоже ловит.
- **Все функции в `en.ts` аннотированы `: string`.** Без аннотации тернарник из двух литералов сужается до
  их union, и ни один перевод в такой тип уже не проходит - ошибка при этом выглядит загадочно.
- **Пусто в настройке значит «как в IDE», а не «английский».** Ради этого всё и делалось: китаец с китайской
  IDE получает китайскую панель, не зная, что переключатель существует. Явный выбор перебивает язык IDE,
  включая явный английский. Настройка машинная (`ClaudePreferences.language`), разрешение языка IDE -
  `IdeLanguage` (по `DynamicBundle.getLocale()`), и `IdeLanguageTest` падает, если список языков в
  Kotlin разъехался со списком в `locales.ts`.
- **Перевод происходит при отрисовке, а не в редьюсере.** `feed/build.ts` кладёт в состояние признаки
  (`ClosedReason`, `ToolMeta`, `CompactOutcome`, `DetailNote`), карточки выбирают слова. Иначе смена языка
  оставляла бы уже набранную ленту во вчерашнем языке. Из того же правила растёт `PermItem.mode` вместо
  готовой подписи и `LimitItem.window` с именем окна от CLI, а не с переводом.
- **`STOPPED_BY_YOU` остаётся английским, и это не забывчивость.** Панель пишет `'Stopped by you'` в
  `MetaItem.stats`, строка уезжает в IDE, и `NotificationReasons.kt` ищет в ней **английский текст**, чтобы
  не слать пуш об оборванном ходе. Переведёшь - у всех неанглийских пользователей пуш на каждый Escape, молча.
  По той же причине по префиксу фильтрует `sounds.ts`. То, что видно на экране, берётся из `MetaItem.outcome`
  рядом.
- **Ширина кнопок MODEL/EFFORT/MODE считается в колонках, а не в символах** (`columns` в `catalog.ts`).
  Иероглиф, кана и хангыль рисуются на две колонки: по длине строки китайское «不问» выходило короче
  «Don't ask», и кнопка строилась уже собственной подписи. Тест проверяет это на всех десяти языках.
- **Описания моделей от CLI приходят по-английски всегда** - он не знает, какой язык у панели. Поэтому там,
  где его список называет знакомую модель, берутся наши слова, а от CLI - только набор моделей
  (`modelOptions`). Незнакомой модели остаётся его описание: одна английская строчка лучше пустой.
- **Телефон говорит языком стола.** Локаль едет фактом `locale` (`RemoteFeed.PROJECT_FACTS`) - `init` для
  этого не годится, он несёт рабочий каталог. `setLanguage` для телефона запрещён (`RemoteCommands.DENIED`):
  настройка машинная, менять её с дивана незачем. Заголовки пушей переводит `PushWords.kt` - единственное
  место, где у плагина есть свои слова: телефон спит, панель не запущена, текст запечатывается здесь.
- **Что нарочно остаётся английским.** `PromptImprover.BUILT_IN_INSTRUCTIONS` - это промпт к модели, и он
  просит писать на языке черновика; перевод сломал бы это правило (на экране рядом есть локализованная
  строчка, объясняющая почему). Имена инструментов (`READ`, `EDIT`, `BASH`), маркер `[Image #N]`, значения
  флагов effort, `shift+tab`, длительности вида «38h 10m» - это идентификаторы и показания приборов, а не слова.
- **Список CJK-локалей один - `CJK_LOCALES` в `locales.ts`.** Провайдер выставляет по нему `data-cjk` на
  корне, и правило про разрядку в `base.css` спрашивает атрибут, а не перечисляет теги заново. Копия в CSS
  ничем не удерживалась рядом со списком языков: десятый язык, добавленный наверху, молча остался бы с
  разрядкой между иероглифами.
- **`<html lang>` пишет провайдер на каждую смену языка** (`i18n/index.ts`). Не косметика: китайский и
  японский делят кодовые точки и рисуют часть из них по-разному, и вариант выбирается по этому атрибуту.
  Оттуда же работает правило, снимающее разрядку в CJK (`base.css`), и шрифтовой стек с явными семействами
  CJK (`tokens.css`): Instrument Sans режется по `unicode-range` на латинице, всё остальное проваливается
  дальше по списку, и без имён семейств браузер выбирает по своему порядку.
- Проверить без IDE: харнесс, выпадающий список языков в тулбаре (он же `?lang=zh-Hans` в адресе) - язык
  доезжает до панели через `init` от плеера, то есть ровно тем же путём, что в жизни.
- **Не переведена вкладка «Statistics»** - ни её собственные подписи, ни 46 ачивок. Экран целиком
  английский намеренно: наполовину переведённый экран читается как поломка, а целиком английский - как
  «сюда ещё не дошли».

## Голосовой ввод: микрофон в JVM, а не в браузере

Кнопка микрофона справа от слэша диктует в поле ввода по ключу Deepgram, который человек заводит сам.
Живёт в трёх местах, как удалённый доступ: `src/main/kotlin/.../voice/` (микрофон, стрим, хоткеи, ключ,
баланс), `Composer`/`App` (кнопка, живая вставка, отмена), `components/VoiceInput.tsx` (экран настроек).

- **Пишет JVM, а не встроенный браузер.** Панель отдаётся по `http://acc-webview` (см. `WebviewResources`),
  а это не secure context - `navigator.mediaDevices` там попросту отсутствует. Чтобы он появился, нужен
  флаг командной строки CEF, а флаги CEF ставятся на весь процесс IDE, то есть и на браузеры чужих
  плагинов. `javax.sound.sampled` не стоит ничего: он в JDK, у IDE на macOS уже есть и
  `NSMicrophoneUsageDescription` в Info.plist, и entitlement `com.apple.security.device.audio-input`, а
  вдобавок из JVM можно открыть сокет с заголовком `Authorization`, чего браузерный WebSocket не умеет
  вовсе (в соседнем notastream из-за этого пришлось искать недокументированный подпротокол).
- **Линия открывается на время диктовки и закрывается после.** Открытая линия - это микрофон, отобранный
  у всех остальных приложений; панель, тихо владеющая микрофоном весь день, - панель, которую сносят.
- **Сокет, а не файл в конце.** Соединение поднимается в начале записи, звук течёт по ходу речи, и к
  отпусканию клавиши остаётся досчитать хвост: замерено в notastream - 135 мс против 0.8-1.4 с у
  пакетного пути, где за соединение, загрузку и расшифровку платят, когда человек уже замолчал.
  Таймауты (4 с на открытие, 1.5 с на хвост, 150 мс тишины после куска) оттуда же.
- **Клавиша, нажатая и сразу отпущенная, - не сетевая авария** (`finalizeOnOpen` и `heard` в
  `DeepgramStream`). Пара сотен миллисекунд короче любого рукопожатия, поэтому конец записи регулярно
  приходит, когда сокета ещё нет; раньше это считалось провалом, и панель писала «Deepgram недоступен» о
  соединении, которое через мгновение открывалось нормально. Теперь хвост запрашивается в `adopt`, когда
  сокет доехал, а запись, в которой не было ни одного куска звука, просто закрывается - просить досчитать
  нечего, и ждать полторы секунды с горящей кнопкой не за чем.
- **Хоткей ловится, пока клавиатура у IDE** (`VoiceHotkeys`, `IdeEventQueue.addDispatcher`). Системный
  хук отпадает не по лени: на macOS он требует Accessibility, на всех платформах - нативный бинарник, а
  библиотека, которой это делают все, под GPL, что с лицензией плагина несовместимо; те, что не GPL,
  не отдают отпускание клавиши, а без него push-to-talk не построить. Через очередь IDE заодно можно
  **съесть** событие: зажатый на пять секунд Ctrl+Shift+D иначе отработал бы ещё и в keymap.
- **Автомат хоткеев отделён от событий** (`HotkeyEngine` + тест). Это та часть, которая ломается молча:
  наполовину отпущенный аккорд, автоповтор, прочитанный как второе нажатие, отпускание клавиатуры,
  глушащее запись, начатую мышью. Два режима называются как в notastream - `pushToTalk` (держишь) и
  `holdTalk` (нажал - пошло, нажал ещё - встало), и у каждого два независимых триггера: клавиша и кнопка
  мыши.
- **Одиночный модификатор - законный биндинг, и лучший.** Модификатор сам по себе не активирует в keymap
  ничего, поэтому «держать правый Option» ни с чем не конфликтует; ради этого в биндинге хранится сторона
  клавиатуры (`KeyEvent.getKeyLocation`). Записывается он не по нажатию, а по отпусканию: в момент нажатия
  «правый Option» неотличим от начала «правый Option + D».
- **Мышь - только боковые кнопки** (`VoiceHotkeys.BINDABLE_BUTTONS`). Левая - это сам интерфейс, средняя и
  правая уже что-то значат в любом месте IDE, и диктовка, едущая вместе с контекстным меню, срабатывала бы
  весь день случайно.
- **Слот принимает только своё устройство** (`VoiceHotkeys.Device`). Строка спрашивает аккорд в одной
  половине и кнопку мыши в другой, а запись слушала и то, и другое: палец на боковой кнопке, пока на экране
  «нажмите клавишу», записывал эту кнопку как клавиатурный хоткей - в строке, которая рядом писала «мышь» и
  показывала пустой слот. Теперь в клавиатурной половине мышь не перехватывается вовсе (под ней есть кнопка,
  которой запись отменяют), а в мышиной клавиши съедаются и ничего не биндят, кроме Escape. Подпись ожидания
  тоже своя на каждую половину - «нажмите клавишу» над слотом, который клавиш не принимает, читается как
  поломка. Строка при этом не переносится никогда: половина, уехавшая под соседку, читается как «строка
  изменилась», а не как «жду нажатия». Не влезло - усекается подпись («Не задано», «Нажмите кнопку…»), но
  никогда не клавиши: аккорд без последней клавиши не короче, он другой.
- **Клавишу забирают вместе с её символом** (`swallowTyped` в `VoiceHotkeys`). Нажатие приходит тремя
  событиями - `KEY_PRESSED`, `KEY_TYPED`, `KEY_RELEASED`, - и код клавиши есть только у первого и третьего.
  Съеденные два оставляли третье в покое, и хоткей из Option и F начинал диктовку и печатал ƒ в поле ввода.
  Признак вешается на само нажатие: у `KEY_TYPED` спрашивать нечего, у него нет ни кода, ни стороны - только
  символ, и опознаётся он тем, что идёт следом за своим нажатием.
- **Хоткей едет в панель клавишами, а не строкой** (`HotkeyBinding.caps` → `VoiceHotkeyCap` →
  `components/HotkeyCaps.tsx`). Раньше IDE собирала «⌥F» одной строкой, а панель рисовала её текстом: ⌥ и ⌘
  не входят в шрифт панели и проваливались в системный - своего размера и веса, посреди строки, набранной
  нашим. Теперь каждая клавиша - плашка, а два знака - собственные рисунки; какой клавише знак, а какой слово,
  решает сторона, которая знает систему (Mac печатает ⌥ и ⌘, Windows - свою клавишу, у Linux Super). Сторона
  клавиатуры («правый Option») едет словом и переводится в панели.
- **Живой текст: финалы в поле, промежуточный хвост - псевдоэлементом.** Хвост рисуется через
  `data-voice` и `.field[data-voice]::after`, а не узлом в поле: узел попал бы в токены черновика при
  первом же чтении, а подмена его посреди композиции вырвала бы недописанный иероглиф у метода ввода.
  Правила склейки фраз (пробел перед куском, но не второй; после чипа - всегда) живут в
  `webview/src/feed/voice.ts` с тестом: они ломаются молча, а видно это уже в отправленном сообщении.
- **Диктовка дописывается в конец черновика, а не в каретку.** Так ждут люди, и только так это переживает
  то, что поле вообще не в фокусе: хоткей работает из редактора.
- **Ошибка едет кодом, а не предложением** (`no-key`, `mic`, `key`, `network`, `deepgram`). Панель говорит
  на десяти языках, IDE - на одном; сентенцию собирает `voiceMessage` в `feed/voice.ts`.
- **Баланс требует роли Owner или Admin.** Ключ с ролью Member прекрасно расшифровывает и не видит денег
  вовсе - это отдельное состояние (`noAccess`), а не ошибка: «что-то пошло не так» над рабочим ключом
  заставило бы менять ключ, с которым всё в порядке.
- **Мультиязык предлагается с предупреждением.** Замер в notastream: `multi` проиграл названному языку и
  на одноязычной речи (0.996 против 0.999), и на смешанной - той самой, ради которой существует. Он есть,
  потому что его просили, и подпись на экране говорит, кому он подходит.
- **Разговор с Deepgram описан дважды** - `voice/DeepgramStream.kt` и `webview/src/mobile/dictation.ts`:
  те же query-параметры, тот же разбор ответа, те же числа (1500 мс на хвост, 150 мс тишины, 200 000 байт
  в очереди). Одним кодом это не сделать - по одну сторону Kotlin в IDE, по другую страница в руке, - так
  что это случай `Frame.kt`/`frame.ts`: меняешь здесь - меняй и там. Расхождение ничего не ломает и
  поэтому опасно: телефон просто начинает расшифровывать чуть иначе, чем стол.
- **Ключ - в PasswordSafe, наружу не отдаётся** (`VoiceKeys`). Панель знает только последние четыре
  символа: секрет, который не входит в страницу, не может из неё уйти.
- **С телефона диктовать можно, но микрофон - его собственный** (`webview/src/mobile/dictation.ts`,
  `useDictation`, `VoiceGrant`). Телефон просит у IDE не микрофон, а временный токен Deepgram
  (`/v1/auth/grant`, минута жизни, только транскрипция) и пишет своим микрофоном - тем, что в руке, а не
  тем, что через комнату. Звук идёт прямо в Deepgram, минуя релей: живой голос через сервер, который по
  устройству умеет носить только запечатанные конверты, - единственное, чего он носить не должен, да и
  шёл бы вдвое дольше. Постоянный ключ не уходит с машины никогда, а `voiceToken` - единственная
  голосовая команда в `ALLOWED`; всё остальное телефону запрещено (`RemoteCommands`).
- **Запись начинается до того, как приедет токен.** Круг до IDE и обратно - полсекунды на хорошей сети,
  и это ровно те полсекунды, в которые человек уже говорит: куски копятся в памяти и уходят одним махом,
  когда сокет открылся. Токен, успевший прийти раньше микрофона, тоже не теряется (`waiting` в
  `useDictation`) - на телефоне с уже выданным разрешением сеть выигрывает эту гонку регулярно.
- **Токен едет подпротоколом, а не заголовком.** Браузерный WebSocket заголовков не умеет вовсе, а
  временный токен Deepgram принимает в форме `bearer` (документированная форма `token` - для постоянного
  ключа и отвечает на временный 401). Найдено перебором в notastream, проверено здесь.
- **Кнопка на телефоне работает жестом мессенджера**: держишь - пишет, отпустил - встало; коротко тапнул -
  осталось включённым до следующего тапа. Держать кнопку две минуты рука не хочет, а жест этот все уже
  знают.
- **Предохранители на случай, когда отпускание не доедет:** потолок в две минуты и остановка при уходе
  фокуса из окна IDE (`HotkeyEngine.windowLostFocus`). Клавишу, отпущенную в другом приложении, мы не
  увидим никогда.
- Проверить без IDE: харнесс, любой сценарий с лентой - кнопка есть везде, речь выдумывает плеер
  (`player.ts`), фразы приходят по словам серым хвостом, а каждая третья диктовка падает, чтобы полоска с
  ошибкой тоже была видна. Экран настроек там же, вместе с балансом и записью хоткея.

## Прошлый разговор - запись, а не работа, которая идёт

Вкладка, открытая из истории или из поиска, проигрывает транскрипт: те же события, что и в живом ходе,
только с пометкой `replay`. Всё, что панель считает «происходит сейчас», обязано эту пометку уважать -
иначе вчерашнее выдаёт себя за сегодняшнее, и каждый такой случай выглядит как поломка.

- **Занятость контекста из проигранного хода не берётся** (`case 'result'` в `feed/build.ts`). Цифры
  прошлого хода говорят, сколько он прочитал, а шкала читает их как «сколько занято сейчас»: разговор
  длиной в день открывался красной сотней процентов, пока не приедет точный ответ от CLI (`INIT_MARKER`
  в `ClaudeSessionHub`). Ровно по той же причине из реплея не берётся и `liveContextUsed`.
- **Список задач из реплея не всплывает над полем ввода** (`TodoItem.replayed`, `latestTodo` в `App.tsx`).
  Панель над полем говорит, что делается сейчас, а в открытом на чтение разговоре не делается ничего -
  вчерашний список с пометкой RUNNING над пустым полем читается как зависшая работа. Сам элемент в
  состоянии остаётся (разговор его правда имел, и продолженный агент его помнит), и стоит агенту
  написать свой список живьём, панель возвращается. Помечаются все три дороги, которыми список
  рождается: `TodoWrite`, `TaskCreate`/`TaskUpdate` и ответ на `TaskCreate`.

## Вопрос человеку ждёт столько, сколько нужно

Разрешение, план и вопрос с вариантами держат ход, пока человек не ответит. Ни таймера, ни автоответа
нет ни у панели, ни у CLI - и это обещание, а не случайность: у конкурента на ответ даётся пять минут,
после чего агент отвечает себе сам, и в отзыве это выглядело как «отошёл от стола, вернулся - важные
файлы удалены».

Проверено на CLI 2.1.247, разбором бинарника и живым прогоном с тем же способом запуска, что у плагина:
запрос `can_use_tool` уходит без срока и ждёт хоста сколько угодно (семь минут без ответа - ничего не
произошло, команда не выполнилась). Два механизма автоответа в CLI есть, и оба до панели не достают:

- **`askUserQuestionTimeout`** («Question auto-continue timeout» в `/config`) - автопродолжение вопроса
  «теми ответами, что уже выбраны». По умолчанию `never`, живёт в терминальном интерфейсе (обратный
  отсчёт, «нажмите любую клавишу, чтобы остаться») и сам себя выключает, когда ответить может кто-то
  снаружи. Панель - именно этот «кто-то»: вопрос уезжает к ней по каналу разрешений, и переменная
  `CLAUDE_AFK_TIMEOUT_MS`, выставленная нарочно, на него не подействовала.
- **`dialogExpiry`** (по умолчанию 5 минут) - срок жизни запроса `request_user_dialog`, и только для
  хостов, которые объявили, какие диалоги умеют. Панель не объявляет ни одного, а незнакомый подтип
  запроса получает честный отказ сразу (`PermissionChannel.Incoming.Unsupported`) - молчание там
  остановило бы ход навсегда.

Отсюда правило: **в пути разрешений не заводить таймеров.** Записи о заданных вопросах уходят только
вместе с процессом, который их задал (`ClaudeSession.awaitingPermission` чистится на stop, на смерть
процесса и на `/clear`), а `SessionPermissions.forgetUnanswerable` выбрасывает лишь то, чего этот
процесс уже не ждёт.

### Обратная сторона: вопрос могут отозвать, и это надо показать

CLI умеет забирать вопрос назад - присылает `control_cancel_request` с номером запроса. Случается это
по-настоящему: Stop, нажатый над висящей карточкой, отменяет вопрос вместе с ходом; то же делает хук,
успевший принять решение, пока панель уже спрашивают.

- **Отозванный вопрос не отвечают.** Ответ на него CLI выбрасывает («Ignoring can_use_tool
  control_response»), а карточка к тому времени уже нарисовала бы решение, которого никто не исполнял.
  Поэтому это `Incoming.Withdrawn` - новость, а не запрос; ответом (`Unsupported`) закрывается только
  незнакомый **подтип**.
- **Строка проверяется отдельной подстрокой.** `"control_cancel_request"` не содержит
  `"control_request"`, и до правки новость об отзыве проваливалась мимо разбора канала в разбор ленты.
- **Карточка закрывается «отозванной», а не «решённой».** Разрешение и вопрос с вариантами просто
  снимаются с экрана (в ленте их и не рисуют - они живут закреплёнными над полем ввода), а план
  остаётся: текст плана всё ещё стоит читать, и потерять его из-за остановленного хода - потеря
  человека. У плана пропадают кнопки и появляется строчка о том, что агент перестал ждать
  (`PlanCard.withdrawn`), а фильтр ленты убирает только по-настоящему решённые планы.
- **Слово одно на три стороны:** `SessionPermissions.WITHDRAWN`, `'withdrawn'` в `protocol.ts`,
  `planDecisionOf` в `useCardState.ts`. Последнее - потому что раньше план читался как «approve, иначе
  keepPlanning», и отзыв молча превратился бы в «отправили на доработку»: карточка исчезла бы из ленты.
- **Ждёт ли разговор человека - считается там же.** Пока запись жива, `awaitsYou` держит и строку
  состояния, и точку на вкладке, и плашку в списке на телефоне; отзыв обязан её снять, иначе разговор
  вечно обещает решение, которого больше нет.
- Проверить без IDE: харнесс, сценарии «A permission the agent takes back» и «A plan the agent takes
  back».

## Субагент оставляет след в ленте, а не только чип в шапке

Запуск субагента - строка разговора наравне с вызовом инструмента (`components/items/TaskCard.tsx`).
Свёрнутая говорит, кто и зачем запущен и сколько работал; раскрытая - полное задание (`prompt` вызова)
и журнал агента с его отчётом в конце.

- **Чип и карточка отвечают на разные вопросы.** Чип - «за кем смотреть прямо сейчас», и он пропадает,
  когда агент закончил, а человек смотрит в другое место (`hiddenTaskIds` в `App`). До карточки вместе с
  чипом уходило всё: ход, поднявший пять агентов, читался потом так, будто модель ответила из воздуха, -
  ни задания, ни ответа нигде. Ровно эта жалоба и пришла с отзывом.
- **Задание берётся из вызова, а не из события.** `task_started` несёт одну строку описания; целиком
  поручение сказано только в `input.prompt` (`taskPrompt` в `feed/build.ts`), и хранится оно обрезанным
  до 4000 символов: состояние ленты копируется на каждую перерисовку, а флот агентов с десятью
  килобайтами инструкций каждый оплачивается на каждой из них. Агент, поднятый скиллом, задания не
  имеет вовсе - у него нет вызова.
- **`Workflow` разбирается той же веткой, что `Task`** (`feed/build.ts`). Его конец приходит не
  результатом инструмента, а уведомлением задачи: оставленный обычным вызовом, он стоял в ленте вечно
  помеченным «unfinished» - рядом с карточкой, в которой был ответ. Имя `workflow` ставится сразу, потому
  что `subagent_type` у него нет, а отчёт с флотом приезжает только с первым `task_progress`.
- **С CLI 2.1.257 результат вызова приходит сразу и это не конец** (записано живым прогоном): `task_started`
  с `tool_use_id`, затем `tool_result` со словами «Workflow launched in background. Task ID: …», дальше флот
  идёт фоновой задачей через `task_progress`, конец - `task_notification`. Этот текст надо читать как
  подтверждение запуска, как «Async agent launched successfully» у `Task` (`ASYNC_AGENT_LAUNCHED`): прочитанный
  как результат, он закрывал карточку на 0.0s, чип гас вместе с ней, и оркестрация из дюжины агентов не была
  видна нигде, пока шла.
- **Журнал агента рисует один компонент на два места** (`AgentLog` в `AgentStreamView.tsx`): экран чипа и
  нутро карточки. Вторая копия разошлась бы с первой на первой же правке.
- Проверить без IDE: харнесс, сценарии «A subagent call», «Several agents in parallel» и «A workflow: a
  fleet of agents at once».

## Агенты workflow видны только по отчёту CLI

Вызов `Workflow` (режим ultracode) - это одна задача, за которой работает флот агентов: девять, сорок.
Обычным путём их не видно вовсе, и это не недосмотр панели, а устройство CLI: **события этих агентов в
поток не приходят ни одной строкой**. Проверено записью реального прогона на CLI 2.1.247 - все строки
потока идут с пустым `parent_tool_use_id` (признак, по которому панель отличает субагента), поля `agentId`
нет ни в одной, а разговоры агентов CLI пишет прямо на диск, в свой каталог. Поэтому чипов у них быть не
может: переключаться не на что, показывать нечего.

Единственное, что панель о них узнаёт, - служебный отчёт `task_progress.workflow_progress`. Там есть всё:
фазы по порядку, каждый агент со своим состоянием, моделью, попыткой, длительностью, токенами, числом
вызовов и превью результата, плюс строки, которые скрипт напечатал сам через `log()`.

- **Отчёт присылают целиком на каждое изменение**, а не дельтой - CLI держит список в задаче и сам его
  сливает. Поэтому `feed/workflow.ts` - чистая функция над последним отчётом, без накопления.
- **`start` - это и «в очереди», и «идёт»**, различает их наличие `startedAt`. Флот из сорока при
  потолке в шестнадцать стоит в очереди больше чем наполовину, и очередь, нарисованная как работа,
  показывает вчетверо больше занятых агентов, чем есть.
- **`error` со `skipped` - не падение**, а снятый рукой агент; в счётчик упавших он не идёт.
- **Строку `last_tool_name` для workflow панель выбрасывает**: там лежит метка последнего шевельнувшегося
  агента, и флот из девяти давал девять одинаковых строчек «→ Scout the components» и ни слова про девять.
- **Чип считает флот** (`workflow:9`), потому что `subagent_type` у workflow нет вовсе и подпись читалась
  как «agent:agent». Кольцо на чипе заполняется долей завершённых - это единственная задача, которая
  вообще знает, сколько ей осталось.
- Проверить без IDE: харнесс, сценарий «A workflow: a fleet of agents at once» - чекпоинты повторяют
  форму настоящего отчёта, включая очередь, повтор, пропуск и падение одного агента.

## Форк продолжает разговор, а не начинает похожий

Форк - это тот же разговор в новой вкладке: CLI поднимает его через `--resume` с `--fork-session`, то есть
с полным транскриптом родителя. Отсюда всё, что должно совпасть с родителем, а не с настройками машины.

- **Модель, усилие и режим наследуются от родительской вкладки** (`ClaudeSessions.branchFrom` кладёт их в
  `SessionLaunch`). Раньше форк стартовал с умолчаний, а каждый селектор пишет умолчание заодно с
  переключением своей вкладки: модель, выбранная в соседней вкладке, решала, на чём поедет форк отсюда.
  Продолжать тот же разговор на другой модели и с другим усилием - не то, что написано на кнопке. Режим
  едет по тому же правилу и с тем же ограничением, что и всё остальное: он применяется к этому разговору
  и ничего не пишет в настройки, так что одобренный план освобождает форк, но не решает ничего за
  следующую вкладку из «+».
- **Шкала контекста на форке начинается с родительской, а не с нуля** (`App.fork` + `case 'context'`).
  Свежая вкладка не знала ни занятости, ни размера окна и падала на общий запасной размер в двести тысяч:
  на любом сколько-нибудь длинном разговоре это меньше унаследованного, и шкала открывалась красными
  100%. Точную цифру у CLI спрашивают, как только поднялся процесс (`INIT_MARKER` в `ClaudeSessionHub`), -
  до этого держится родительская, и это самое правдивое, что вообще есть.
- **Форк переставляется внутри своей группы, а вся группа - за голову** (`moveWithinGroup` в `tabs.ts`,
  `SessionRegistry.moveTab`, тот же расчёт в `Header` над «единицами» строки). Голова группы - разговор, из
  которого всё выросло, и она не двигается: полоса цвета, отступ и зазор рисуют группу именно по ней.
  Форк из группы не выходит, в чужую не заезжает, и в группе из двух вкладок жест снова тянет всю группу -
  переставлять там нечего, а жест, который видимо ничего не делает, читается как поломка. Порядок хранится
  в IDE, потому что список вкладок один на всех клиентов.

## Правка видна сразу, а не за двумя стрелками

Дифф законченного `Edit` стоит в ленте открытым: строки, которые убрали, и под ними строки, которые
добавили. Так это делает Codex, и причина та же - неправильную правку надо заметить, не собираясь её
искать.

- **Вызов правки не складывается в группу** (`isEditTool` - один список на все три места, где он нужен).
  В пачке из шести чтений правка пряталась за двумя закрытыми стрелками сразу - группы и своей карточки.
- **У провалившейся правки диффа нет.** Дифф собирается из того, что агент просил заменить, а не из того,
  что получилось: на отказе («такого текста в файле нет») он рисовал изменение, которого не было, и
  выбрасывал объяснение CLI - карточка отдаёт диффу своё тело. Нет диффа - видно причину.
- **Открыто показывается не всё** (`DIFF_PREVIEW_LINES` в `ToolCard`): первые шесть строк, а хвост - под
  стрелкой, с честной подписью, сколько осталось. Правка, переписывающая файл одним куском, иначе
  выдавливает с экрана сам разговор - на двадцати четырёх строках именно это и происходило. Строка «ещё N
  строк» - сама кнопка, которая их показывает и прячет обратно: стрелка в шапке делает то же самое, но
  шапка и дифф - соседи, а не одно внутри другого, и строка, которая открывается снизу, а закрывается
  только сверху, читалась как два разных элемента, случайно согласных друг с другом. Диффы чуть длиннее потолка показываются целиком
  (`DIFF_PREVIEW_SLACK`): обрезать девять строк до шести ради подписи «ещё 3» - это клик, который ничего
  не экономит.
- **`Write` диффа не рисует.** Новый файл - это не «что изменилось», а весь файл целиком, и вываливать его
  в ленту незачем.

## Путь в ленте открывает файл в редакторе

Заголовок карточки `READ`/`EDIT`/`WRITE` и путь в тексте ответа - ссылки: нажатие открывает файл в
редакторе рядом, а у правки - на месте самой правки. Сообщение `openFile` обрабатывает `ClaudePanel`
(`editor/OpenInEditor.kt`), телефону оно запрещено - там нет редактора, а путь наружу не уходит вовсе.

- **Номер строки взять неоткуда, поэтому едет текст.** CLI отвечает на правку фразой об успехе, а не
  местом в файле (проверено по всему локальному архиву разговоров), так что панель шлёт первую
  добавленную строку диффа (`find`), а место ищет сторона IDE - в том самом файле, который собирается
  показать. Номер едет только там, где человек написал его сам: `App.tsx:120` в тексте ответа - и вместе
  с ним столбец, если он написан (`App.tsx:120:30`). Столбец сначала выбрасывался, и это было зря:
  написавший его имел в виду именно тот символ.
- **Сетевой путь не открывается никогда** (`isOpenablePath`, и то же самое на стороне IDE). Текст, из
  которого читается путь, - не человеческий: агент пересказывает файлы, вывод команд и страницы из сети.
  Поход по `//host/share` - это обращение к хосту, которого никто не выбирал, а на Windows машина заодно
  представляется: имя пользователя и ответ на парольный запрос тому, кто слушает. Отказ стоит с обеих
  сторон, потому что вторая - та, которая реально пошла бы.
- **К диску ходят не из потока сообщений.** Спросить у диска «это файл?» стоит секунд, если это уснувший
  внешний диск или отвалившаяся шара, а поток тот же, на котором панель получает все свои сообщения (так
  же отходят в сторону выбор файла и буфер обмена). Там же потолок на чтение файла ради поиска строки:
  минифицированный бандл читать незачем, он откроется с начала.
- **Что считается путём, решает одно узкое правило** (`feed/paths.ts`), и оно нарочно отказывает при
  сомнении: версия `2.1.247`, глоб и каталог ссылками не становятся. Одиночное имя должно попасть в
  список известных расширений: иначе `state.items` посреди фразы про код - тоже «имя с расширением», и
  каждая четвёртая такая ссылка вела в никуда. Со слэшем внутри или с номером строки список не нужен -
  это уже форма пути. Ссылка, которая никуда не ведёт, хуже обычного текста: она обещает и ничего не
  делает.
- **Есть ли такой файл - сначала спрашивают у списка файлов проекта, и только потом у формы строки**
  (`knownFiles` в `feed/paths.ts`, контекст `KnownFilesContext` в `hooks/useOpenFile.ts`). Список тот же,
  что кормит подсказку «@» (`files` от `ProjectCatalog`: до 4000 записей, без `.idea`, `node_modules` и
  сборочных папок). Имя, которое в нём есть, - ссылка, каким бы ни было расширение: голое `.gitignore` в
  блоке кода, `app.iml` в бэктиках, `Makefile` без расширения; `Node.js` в прозе - нет, потому что такого
  файла нет. Повод - первый же отзыв: рядом стояли два одинаковых на вид имени, одно открывалось, второе
  предлагало скопировать, а разницу - расширение из списка - человек не видит и не должен. Вне бэктиков имя
  без точки ссылкой не становится даже из списка: скрипт `build` без расширения превратил бы слово «build»
  в ссылку по всему ответу. Список не полон, поэтому правила формы остаются вторым ответом: путь со слэшем
  или номером строки - ссылка и без списка, а `iml` добавлен в известные расширения, потому что `.idea` в
  список не входит. В харнессе и на телефоне списка нет, там форма решает одна, как раньше.
- **Ссылкой становится путь и в голом тексте, и внутри блока кода** (`withFileRefs`), а не только то, что
  в бэктиках. Так и приходит самый частый случай: на просьбу «дай список файлов» агент отвечает голыми
  строками, а список путей, по которым нельзя нажать, - это ровно то перепечатывание, ради которого всё
  делалось. В прозе правило строже, чем в бэктиках: нужен слэш или номер строки, иначе «Node.js» посреди
  фразы стал бы ссылкой в никуда. Блок кода при этом теряет волну проявления - она умеет бежать только по
  цельной строке, - и это дешевле, чем список, по которому нельзя нажать.
- **Ссылками становятся и пути в вашем собственном сообщении, и в тексте ошибки** (`LinkedText` через
  общий `PathLink`). Путь, вставленный в поле руками, - самое явное указание на место, какое вообще
  бывает, а в тексте ошибки живёт стек с путями.
- **Диапазон не просто открывается, а выделяется**: `App.tsx:15:33-40` выделит в редакторе те восемь
  символов, `App.tsx:15-20` - шесть строк. Написать диапазон - значит попросить показать этот кусок, а не
  поставить каретку в его начало и оставить остальное считать глазами. Конец включительный, как считает
  человек, и оба конца прижимаются к тому, что в файле реально есть: ссылка, написанная по памяти или
  против успевшего измениться файла, обязана попасть куда-то настоящее. Раньше вся ссылка отвергалась
  из-за хвоста, то есть текстом оставалось самое точное, что человек вообще написал.
- **Путь в бэктиках открывается, а не копируется.** Копирование по нажатию осталось у всего остального:
  флаг, имя ветки, идентификатор нужны в буфере, а путь - в редакторе. Подсказка при наведении говорит,
  что именно сделает нажатие. На телефоне контекст не выдаётся вовсе, и там путь копируется как раньше.

- **Голое имя ищется по проекту, как «Go to File», а не только в корне** (`OpenInEditor.byName`, `rank` с
  тестом). Первый релиз искал относительный путь только от корня проекта, и `Button.js` в бэктиках - а это
  половина всех упоминаний файлов в ответах, посчитано по транскриптам этого же проекта - рисовалось ссылкой
  и молча не открывало ничего; ровно это и написали в первом отзыве на фичу. Теперь имя спрашивают у индекса
  проекта (в smart mode: пока индекс строится, клик ждёт, а не отвечает «нет»), а написанные перед ним папки
  сверяют с хвостом пути по сегментам: `src/Button.js` - это `legacy/src/Button.js`, но не `xsrc/Button.js`.
  Не нашлось под этими папками - предлагаются все файлы с таким именем: список, из которого выбирают, - это
  ответ, а «ничего не произошло» - единственное, чем клик по ссылке быть не должен. Несколько совпадений -
  чузер IDE с путями от корня и написанным в заголовке; слов плагина в нём нет, потому что панель говорит
  на десяти языках, а IDE на одном. Исключённые папки и библиотеки в индексе не лежат - `node_modules` на
  имя не отзывается. Регистр - как у файловой системы: на маке и Windows `readme.md` находит `README.md`.
- **Чип файла в отправленном сообщении - кнопка, а не подпись** (`chipFile` в `feed/reference.ts`, с
  тестом). Файл открывается по своему пути, картинка из буфера - по файлу, который под неё записала
  оболочка, ссылка из редактора - на то же выделение: подпись `L12:5-L18:30` разбирается обратно
  (`rangePlace`), и конец колонки уменьшается на единицу - редактор пишет колонку ПОСЛЕ последнего
  выделенного символа (`SelectionReference`), а `select` в `OpenInEditor` считает конец включительно, как
  человек. Папка, команда и цитата остаются подписью; на телефоне подписью остаётся всё - там нет редактора.
- **Диапазон через строки с колонками на обоих концах выделяется до своего конца** (`select`): раньше
  `endColumn > column` читалось как «кусок одной строки», и `App.tsx:12-18:5-30` выделял кусок двенадцатой.
- Проверить живьём: `sandbox-project` держит три `Button.js` в разных папках, два `README.md`, два
  `settings.json` и один `format.js` в подпапке - список в его README. Голое имя обязано открыть
  единственный файл сразу и предложить выбор из трёх, `components/Button.js` - открыть один без вопросов.

## Процент компакта считает лента, а не карточка

Сколько компакт уже идёт, записано в самой карточке ленты (`CompactItem.startedAt`, часы машины с IDE), а
не в секундомере, который заводится при отрисовке. Секундомер живёт ровно столько, сколько узел на экране:
возвращение в IDE после перерыва, восстановление панели из журнала, телефон, подключившийся посреди
компакта, - каждый такой случай отправлял процент обратно на ноль, пока сам компакт продолжал идти.
Считается разница через `useNow`, как и пауза перед повтором запроса рядом.

## MODEL, EFFORT и MODE принадлежат разговору, а не окну

Три чипа под полем ввода дают одно и то же обещание: выбор применяется к тому разговору, который на
экране, и НЕ трогает соседние вкладки, что бы в них сейчас ни происходило. Модель и усилие вдобавок
запоминаются как умолчание - с них начнётся следующая вкладка; режим разрешений умолчание не пишет, у
него для этого своя строка в меню шапки (`setDefaultMode`).

Устроены они по-разному, и разница не декоративная:

- **Режим** едет служебной заявкой `set_permission_mode`, CLI отвечает применённым режимом, отказ
  откатывает чип. Умолчание не пишется (`ClaudeSessions.setPermissionMode`).
- **Модель** едет заявкой `set_model`, отказ настоящий (модель может быть запрещена организацией), и
  умолчание пишется только на успех - иначе следующая вкладка стартовала бы с флагом, от которого CLI
  не поднимется.
- **Усилие** едет заявкой `apply_flag_settings`, и вот тут всё остальное приходится помнить нам.

Про усилие подробно, потому что ломается оно молча:

- **Ключа два, и они всегда едут вместе** (`effortLevel` и `ultracode`, см. `ClaudeSession.setEffort`).
  Слой настроек CLI сливает, а не заменяет: не назвал ключ - остался прошлый выбор, то есть
  переключение с ultracode на max оставило бы оркестрацию включённой. `ultracode` - это его же
  собственное имя для «xhigh плюс постоянная оркестрация», `auto` пишется как `null`.
- **Раньше это ехало фальшивым ходом** - панель писала `/effort high` в разговор от лица человека,
  глушила ответ и, пока шёл чужой ход, держала команду до его конца. Всё это удалено вместе с
  машинерией (`applyPreference`, `pendingPreference`, `flushPreference`,
  `suppressingPreferenceReply`): заявка применяется мгновенно, работает посреди идущего хода и
  перебивает флаг `--effort`, с которым процесс поднялся (замерено на CLI 2.1.247 нашими же флагами
  запуска).
- **Канал не отказывает.** Неизвестный уровень, запрет организации, выключенные workflow - на всё
  приходит `success`; внятные объяснения у CLI есть, но живут на его мосту Remote Control, до нас они
  не доезжают. Поэтому у усилия нет ни отказа, ни отката - в отличие от модели и режима.
- **И не читается обратно.** `get_settings` отдаёт слияние настроек с диска (`resolved` на этой версии
  пустой), смена через `/effort` в нём не видна вовсе, в `system/init` усилия нет, и события о смене
  CLI не шлёт. Значит правда об усилии живёт ровно в одном месте - `ClaudeSession.effort`.
- **Панель узнаёт его сообщением `effort`, и оно живое, а не журнальное.** Это состояние, а не то, что
  разговор сказал: в журнале каждый выбор лежал бы в истории ленты вечно и вытеснял бы оттуда то, чем
  телефон восстанавливает разговор, а первым выпало бы из журнала как раз то единственное сообщение,
  которое и объясняет, с чем вкладка стартовала. Поэтому смена и рождение разговора рассылаются
  `emitLive`, подключившемуся клиенту усилие кладут в `attach`, а `resetJournal` называет его заново -
  всё тем же способом, что и очередь.
- **Рождение разговора объявляется отдельно** (`ClaudeSessions.onBorn`). Вкладка, в которой усилие
  никто не трогал, обязана показывать то, с чем стартовала: без этого её нарисовало бы текущее
  умолчание, то есть выбор, сделанный позже и в другой вкладке. Ровно та жалоба, ради которой всё это
  и переделывалось.
- Проверить без IDE: харнесс - плеер отвечает на `setEffort` сообщением `effort`, как это делает
  оболочка. Живьём - две вкладки в песочнице с разным усилием: `low` отвечает заметно быстрее, а на
  `ultracode` в задаче `Workflow` появляется флот агентов.

## Отмена в поле ввода одна, откуда бы её ни позвали

История отмен поля - своя (`undoStack` в `Composer`), потому что браузерная не видит чипов: они кладутся
через Range, а не через `execCommand`. Cmd+Z перехвачен, но у поля есть второй вход - контекстное меню,
которое рисует сама IDE, и его «Undo» запускает браузерную отмену.

- **Нативная отмена перехватывается и уводится в нашу историю.** Иначе получалось то, ради чего это и
  делалось: меню отдирало от текста напечатанное, вложения оставляло стоять, наша история не двигалась - и
  следующий Cmd+Z возвращал то, что меню только что убрало. Отмена, идущая вперёд.
- **Ловится `input`, а не `beforeinput`.** Команда, запущенная так, `beforeinput` не шлёт вовсе, так что
  отменять нечего: к моменту события DOM уже переложен. Здесь это ничего не стоит - наш откат
  перерисовывает поле из токенов и заодно чинит то, что нативная отмена успела разобрать.
- **Слушатель на самом поле и в фазе перехвата**, потому что React слушает на корне страницы: `stopPropagation`
  не даёт обычной обработке ввода прочитать полуразобранный DOM как «человек что-то напечатал».
- **Пустая история - не повод стирать черновик.** История своя у каждой вкладки и обнуляется при переходе
  между ними, а браузерная - нет: без этой ветки меню съедало кусок текста в только что открытой вкладке.
  Тогда поле просто перерисовывается из своих же токенов.
- Проверить без IDE: харнесс - `document.execCommand('undo')` в поле делает ровно то же, что пункт меню.

## Вложение уносят из панели путём, а не подписью

Скопированное сообщение - и из поля ввода, и из ленты - несёт пути к вложениям, а не их подписи. Правило
живёт в `feed/tokens.ts` (`clipboardText`) с тестом, а выделение в ленте подменяет `feed/copy.ts`.

- **Что видит агент и что уносит человек - разные строки.** Агенту едет сообщение: `@путь` у файла,
  `[Image #3]` у байтов, которые идут вложением рядом с текстом. Человек копирует это в задачу, в чат, в
  терминал - там `@` ничего не значит, а «Image #3» называет то, чего нигде нет. Поэтому в буфер идёт
  сам путь, а текст сообщения остаётся текстом.
- **Чип в ленте несёт свой текст атрибутом** (`data-acc-copy`), а обработчик копирования подменяет им
  выделение - в клоне выделения, а не на экране. Вмешивается он, только если в выделении есть чип: во
  всём остальном браузер копирует правильно и сам.
- **Вставленному из буфера дают файл** (`webview/PastedFiles.kt`, `webview/src/pasted.ts`). Скриншот и
  документ приходят байтами без пути (страница не имеет права знать, где что лежит на машине), поэтому
  IDE пишет их в свой системный каталог и отвечает путём. С этого момента вложение ведёт себя как любое
  другое: копируется путём, открывается в редакторе, его можно назвать другому человеку.
- **Картинка при этом всё равно едет агенту байтами.** Файл - для человека: перечитывать его инструментом
  значит просить разрешение на то, что агенту уже отдали.
- **Документ без файла не вставлялся вовсе.** До этого вставка чего угодно, кроме текста и картинки, молча
  не делала ничего - у панели были байты, которые некуда положить. Теперь это обычный чип с путём.
- **Имя приходит от буфера и остаётся именем** (`PastedFiles.nameFor`): последний сегмент, буквы, цифры и
  простая пунктуация. Каталог выбирает плагин - сообщение, которое говорит, куда писать, можно заставить
  сказать что угодно. У скриншота имени нет вовсе (в буфере пиксели), там имя собирается из времени.
- **Свободное имя занимается в момент подбора, а не только проверяется** (`PastedFiles.free` создаёт файл через
  `createNewFile`). Несколько файлов из одной вставки пишутся параллельно, каждый своим потоком, и проверка
  «существует ли» пропускала двоих под одно имя: второй затирал первого, агенту доставался один документ
  дважды. Провалившаяся запись удаляет занятый файл - пустой файл под именем документа хуже отсутствующего.
- **Каталог метётся по возрасту** (14 дней, `PastedFiles.sweep`), и метётся на входе, а не по таймеру:
  единственный момент, когда эта папка вообще кому-то важна, - это когда в неё что-то кладут.
- **Телефону `savePastedFile` запрещён** (`RemoteCommands`): он пишет файл на чужую машину и отвечает
  путём на ней, а телефон прикладывает своё через собственный экран.
- **В поле «свой ответ» у вопроса агента вставка работает так же** (`AskPanel`). Ответ уезжает текстом и
  только текстом, поэтому туда кладётся путь - в место каретки, а не в конец: ответ бывает написан
  наполовину.
- Проверить без IDE: харнесс - плеер отвечает на `savePastedFile` выдуманным путём (`player.ts`), так что
  видно и чип, и то, что уносит копия.

## Вставку читают в ленте, а не в подсказке

Вставка из буфера — единственное вложение, которому больше негде быть: чип файла отсылает к файлу на
диске, а вставка не существует нигде, кроме этого сообщения. Поэтому она раскрывается по нажатию прямо в
карточке (`PasteView` в `components/items/UserCard.tsx`), а подсказка при наведении показывает только
первые строки.

- **Подсказка не повторяет то, на чём висит** - правило на всю панель, а не свойство чипа. Точка на
  вкладке статистики молчит (рядом стоит слово «Статистика»; у вкладки разговора та же точка говорит, чем
  та занята, - этого нигде больше нет), а чип фоновой команды показывает саму команду и молчит, когда её
  нет. Наведение, отвечающее тем, что и так на экране, ещё и закрывает строку под собой.
- **У чипа файла подсказка говорит, что сделает нажатие, а не повторяет имя.** Раньше она повторяла
  подпись самого чипа с папками впереди: наведение, которое отвечает тем, что и так на экране, - потраченное
  наведение, и оно закрывает строку под чипом, пока это делает. Теперь чип открывает файл (см. «Путь в
  ленте открывает файл в редакторе»), и подсказка у него та же, что у любого открывающегося пути.
  Исключение одно - имя, не влезшее в подпись: разрезанное посередине, оно не читается, и подсказка тогда
  единственное место, где оно есть целиком (`chipTitle`). У чипа, который ничего не открывает (папка,
  команда, телефон), пустая строка означает «наводить не на что», и атрибут в этом случае не выставляется
  вовсе: пустая подсказка под курсором читается как что-то недогрузившееся.
- **В подсказку не кладут текст целиком, и это правило, а не вкус.** Так было: `chipTitle` отдавал две
  тысячи символов, а рисует подсказки один общий элемент шириной 220 px, сквозной для указателя
  (`Tooltips.tsx`). Сто строк в нём — полоса в двадцать символов во всю высоту окна, обрезанная его
  краем, и проскроллить её нельзя в принципе. Потолки живут в `feed/reference.ts` (`chipTitle`) и держатся
  тестом; в `tooltip.module.css` под ними стоит `max-height` — страховка на случай, если мимо потолка
  что-нибудь однажды проедет.
- **Раскрытие чинит и телефон.** Подсказок там нет вовсе (`hover: hover` в `Tooltips`), то есть
  посмотреть вставку с телефона было нельзя никак. Лента общая — то же нажатие открывает текст и там.
- **Раскрытый текст ограничен по объёму** (`pasteBody`), потому что люди вставляют стокилобайтные логи, а
  лента перерисовывается на каждый кусок печатающегося ответа. Обрезка режется по границе строки и
  сообщается парой чисел, из которых слова собираются при отрисовке; кнопка рядом копирует вставку
  целиком, сколько бы её ни было на экране.
- **Строка со счётчиком строк стоит на месте, когда вставка раскрывается.** Кнопка копирования в той же
  строке выше своего текста (двадцать пикселей против тринадцати) и растягивала строку до своей высоты -
  подпись, отцентрованная в выросшей строке, уезжала вниз на разницу ровно в момент раскрытия. Кнопка
  сохраняет размер (это цель для пальца), а строка - высоту своего текста (`margin-block` у
  `.chipPasteCopy`). Стрелка там же стоит по центру строки, а не по её верху: `.caret` написан для шапки
  вызова, где он прижат к первой строке высокого блока.
- **Сворачивает только заголовок, а не всё пятно.** Нажатие внутри текста — это человек, выделяющий
  строку: вставка, схлопывающаяся под выделением, не копируется руками вовсе.
- **Раскрытие не двигает ленту, и это общее правило, а не свойство вставки** (`holdPressed` в `Feed.tsx`).
  Лента липнет к низу, поэтому любой прирост высоты тянул её в конец: раскрытая карточка уезжала с экрана
  вверх, а вместо неё показывался конец разговора — то есть ровно то, на что человек не смотрел. Теперь
  нажатие, которое что-то разворачивает, пришпиливает строку, где оно случилось, и текст открывается вниз
  от неё. Это касается всех раскрывающихся карточек — групп вызовов, мыслей, находок ревью, — потому что
  живёт в общем состоянии карточек (`useCardState`), через которое они все и раскрываются; вставка
  переведена на него по той же причине. Низ при этом проигрывает намеренно: раскрыл старое — читаешь его,
  а вернуться вниз предлагает своя кнопка. Якорь пишется и на нажатие мыши, и на клавишу: карточка
  раскрывается и с клавиатуры, а якорь от прошлого клика пришпилил бы чужую строку.
- Проверить без IDE: харнесс, сценарий «A paste inside a sent message». Сообщения там приезжают
  `promptEcho` — обычная отправка из харнесса несёт голый текст, а речь именно про чипы.

### С какой длины вставка вообще сворачивается - решает человек

Порог живёт в настройках («Pasted text» за строкой «Settings»): «никогда» или число строк, с которого
вставка становится чипом. По умолчанию два - то есть ровно прежнее поведение, любая вставка с переносом
строки.

- **Правило считает `feed/reference.ts`** (`collapsesPaste`, `pasteCollapseLines`), а не композер: оно
  ломается молча, и видно это уже в отправленном сообщении.
- **Строки считаются те, что видно в поле, а не те, что записаны в тексте** (`wrappedLineCount` в
  `composerDom.ts`). Скопированное из браузера или из просмотрщика логов часто приходит одной строкой без
  единого перевода - по прежнему счёту это «одна строка», то есть ниже любого порога, и стена текста
  въезжала в поле ровно в том случае, ради которого сворачивание и сделано. Меряется настоящей раскладкой
  в невидимой копии поля: сколько строк займёт текст, зависит от ширины панели и от шрифта, взятого из
  настроек IDE, - посчитать это по числу символов нельзя.
- **Длинный текст отвечается без раскладки.** Ни один глиф не уже нескольких пикселей, поэтому текст
  длиннее «самой широкой строки, умноженной на порог» не может уместиться в меньшее число строк - и
  двести килобайт одной строкой обходятся в 5 мс вместо 96.
- **«Ничего не выбрано» и «выбран ноль» - разные вещи.** Пустое значение настройки означает умолчание
  панели, ноль - «не сворачивать никогда». Поэтому IDE шлёт поле только когда выбор сделан
  (`pasteCollapse` в `ProjectCatalog.sendInit`), а панель начинает с двойки сама: харнесса за IDE нет
  вовсе, и поле, ничего там не сворачивающее, было бы другим полем.
- **Настройка машинная и телефону запрещена** (`RemoteCommands.DENIED`): телефон вставки в чипы не
  сворачивает вовсе.

## Полоска контекста подписана, иначе её не читают

Над полем ввода - шкала занятого контекста, и в конце её стоит «ctx 42%» цветом самой полоски
(`ContextMeter` в `Composer.tsx`). Без подписи её принимали за украшение: в отзывах просили показать
контекст, который панель показывала всё это время. В узких раскладках (compact, left, right) шкала
вертикальная, места под цифру нет - там та же строчка живёт подсказкой при наведении.

«ctx» не переводится: это показание прибора, как значения effort и «38h 10m» у колец расхода.

## Разговор из истории открывается там, где нечего терять

Выбранный в истории разговор занимает вкладку на экране, если она нетронута - пустая лента, пустое поле,
ничего не идёт, - и открывает свою во всех остальных случаях. Правило живёт в `feed/resume.ts`
(`isUntouchedTab`) с тестом: ломается оно молча, а расплата - чужая работа, стёртая без предупреждения.

- **Черновик считается наравне с лентой.** Недописанный запрос в поле - это тоже работа, и он принадлежит
  вкладке: разговор, открытый поверх него, унёс бы слова вместе с вкладкой, в которой их писали. Туда же
  идут очередь отложенных сообщений, фоновые команды и вывод команд через «!».
- **Вопроса «открыть здесь?» больше нет.** Раньше над занятой вкладкой висел диалог с двумя ответами -
  «отмена» и «убить идущий ход», причём второе он не проговаривал. Взвешивать нечего, когда третий ответ
  ничего не стоит: открывается своя вкладка.
- **Уже открытый разговор не открывается второй раз** (`tabHolding` там же). История - список всего, включая
  то, что сейчас на полосе вкладок, и выбор такой записи значит «покажи мне её»: фокус переходит на
  существующую вкладку, реплей не проигрывается. Две вкладки на один разговор - это два процесса над одним
  транскриптом, и написанное в одну для другой не существует. Чтобы это работало сразу после нажатия, вкладка
  запоминает разговор в тот же момент (`resumed` в редьюсере), а не ждёт, пока поднявшийся процесс назовёт
  себя: id при продолжении сохраняется (новый получает только форк), и несколько секунд ожидания как раз и
  давали второй такой же вкладке появиться. Телефон делит то же правило и ту же функцию - для этого инвентарь
  несёт разговор каждой вкладки (`conversation` в `RemoteAgent.inventoryBody`).
- **После сброса журнала IDE называет разговор вкладки заново** (сообщение `conversation`, `resetJournal` и
  `attach` в `ClaudeSessionHub`). Сброс, который идёт следом за выбором из истории, стирал записанную панелью
  отметку, а процесс называет разговор только когда поднялся - через секунды или никогда (нет исполняемого
  файла, нужен вход). В эту щель второе нажатие той же строки открывало вторую вкладку на один транскрипт, а
  прыжок к находке ждал под вуалью процесс, который мог не прийти. Досылается так же, как модель и усилие.
- **Разговор из истории поднимается на своей модели, а не на умолчании панели** (`ClaudeHistory.Page.model`
  читается с хвоста транскрипта по подписи под ответом, `ClaudeSessions.adoptModel` ставит её спящему процессу
  до `wake`, панели она едет сообщением `model` с `born: true`). Умолчание - это то, с чего стартует НОВАЯ
  вкладка; старый разговор отвечала своя модель, и его сообщения набраны под её окно. Поднятый на умолчании,
  разговор с модели в миллион токенов попадал в окно на двести тысяч: CLI честно отвечал 167%, шкала резала до
  красных 100% («любой старый чат открывается на 100%»), а первое же сообщение ушло бы в компакт, о котором никто
  не просил. Сам CLI без `--model` продолжает сессию на её модели - проверено живым прогоном. Ровно поэтому
  `born` не пишет умолчание: модель старого разговора - факт про вкладку, а не выбор для следующей. Панель
  меряет выбор по `ownModel` вкладки, а не по настройке, иначе своя модель разговора читалась бы как «CLI сам
  переключил» с галочкой в меню.
- **Вкладку заводит IDE, а не тот, кто попросил** (`ClaudeSessionHub.resumeConversation` →
  `SessionRegistry.takeOver`). Список вкладок один на всех клиентов, и запрос, называющий вкладку, которой
  в списке нет, раньше оставлял живой процесс, на который ничто не указывает: панель с закрытыми вкладками
  на выбор из истории мигала и оставалась пустой, а разговор при этом уже был поднят - он «открывался»
  следующим нажатием «New chat». Так же теперь и телефон обходится одним сообщением вместо трёх.
- **Имя разговора едет вместе с запросом.** Продолжение сбрасывает имя вкладки на стороне IDE (оно описывает
  то, чего в ней больше нет), а список вкладок приходит оттуда же - поэтому имя, записанное только в своё
  окно, жило до ближайшего ответа, и вкладка из истории стояла «New chat», пока в неё не напишут. Ставится
  оно поверх любого прежнего, включая имя от модели: то принадлежало предыдущему разговору.
- **Вкладка статистики - не разговор.** Она стоит в той же полосе и может быть активной, а её идентификатор
  не принадлежит никакому разговору: reuse проверяет, что активная вкладка вообще есть в списке разговоров.
- Проверить без IDE: харнесс, любой сценарий с лентой - плеер отвечает на выбор из истории коротким реплеем
  (`answerResume` в `player.ts`). Три случая подряд: занятая вкладка даёт новую, «+» и сразу история -
  открывает в ней же, «+», слово в поле и история - снова новая, а слово остаётся на месте.

## Прошлый разговор открывается с конца, а не целиком

Чат из истории приезжает в панель **хвостом** (`ClaudeHistory.opening`), остальное подгружается
страницами по метке над лентой. До этого в панель уходил весь транскрипт сразу, и на Windows чат из
истории открывался пустым: файл рабочего дня — десятки мегабайт, он уезжал десятками пачек по мегабайту,
каждую приходилось резать на куски и склеивать уже в странице, а потерянный кусок уносил с собой всю
пачку из двухсот сообщений — молча, `JSON.parse` спотыкался на склейке. На macOS проходило, на Windows
канал в страницу уже нет.

Что из этого следует и что легко сломать:

- **Граница живёт в общем редьюсере, а не в каждом экране** (`oldestEventUuid`, `reachedStart`,
  `earlierPages` в `PanelState`; `historyPage` в `feed/build.ts`). Телефон умел это раньше панели и
  держал у себя вторую копию — теперь копия одна, и правка чинит оба экрана. Появится третий экран —
  ему не понадобится третье понимание «что выше этого».
- **Опознаётся по `uuid` строки транскрипта, а не по номеру.** Живой журнал и файл на диске не имеют
  общей нумерации: журнал подмешивает статусы и разрешения, которых на диске нет вовсе, — счётчик
  разъезжается на первом же изменении статуса.
- **`cursor` в `replayFinished` имеет три значения, и `null` — не то же, что его отсутствие.** Строка —
  это шов, `null` — «начало уже на экране», отсутствие — «про границу ничего не сказано, не трогай её».
  Последнее и есть телефон: реплей ему не пересылается вовсе (`RemoteFeed.isReplayLine`), у него своя
  граница из собственного хвоста.
- **Страница читается окном, а не файлом** (`ClaudeHistory.windowOf`): один проход, в памяти — страница
  плюс небольшой запас. **Окно режется из сырых строк, и разбирается только то, что в нём осталось**
  (`candidates` → `windowOf` → `replayLine`): раньше каждая строка до границы парсилась дважды (вывод команды и
  форма содержимого) и укорачивалась, чтобы через мгновение быть выброшенной окном. На транскрипте рабочего дня в
  полсотни мегабайт это были секунды на страницу, а прыжок к находке поиска выше загруженного просит страницы одну
  за другой - вуаль стояла над лентой столько, сколько нужно, чтобы прочитать весь файл столько же раз. Сырые
  строки стоят прохода строковых проверок; `drawsOwnRow` и `uuidOf` и так читают строку без разбора. Запас нужен, потому что нарезка может шагнуть выше, чтобы страница начиналась со
  строки, которую следующий запрос сможет назвать. Окно, обрезанное ровно по размеру, шагать некуда.
- **Окно ограничено ещё и весом, а не только числом строк** (`MAX_WINDOW_CHARS` в `windowOf`, с тестом). Окно
  держит сырые строки, а сырая строка - это результат инструмента целиком, по полмегабайта; четыре тысячи
  таких на разговоре рабочего дня - гигабайты в куче IDE, ровно на тех разговорах, ради которых постраничная
  загрузка и сделана. Перебор веса выбрасывает самые старые сообщения; единственное, что не отдаётся никогда, -
  последняя строка. Цена - страница короче обычной на разговорах с тяжёлыми чтениями, то есть лишнее нажатие.
- **Размер страницы зависит от того, кто спросил** (`ClaudeHistory.earlier`, `hub.isLocal`).
  Телефонная страница обязана пролезть в кадр релея (256 КБ), панельная — нет. Одна на двоих была бы
  меньшей из двух, и чтение длинного чата на столе превратилось бы в череду нажатий.
- **Пачка в страницу ограничена весом, а не только числом сообщений** (`batchOf` в `WebviewHost`).
  Ограничения по числу хватало для живой работы и не хватало ни для чего крупного.
- **Куски нумерованы, и потеря больше не молчит.** Мост в странице проверяет порядок и разбор, а о
  провале сообщает обратно (`channelLoss` → `DiagnosticsLog`). Сообщение перечислено в `DENIED`
  (`RemoteCommands`) — оно про дорогу между IDE и её собственной панелью, и телефону там сказать нечего.
- **Позицию чтения держит `Feed`, а не экран** (проп `earlierPages`). Страница встаёт выше всего, что на
  экране, а браузер хранит прокрутку числом: без поправки читаемые строки прыгают вниз на высоту
  загруженного. Признак — счётчик отвеченных страниц, а не рост ленты: метка над лентой сохраняет свою
  личность, и по росту «загрузили выше» не отличить от «пришёл ответ ниже».
- Проверить без IDE: харнесс, сценарий «system» → чекпоинт про конец реплея. Метка над лентой там
  нажимается, страницы выдумывает сам плеер (`harness/player.ts`), третья приходит без курсора — на ней
  метка исчезает.

## Место чтения переживает переключение вкладок

У каждой вкладки своя лента (`key={active}` в `App.tsx`), то есть на каждом переключении она строится с
нуля, а построенная с нуля лента открывается в конце. Читаешь что-то в середине долгого разговора,
заглянул в соседнюю вкладку, вернулся - и чтение выброшено. Поэтому единственное, что стоит переносить
через переключение, живёт снаружи ленты: `feedPlaces` в `App.tsx` держит место по вкладке, правила -
`feed/place.ts` с тестом.

- **Место держится строкой ленты, а не числом пикселей.** Лента растёт не только внизу: отвечает фоновая
  команда, отчитывается субагент, перерисовывает свой флот workflow. Всё это выше того, кто читает выше, и
  запомненная прокрутка сдвинула бы его на высоту того, чего он не видел. Запоминается строка на верхней
  кромке и то, насколько её собственный верх выше кромки; голое смещение остаётся запасным ответом на
  случай, когда строки в ленте уже нет (план решён, ошибка убрана).
- **«Стояло в конце» запоминается фактом, а не числом.** Пока вкладки не было на экране, в неё мог
  напечататься ответ, и человек оставил её на конце разговора, а не на пикселе, где конец тогда был.
- **Строка на кромке ищется делением пополам** (`rowAtEdge`), а не перебором: строки стоят по порядку, а
  событие прокрутки приходит десятками в секунду, и длинный чат - это сотни строк, которые иначе
  промерялись бы каждый раз.
- **Пишется на прокрутку, а не при уходе.** Когда вкладку снимают с экрана, её строки уже разбирают, и
  единственный честный замер - сделанный, пока они стояли. Прокрутка при этом ничего не пропускает:
  выставленный руками `scrollTop` поднимает своё событие, так что программные прыжки приходят туда же.
- **Вернувшаяся строка ещё мгновение придерживается** тем же механизмом, что и раскрытая карточка
  (`held`): лента досаживается после отрисовки (доехал шрифт, карточка домерилась себя). По той же причине
  прыжок к результату поиска и кнопка «вниз» этот придерживатель гасят - просьба человека старше пина.
- **Прыжок к находке выполняется один раз** (`Feed.onFocused`, `forgetFeedFocus` в обоих `App`). Лента
  строится заново на каждое переключение, и просьба о прыжке, оставленная стоять, выполнялась каждой новой
  лентой: возврат на вкладку выбрасывал к находке вместо места, которое лента только что честно вернула.
  Лента сообщает, что прыгнула, и просьба забывается; стрелки капсулы просят заново на каждый шаг.
- Проверить без IDE: харнесс, любой сценарий с лентой - прокрутить вверх, нажать «+», вернуться на первую
  вкладку: лента обязана стоять там же. Оставленная в конце обязана вернуться в конец.

## Статистика и ачивки: одна книга на всю машину

Вкладка «Statistics» и экран ачивок за ней собирают цифры в трёх местах, и границы между ними
намеренные:

- **`src/main/kotlin/.../stats/`** - сбор и правила. `StatsCollector` (один на проект, живёт в
  `ClaudeSessionHub.stats`) слушает поток агента, сообщения, решения по разрешениям, вкладки и
  пишет всё в `StatsLedger` - сервис уровня приложения, у которого один JSON-файл на всю машину
  (общий каталог JetBrains, чтобы WebStorm и IntelliJ считали в одну книгу). Единица хранения -
  `DayRecord`: день одного проекта, только счётчики, суммы и максимумы. Любой диапазон на вкладке -
  это арифметика над днями, поэтому переключение 7/30/всё не ходит в IDE.
- **Вкладка считает всю машину, а не открытый проект.** Панели уезжают дни, уже сложенные по всем
  проектам (`StatsSnapshot.daysTogether`), и по ним же считаются ачивки. Счётчики складываются,
  максимумы берутся по большему, а минуты **объединяются, а не суммируются**: два проекта, работавшие
  в одну минуту, потратили одну минуту жизни. Сумма проектных минут ровно этим и врала - день в 2 часа
  показывался как 4. По проектам осталась одна карточка «WHERE THE HOURS WENT», и она рисуется из
  минут, которые проекты несут отдельно от дней; её строки законно складываются в больше, чем длится
  день. Пятичасовое окно лимита - тоже про аккаунт, а не про проект: считается по множеству окон.
- **Из IDE едет не только следующая планка, но и взятая** (`line` в `AchievementState`, `Achievements.Definition.lineOf`). Без неё панель знала только «сколько ещё до следующей», и оба места, где это видно, врали: полоска прогресса заполнялась от нуля (на IV она почти полная всегда), а «earned lately» подписывала тир текущим значением - «10 hours · III» над «7h 23m» читается как обещание, которое не выполнено, хотя третья планка стоит на шести часах, а имя ачивки - это пятая. Правишь лестницы - не забывай, что панель теперь считает прогресс между двумя планками.
- **Планки ачивок калиброваны под агента, а не под человека с клавиатурой.** Пятый тир - примерно год
  плотной работы, первый - первые дни. Считать «нормальным» темпом ~4000 строк и ~1000 команд в день:
  на прежних планках («тысяча строк», «десять файлов за ход», «пять MCP») экран заполнялся за два дня.
  Ладдеры про привычку (серии, выходные, недели) не трогать - они и так медленные. Двигаешь планку -
  поднимай `Achievements.RULES_VERSION` и вписывай id в `RECALIBRATED`: при следующем запуске книга
  разово забудет взятые тиры этих ачивок и заработает их заново. Иначе на экране останется пятый тир
  против планки, которой больше нет.
- **Ступеней у ачивки столько, сколько линий в её лестнице** (`Achievements.Definition.steps` → `steps` в
  сообщении `statistics` → пипсы на карточке). Пять - у большинства, но не догма: у вехи одна, у «Thanks»
  три - по одной на каждый способ сказать спасибо (звезда на GitHub, отзыв на странице плагина, слово
  тому, кто о плагине не слышал); четвёртого способа в плагине нет.
  Короткая лестница, пройденная целиком, красится верхним тиром: «сделано» есть «сделано», сколько бы
  линий на это ни ушло. Тест каталога читает `Achievements.kt` и падает, если стороны разошлись в числе
  ступеней. Двигаешь лестницу - смотри `RECALIBRATIONS`: забывается только то, что переехало после версии,
  записанной в книге, а не весь список разом.
- **Имя ачивки - имя, а не планка; подпись - что меряют, а не сколько надо** (`catalogue.ts`). Под именем
  и так стоит цифра против цели, а рядом с ним - римский тир, поэтому «Tier V wants 60» и «30 active days»
  в подписи повторяли то, что уже видно, а имя-число («10 hours» над «7h52/8h») читалось как невыполненное
  обещание: это третья линия из пяти, а имя взято с пятой. Цепочки по одной метрике (часы в панели, строки)
  различаются титулами, а не числом, - тест каталога держит имена уникальными и запрещает слово «tier» в
  подписи. Веха - одна планка: одна полоса вместо пяти, без римской цифры, и в общем счёте шагов она стоит
  единицей, а не пятёркой.
- **Правила ачивок - в Kotlin (`Achievements.kt`), слова и иконки - в TS
  (`webview/src/stats/catalogue.ts`).** Связаны по id, и тест с каждой стороны читает файл другой
  стороны: добавил ачивку в одном месте - оба теста красные, пока не добавишь во втором. Момент
  получения тира записывается в IDE, а не в панели: тир, взятый с телефона ночью, должен получить
  свою дату и без открытой панели.
- **Подпись в угловых скобках - не модель** (`StatsCollector.isRealModel`). CLI подписывает `<synthetic>`
  свои собственные ответы: прерванный ход, неизвестную команду, текст ошибки API. Принять её за модель -
  значит и завести в карточке строку, которой никто не запускал, и отнять ход у той модели, что реально
  работала до прерывания. Лента панели отбрасывает те же метки (`realModel` в `feed/build.ts`), а книга
  чистится при чтении файла, а не разово при старте: файл общий на машину, и соседняя IDE со старым
  плагином записала бы их снова.
- **Что легко сломать.** Каждая метрика обязана только расти (счётчик, сумма, максимум) - иначе тир
  придётся отбирать, а это не про ачивки. Строки replay не считаются вовсе (прошлое уже посчитано).
  Пути на диск не пишутся: проект - это имя плюс хэш, файлы в дне - короткие хэши. Сообщения
  `statistics` и `stat` в `RemoteCommands` запрещены для телефона: книга - про всю машину, а не про
  один разговор. Что считает только панель (чипы в сообщении, сердечко, руки на клавиатуре) - она и
  сообщает через `stat`; всё остальное IDE видит сама и там же считает.
- **Одна ачивка делится отдельно** (кнопка на карточке, `PosterOptions.width` и `heading`). Дорога та же,
  что у целого экрана: клонируется живой узел карточки. Отличий два - ширина (целый экран требует 900 px
  под четыре плитки, одна карточка на такой ширине выглядит ошибкой) и шапка: у карточки логотип и имя
  плагина сверху с фразой от первого лица, у экрана - марка внизу. Кнопка стоит в верхнем ряду карточки
  и держит своё место всегда, иначе при наведении имя прыгало бы вбок; из снимка она вырезается по `SKIP`,
  а `data-hover` с клона снимается руками - указатель в момент нажатия стоит на карточке, и её подсветка
  уехала бы в картинку.
- **Картинка «поделиться» - это сам экран, а не второй его рисунок**
  (`webview/src/stats/poster.ts`). Кнопка в шапке клонирует живой узел вкладки, разворачивает у клона
  прокрутку, кладёт рядом подпись с логотипом и «plugin for <IDE>» и рисует всё это в canvas через
  SVG `foreignObject`. Отсюда три вещи, которые ломаются молча: внутрь `foreignObject` не попадают ни
  правила страницы (они собираются в свой `<style>`), ни переменные с `:root` (они пишутся на обёртку
  явно); а всё, чему на картинке не место, помечается атрибутом `SKIP` - иначе кнопка «поделиться»
  окажется на своём же снимке. Ширина снимка не меньше 900 px: в узкой панели плитки встают в одну
  колонку, и картинка выходит нечитаемой.
- **Скачивания в JCEF нет.** Ссылка с `download` внутри панели молча не делает ничего, поэтому
  байты уезжают в IDE сообщением `saveImage`, а файл пишет `webview/ImageDownloads.kt` - в папку
  загрузок, с уведомлением «Показать в Finder». Имя оттуда - только имя: разделители и точки в начале
  срезаются (`safeName`), папку выбирает плагин. Телефону `saveImage` запрещён.
- Проверить живьём без IDE: харнесс, сценарии «Statistics: a summer of work» и «Statistics: the
  second day» - они шлют готовое сообщение `statistics` и открывают вкладку. Кнопку «поделиться» там
  тоже можно нажать: харнесс играет роль оболочки и скачивает картинку браузером (`player.ts`).

## Обратная связь: обещание, которое держится тестом

Кнопка-облачко рядом с сердечком открывает экран «Feedback» в боковом меню: тип обращения, текст,
необязательная почта, вложения и галочка «приложить отладочные логи». Живёт это в трёх местах, как и
удалённый доступ:

- **`webview/src/components/Feedback.tsx`** — кнопка (три варианта под три раскладки композера), сама
  форма и второй экран с предпросмотром отчёта. Состояние формы держит `App.tsx`, а **не** сам экран:
  уход в предпросмотр размонтирует экран, и написанное пропало бы.
- **`src/main/kotlin/.../feedback/`** — `DiagnosticsLog` (кольцевой буфер технических событий),
  `FeedbackReport` (сборка отчёта), `FeedbackEnvironment` (версии), `FeedbackAttachments` (выбранные
  файлы), `FeedbackSender` (первый настоящий HTTP-запрос плагина), `FeedbackDesk` (координатор, живёт в
  `ClaudePanel`).
- **`feedback-service/`** — приёмник на своём сервере (`feedback.mzpizote.com`), пересылает в телеграм.
  Отдельный сервис, а не роут в релее: релей самодостаточен, под Apache-2.0 и готовится к выносу, а
  приёмник с токеном чужого бота был бы мёртвым грузом в каждой чужой копии. Как деплоить — в
  `feedback-service/README.md`.

Что легко сломать, не заметив:

- **Обещание «в отчёт не попадает приватное» держится `FeedbackReportTest`, а не аккуратностью.** Журнал
  разговора — это весь разговор: промпты, ответы, содержимое прочитанных файлов, пути. Из него не
  копируется ничего: каждая запись разбирается на форму (тип события, имя инструмента, размер в байтах,
  успех, тайминг), и строка отчёта пишется из этих фактов. Поля читаются по белому списку — незнакомое
  поле не попадает в отчёт по умолчанию. Имена файлов — короткими хэшами (тот же digest, что в
  статистике). Меняешь отчёт — этот тест главный.
- **В `DiagnosticsLog` нельзя класть содержимое.** Соблазн в одной строке: `ClaudePanel` при незнакомом
  сообщении логирует в `idea.log` весь JSON от панели, включая текст промпта. В буфер идут только тип и
  длина — буфер уезжает наружу, `idea.log` нет.
- **Панели не отдаются пути к файлам.** Выбранное держит IDE, панель знает `id`, имя и размер; при
  отправке она называет `id`. Поэтому она не может назвать файл, который человек не выбирал, и путь не
  может утечь с экрана, который отправляет данные наружу.
- **Сообщения фидбэка обрабатываются в `ClaudePanel`, а не в `SessionCommands`.** До `ClaudePanel`
  сетевой клиент не доходит физически — это гарантия помимо списка. В `RemoteCommands` они всё равно
  перечислены в `DENIED`, иначе `RemoteCommandsTest` красный.
- **В compact-раскладке кнопка стоит в ряду инструментов, а не рядом с сердечком.** Три селектора делят
  тот ряд и не сжимаются меньше своего текста (`.selectorAuto`), так что вторая кнопка выдавливает
  сердечко за край — ровно в тех узких панелях, ради которых compact и выбирают.
- **`PRIVACY.md` — часть фичи, а не документация о ней.** Там перечислено, что именно едет в отчёте;
  добавил в отчёт новое — правь и его, иначе страница начинает врать.
- **Ключ и адрес приёмника переопределяются для проверки**: `-PfeedbackUrl=http://localhost:8081` и
  `-PfeedbackKey=…` у `runIde`. Общий секрет в плагине — замедлитель против сканеров, а не защита: он
  лежит в открытом бинарнике, и в `feedback-service/README.md` это сказано прямо.
- Проверить форму без IDE: харнесс отвечает на сообщения фидбэка сам (`harness/player.ts`) — отдаёт
  образец отчёта, выдуманные файлы и каждую третью отправку роняет, чтобы был виден путь с ошибкой.

## Новогодний слой: три украшения и одно окно в календаре

С 24 декабря по 3 января панель наряжается: гирлянда одной строкой под шапкой, снег над лентой и
ледяная кнопка Send. Больше ничего — ни настройки, ни уровней, ни экрана в боковом меню.

- **Ворота — `webview/src/holiday.ts`**, и они целиком в панели, а не в IDE. Панель рисуется JCEF на той
  же машине, где идёт IDE, так что её `new Date()` — это и есть календарь IDE; скос часов, ради которого
  живёт `hooks/useNow.ts`, — проблема телефона, а телефон не наряжается. `hooks/useHoliday.ts` пересчитывает
  ответ на границе суток: тул-виндоу открывают один раз и оставляют, и панель, прочитавшая календарь при
  монтировании, встретила бы 24-е неукрашенной.
- **`HOLIDAY_OVERRIDE` перед релизом обязан стоять в `auto`, и это держит тест, а не память.** Это
  единственный включатель темы; `'on'` и `'off'` нужны, чтобы посмотреть слой в песочнице и в харнессе
  в обычный августовский день. Забыть его в `'on'` — выпустить вечную зиму, в `'off'` — декабрь без
  зимы, и больше ничто бы этого не поймало: с включённой темой панель работает нормально, просто
  наряжена в июле. Поэтому же сам ключ передаётся в `holidayUnder` параметром: у константы компилятор
  сузил бы тип до текущего значения и объявил две ветки из трёх недостижимыми.
- **Украшения кладутся в `App.tsx`, а не в `Feed`.** Лента общая с телефоном
  (`mobile/screens/Thread.tsx`), и всё, повешенное в `Feed`, поехало бы на экран, у которого своя шапка
  и свой композер.
- **Гирлянда стоит в потоке первым ребёнком `.content`, а не абсолютом поверх `.panel`.** При боковых
  раскладках `.panel` — грид, а `.railColumn` занимает всю его высоту: полоса поперёк панели
  перечеркнула бы чипы model/effort/mode. Снег — абсолютный слой внутри `.body` (он уже `relative` и уже
  красит фон ленты), `pointer-events: none` обязателен: лента — выделяемый текст.
- **Снег падает и пропадает — сугроб на нижней кромке пробовали и сняли.** Копящийся слой закрывает
  разговор, а украшение, которое приходится обчитывать, перестаёт быть украшением. Если идея вернётся:
  расти надо `transform`-ом блока во всю высоту, а не высотой короткого блока — `height` раскладывает
  ленту заново каждый кадр.
- **Лёд не трогает `Run` и `Queue`** (`[data-holiday] .send:not(.sendRun):not(.sendQueued):not(:disabled)`
  в `composer.module.css`). Оранжевая `Run` означает «уйдёт в твою оболочку» — это смысл, а не
  украшение; кнопка очереди делит класс с Send и намеренно нейтральна; у выключенной свой приглушённый вид.
- **Keyframes живут в `holiday.module.css` рядом со своими классами** — по той же причине, что описана в
  шапке `shell.module.css`: CSS-модуль переименовывает имена анимаций вместе с классами. Заодно весь слой
  снимается одним файлом.
- Проверить без IDE: харнесс, любой сценарий с лентой — он рендерит настоящий `App`, так что украшения
  видны сразу, включая ледяную кнопку.

## Поиск по разговорам: индекс в IDE, окно в панели, капсула в ленте

Лупа - третья группа в ряду инструментов под полем (после «скрепка / слэш»), тот же ряд во всех
четырёх раскладках, плюс Cmd/Ctrl+F, пока фокус в панели. Окно с тремя табами: «Этот чат», «Все чаты»
(оба - один набранный запрос, таб меняет только область) и «Спросить ИИ» (описание словами, явная кнопка
«Найти»). Клик по результату сворачивает окно в капсулу в правом верхнем углу ленты: «Back to search»
возвращает окно с тем же запросом, «2/5» со стрелками ходит по находкам этого чата, крестик закрывает
поиск целиком - окно, капсулу, оба поля и ответы (`resetSearch`; тот же крестик в окне делает то же). Escape
и клик мимо окна только прячут окно и всё в нём хранят (`closeSearch`): крестик говорит «с этим покончено»,
шаг назад - «не сейчас». Закрытие вкладки, на которой стоит капсула (или над которой открывали окно, пока
капсулы нет), - тот же крестик: эффект над `sessions` в `App` зовёт `resetSearch`, откуда бы вкладку ни
закрыли - из панели, с телефона или из IDE. Живёт в четырёх
местах: `search/` на стороне IDE (индекс, движок, запуск модели, координатор), `components/Search.tsx`
и `SearchCapsule.tsx` (окно и капсула, общие с телефоном), `feed/search.ts` и `feed/searchText.ts`
(правила, которые ломаются молча), `App.tsx` и `mobile/App.tsx` (проводка).

- **Окно - четыре полосы: табы, поле, результаты, подвал** (`Search.tsx`, `search.module.css`). Табы
  несут по счётчику каждый, поэтому переключаться, чтобы узнать, есть ли там что-нибудь, не надо: оба
  числа приезжают в одном ответе (`counts` в `searchResults`), потому что скоринг для обоих одинаков -
  вторым поиском ради бейджа платили бы на каждом нажатии клавиши. Счётчики считаются ДО обрезки по
  лимиту: бейдж «50» над двумя сотнями врёт ровно о том единственном, что он говорит.
- **Строка результата целиком - кнопка, а плашка «Open in chat» на ней не кнопка.** Наведение показывает
  плашку, нажатие в любое место строки открывает сообщение в его разговоре. Раскрытая строка перестаёт
  быть кнопкой: текст в ней читают и выделяют, поэтому действия выписаны под ним двумя настоящими
  кнопками («Open in chat» и «Copy»), а клик по тексту больше ничего не открывает.
- **«Все чаты» группируются по разговору** (`groupByChat` в `feed/search.ts`): заголовок с названием,
  датой и числом сообщений, под ним строки. Без этого три строки про рефанды из трёх разных разговоров
  читались как один ворох. Порядок групп - порядок, в котором пришли результаты (они отсортированы по
  релевантности), то есть группа с лучшим попаданием стоит первой.
- **Клавиши работают без подсказки в подвале**: ⏎ открывает выбранное, → раскрывает сообщение, ←
  сворачивает, Escape прячет окно. Подвал держит только счёт (см. ниже).
- **Пока модель ищет, окно показывает, что она делает** (`searchProgress`, `AiStep`, `Progress` в
  `Search.tsx`). Запуск идёт `--output-format stream-json`, и каждый вызов инструмента превращается в шаг:
  что искала, какой разговор открыла. Причина простая: прогон занимает 10-25 секунд, и спиннер над
  «Reading the conversations…» столько времени неотличим от зависшего. Шаг едет кодом и темой, а не
  фразой - слова принадлежат панели, она говорит на десяти языках.
- **Капсула в углу ленты: назад в окно, стрелки и крестик.** Стрелки ходят по находкам ТОЛЬКО этого
  разговора, в порядке, в котором сообщения стоят в нём (`chatHits` в `feed/search.ts`, с тестом: сортировка
  по `at`, а не по релевантности), какой бы широкой ни была область поиска: поиск по всем чатам находит
  дюжину разговоров, и стрелка, прыгающая в чужой, была бы списком из окна, только хуже. По остальным
  разговорам - через «назад в окно». Список едет в капсулу целиком при выборе результата (`jumpToHit`
  получает третьим аргументом все находки), счётчик «2/5» и стрелки стоят только когда есть куда шагать,
  шаг закольцован, как у любого find-next, а находка выше загруженного идёт той же дорогой, что выбранная
  из окна (`stepHit` → `showHit`, с вуалью).
- **Окно стоит на ступень выше меню (скрим 44, окно 45), а не на его лестнице.** Чипы MODEL, EFFORT и
  MODE нарочно подняты на 41, выше скрима меню, чтобы второй клик по чипу закрывал его же меню; окно
  поиска на той же высоте оставляло их непритемнёнными и под своим нижним краем. Лестница целиком
  записана в `holiday.module.css`.
- **Ищет IDE, панель только рисует.** Панель держит хвост чата и подгружает страницы по запросу, так что
  даже «этот чат» нельзя искать по тому, что в странице. Транскрипты в 100 раз тяжелее слов, что в них
  сказаны (на этой машине 600 МБ против 4 МБ на 199 чатов): `TranscriptText` вынимает слова человека и
  модели - и ничего из машинерии: ни результатов инструментов, ни размышлений, ни вывода команд через
  «!» (команда остаётся как `! git status`), ни строк с моделью в угловых скобках. `SearchIndex` держит
  их в памяти и копией на диске рядом со статистикой (`search/<slug проекта>/`): jsonl только дописывается,
  поэтому живой файл дочитывается с байта, на котором остановились, а не перечитывается целиком. Копия -
  кеш: нечитаемая перестраивается из транскриптов молча. Обновление не чаще раза в полторы секунды
  (`REFRESH_INTERVAL_MS`): поиск по мере набора спрашивает много раз в секунду.
- **Нечёткость - свой движок (`TextIndex`), а не библиотека.** Инвертированный индекс с BM25; каждое
  слово запроса обязано найтись (нет «почти подходящего» ответа при отсутствующем слове), слово ищется
  по началу (`deepgr` для deepgram), с одной-двумя опечатками (от четырёх букв - короче правка делает
  другое слово) и по усечённой основе (от шести букв, минус до трёх с конца, но не короче пяти: так
  «наследует» находит «наследовал» и «наследование» - настоящий стеммер был бы по одному на язык, а
  усечение одно на все; на этом корпусе «наследует» доходит до «наследовать» и «наследование» только
  через основу, правкой в два символа их не достать), фраза в кавычках должна стоять как написана.
  Латиница и кириллица - разные слова: «fork» не найдёт «форк», и это не чинится. Fuse.js для этого не годится: битап на паттерне до 32 символов
  и оценка по расстоянию от начала строки - для имён, не для тел сообщений.
- **Первая сборка индекса оплачивается при открытии проекта, а не первым нажатием** (`SearchDesk.init`,
  через двадцать секунд после открытия, в фоне): на этом корпусе холодная сборка - секунды даже блоками
  (транскрипты читаются кусками по 256 КБ, побайтово было 8.7 с). Следующие запуски читают копию с диска
  (66 мс на 5400 сообщений), обновление - только дописанное.
- **Слово режется одинаково по обе стороны** (`Words` в `TextIndex.kt` и `feed/searchText.ts`): буквы и
  цифры, подчёркивание разделяет, camelCase и стык буквы с цифрой дают части рядом с целым
  (`oldestEventUuid` - это и oldest, и event, и uuid), свёртка - строчные, без акцентов, ё как е. IDE
  называет найденные термы (`terms` в ответе), панель красит их в ленте; разойдутся правила - панель
  перестанет красить, молча. Тесты по обе стороны держат одни примеры - это случай `Frame.kt`/`frame.ts`.
- **Красится набранное, а не всё слово, и сколько красить - решает IDE** (`Painted` в `TextIndex.kt`,
  `PaintedTerm` в `protocol.ts`). Терм едет с числом `paint`: слово, найденное по началу, красится на длину
  набранного («use» в UserCard светит только «Use»), найденное по основе - на основу, по опечатке - целиком
  (набранных букв в тексте нет). Так же считаются и спаны сниппетов в окне, и ленты через `matchSpans`:
  панель правило не знает, только применяет. Слова запроса - только целые прогоны: набранное «UserCard» -
  одно слово, а не оно и две его половины, которые тоже надо найти.
- **У поля два переключателя, как у Find in Files: Cc и W** (`matchCase`, `wholeWords` в сообщении
  `search`; ⌥⌘C и ⌥⌘W, не на маке Ctrl вместо ⌘; по `event.code`, потому что с зажатым Alt мак печатает
  «ç»). Оба - проверка текста кандидата, а не второй индекс: постинги свёрнуты, и сообщение со словом в
  другом регистре или внутри длинного находится ими как любое другое и отсеивается уже по тексту
  (`paintOf`). Match case хочет буквы как набраны - опечатка не находится вовсе, ей нечего сравнивать; Whole
  words хочет слово само по себе: без начала, опечатки, основы и не часть camelCase, так что «card» не
  находит UserCard. Что нужно проверить, едет в `PaintedTerm` (`text`, `whole`), и лента красит по тем же
  проверкам. Стоят в конце поля после крестика и кольца, и ни тот, ни другое их не двигают: место берётся из
  ширины самого поля.
- **Подсветка в ленте - через CSS Custom Highlight API** (`Feed.paint`, `::highlight(acc-search)`), а не
  через обёртки в тексте: разметка карточек не трогается, чипы, код и волна проявления целы. Строка,
  к которой прыгнули, подсвечивается мазком на 1.8 с (`.rowLit`) и ставится в верхнюю треть экрана;
  лента при этом отлипает от низа - человек ушёл куда-то нарочно.
- **Прыжок - по uuid, а для живого своего сообщения - по тексту** (`rowOf`). Сообщение с диска несёт
  uuid транскрипта (`UserItem.uuid`, `TextItem.uuid`, проставляются в `build.ts`), а своё живое сообщение
  попало в ленту по нажатию Send раньше, чем CLI его записал, - uuid у него нет никогда, и хит на нём
  ищется по словам. Ответы всегда несут uuid события. Хит выше подгруженного тянет страницы вверх
  (`jumping` в `App`), не больше `JUMP_PAGE_LIMIT`, и в начале разговора или на потолке капсула честно
  пишет «нет среди загруженных»; сам текст хита при этом читается в окне (стрелка у результата).
  Чужой разговор открывается правилом истории (`resume` возвращает вкладку): уже открытая - фокус,
  нетронутая - в ней, иначе своя; прыжок ждёт `replayFinished`, иначе страницы запросились бы до того,
  как реплей назвал свою границу, и она бы вернулась вперёд - страница легла бы дважды.
- **ИИ-поиск - отдельный `claude -p` внутри корпуса, а не в проекте** (`AiSearch`). Те же флаги, что у
  «улучшить» (`--safe-mode`, `--strict-mcp-config`, `--no-session-persistence`, всё человеческое через
  stdin), но с инструментами - ровно Grep, Read, Glob - и рабочим каталогом `corpus/` рядом с индексом:
  сессии как текст, `sessions.txt` со списком, у каждого сообщения заголовок `## <uuid> <время>
  <you|claude>`. По сырым транскриптам искать нельзя: строки по мегабайту, один grep съедает контекст.
  Ответ просим JSON-объектом в тексте и разбираем терпимо, без `--json-schema`: схема - аргумент с
  кавычками, а кавычка режет команду на Windows (см. `ClaudeLaunch`). Хит модели превращается в
  обычный через `index.lookup`: выдуманный uuid никуда не ведёт и выбрасывается. Отмена настоящая -
  `ClaudeCli.run` отдаёт процесс через `onStarted`, `searchCancel` его убивает, а провал отменённого
  никому не сообщается.
- **Модель - Sonnet на low, запасная Opus, и это замер, а не вкус** (`AiSearch.MODEL`): на этом корпусе
  три запроса по-русски обе нашли верно, Sonnet low - за 10-23 с и 2-7 центов, Opus low - за 15-24 с и
  6-16 центов, Sonnet medium - 48 с и двадцать шагов на первом же. Скрипт замера - в комментарии к
  константе; менять модель - перемерить.
- **Отмена помнится с момента запроса, а не с момента процесса** (`AiRuns`, с тестом). Первые секунды
  ИИ-поиска - обновление индекса и запись корпуса, процесса ещё нет, и отмена, знавшая только процессы,
  проваливалась в эту щель: прогон стартовал, работал до конца и оплачивался, а ответ панель выбрасывала.
  Теперь запрос известен с `ask`, отмена до старта не даёт ему стартовать, отмена после - гасит процесс, а
  процесс, приехавший после отмены, гасится на приёме.
- **Отметка «докуда дочитали» в копии индекса сдвигается после записи, а не до** (`SearchIndex.keep`, `kept`
  против `seen`, с тестами). Провалившаяся запись оставляла манифест с отметкой, до которой файл не дошёл, и
  сообщения этой записи после перезапуска не находились уже никогда. Теперь манифест пишет только то, что
  на диске есть; провал помечает разговор `stale`, и на следующем обновлении копия пишется целиком.
- **Список рисуется только под той вкладкой, для которой найден** (`answerScope` в `Search`). Ответ несёт
  область запроса; после переключения «все чаты» → «этот чат» до нового ответа список пуст, а не чужой:
  чужие строки без заголовков под другим счётчиком открывали по нажатию другой разговор.
- **Стрелки вверх и вниз в поле описания ходят по строкам, а не по списку** - у поля до шести строк. В
  однострочном поле каретке идти некуда, там стрелки ходят по находкам, как в любом поиске.
- **Cmd/Ctrl+F узнаётся по коду клавиши, как соседние сочетания** (`event.code === 'KeyF'`), с буквой в
  запасе для раскладок, где F стоит в другом месте: по одной букве поиск не открывался с кириллицы.
- **Подсветка в ленте не пересчитывается на каждый кусок ответа** (`PAINT_INTERVAL_MS` в `Feed`). Обход
  всего текста разговора на каждый кадр печатающегося ответа - заметное подёргивание на длинном чате.
  Новые слова красятся сразу, изменения самой ленты - не чаще раза в интервал, а стоящая подсветка между
  проходами не снимается: мигание хуже, чем на мгновение сдвинутый диапазон.
- **Телефону разрешено всё три** (`search`, `searchAi`, `searchCancel` в `RemoteCommands.ALLOWED`;
  лимиты `search` 120/мин под набор, `searchAi` 10/мин как сообщение). Ответ идёт `emitTo` тому, кто
  спросил, и на телефоне принимается до стража по `sessionId` - как история. Окно и капсула общие с
  панелью; проводка в `mobile/App.tsx` своя: чужой разговор всегда открывается своей вкладкой (правило
  телефона), прыжок ждёт `feed.loaded`. Кнопки - в шапке треда и в шапке истории проекта.
- **Что не уезжает наружу.** Индекс лежит на машине и в отчёты попадают только события
  (`DiagnosticsLog.SEARCH`: начался, нашёл N, упал) - ни запроса, ни хита. Хит телефону режется по
  бюджету кадра (`LIMIT_REMOTE`, `TEXT_REMOTE`).
- **Пока лента идёт к найденному, над ней вуаль** (`SearchCapsule`, `.veil` в `search.module.css`). Раньше
  чужой разговор открывался концом, стоял так секунды, пока грузились страницы, и прыгал: экран без того,
  что искали, и без слова почему. Вуаль рисует сама капсула по своему `note === 'loading'`, поэтому у панели
  и телефона она одна и отдельной проводки не требует; капсула стоит над ней (22 против 21 на лестнице),
  чтобы прыжок можно было бросить оттуда же, откуда попросили. Появляется мгновенно, гаснет затуханием поверх
  той отрисовки, в которой строка уже подъехала (`useLayoutEffect` над `focus` в `Feed`), - лента между ними
  не видна. Слова у капсулы остались только про «нет среди загруженных»; про «ищу» говорит вуаль. Вуаль
  непрозрачная: через полупрозрачную было видно, как лента ездит вверх-вниз, пока встают страницы и
  возвращается прокрутка, - это читалось как дрожание, а смотреть там всё равно не на что.
- **Строка «ничего не найдено» не меняется, пока запрос в пути.** Список показывает прошлый ответ, пока идёт
  следующий, и строка идёт со списком: решает `answered` в ответе (панель и телефон), а не `loading`.
  Написанное на каждое нажатие «Ищу…» ↔ «Ничего» и было дёрганьем; о запросе в пути говорит кольцо в поле, и
  только оно: счётчика рядом с полем нет, счёт стоит на табах и в подвале («50 в 12 чатах» для всех чатов).
- **Табы окна не меняют ширину ни от чего.** Активный отличается цветом и подчёркиванием, а не жирностью -
  как вкладки чатов в шапке; счётчик стоит на каждом табе с самого начала, с нуля (`TabCount`). Жирная
  подпись и бейдж, появляющийся с первым ответом, двигали соседние табы на пиксели прямо под указателем.
- **В подвале только счёт, без плашек с клавишами.** Плашки «⏎ open in chat / → whole message» стояли там
  с первой версии окна и сняты по прямой просьбе: клавиши работают и так, а строка, перечисляющая их под
  каждым списком, читалась как мусор, а не как помощь. Три знака (`enter`, `arrowLeft`, `arrowRight`) ушли
  из `HotkeyCaps` вместе с ней - плашки остались только у голосового хоткея. В поле описания для модели
  Enter отправляет, как и в поле под лентой; перенос строки - Shift+Enter или Cmd/Ctrl+Enter (второй
  вставляется руками через `insertText`: textarea сама с ним ничего не делает).
- **Плашка «Open in chat» лежит поверх текста, а не рядом** (`.openPill` абсолютом в `.hit`): соседом по
  флексу она сжимала сниппет под самым указателем. Раскрытая строка под указателем не подсвечивается
  (`.hitOpen:hover`): её фон совпадал с фоном кнопки Copy, и кнопка пропадала; у Copy теперь своя кромка, а
  шеврон при наведении поднимается на два тона над строкой, а не на один.
- **Описание для модели растёт само, от двух строк до шести**, дальше скролл (`AI_LINES_MIN`/`AI_LINES_MAX`,
  layout-эффект в `Search`). Крестик в поле есть на всех трёх табах (`ClearButton`): он гасит `mousedown`,
  чтобы не забирать фокус у поля, и его нет, пока поле пусто.
- **Всем простым полям панели одолжены клавиши композера** (`feed/fieldEdits.ts` с тестом,
  `hooks/useFieldHistory.ts`): Cmd/Ctrl+Backspace удаляет слово перед кареткой, Cmd/Ctrl+Z и Shift к нему -
  своя история отмен с той же склейкой набора (700 мс, граница на пробеле, вставке и смене направления),
  Ctrl+Y - повтор. Причина та же, что у композера: JCEF не пробрасывает в поле системные комбинации с Cmd, а
  Cmd+Z отвечает чужой отменой. Через хук идут оба поля окна поиска, форма обратной связи, инструкции для
  улучшения промпта, «свой ответ» в вопросе агента (ради хука вынесен в `OwnAnswer`: из списка вопросов хук
  не позвать), формы MCP и плагинов, адрес релея, ключ Deepgram и путь к исполняемому файлу. Новое текстовое
  поле без хука - поле, где Cmd+Z отвечает чужой отменой. Крестик, опустошающий поле, идёт через ту же
  историю. DOM пишется раньше, чем состояние: React находит поле уже согласным и не трогает каретку.
- Проверить без IDE: харнесс, сценарий «Searching the conversations» - плеер помнит, что сценарий
  набирал в поле, и отвечает на «этот чат» по этим словам, «все чаты» - по выдуманным сообщениям
  прошлых разговоров витрины, ИИ - через полторы секунды, каждый третий раз с ошибкой; клик по чужому
  разговору открывает вкладку, тянет четыре страницы и заканчивается честным «нет среди загруженных».

## Git — коммиты только с явного разрешения

Не создавай git-коммиты в этом проекте без явного разрешения на каждый
конкретный коммит — включая коммиты, которые обычно случаются «сами
собой» как часть процесса (например каждая завершённая задача при
subagent-driven execution). Я хочу сам посмотреть diff перед тем, как
что-то закоммитится.

Как это применять на практике:
- Правки в рабочем дереве (в том числе через субагентов-имплементеров)
  делать можно свободно — ограничение только на сам `git commit`.
- Если процесс/скилл предполагает коммит как часть шага (ревью задачи,
  правка по фидбеку ревьюера и т.д.) — довести код до готового
  состояния, прогнать проверки, но остановиться перед `git commit` и
  спросить.
- Не откатывай и не трогай уже сделанные раньше коммиты из-за этого
  правила — оно только на будущее.

## Секреты в `.env` — никогда не выводить содержимое целиком

В корне лежит `.env` с `ACC_PUBLISH_TOKEN`, `ACC_PRIVATE_KEY`,
`ACC_PRIVATE_KEY_PASSWORD`, `ACC_CERTIFICATE_CHAIN` — токен и ключ подписи для
публикации в JetBrains Marketplace. Ключ и сертификат — многострочные
PEM-блоки, а не пары `КЛЮЧ=значение`. Разовая попытка замаскировать вывод
самодельным `sed`/`grep` по шаблону `КЛЮЧ=` один раз уже привела к тому, что
весь PEM-блок (без `=` внутри строк) прошёл маскировку насквозь и целиком
утёк в чат — только через глупую самоуверенность, что «одна команда с виду
безобидна».

Правила железно, без импровизации на месте:
- Никогда не читать `.env` целиком и никаким инструментом — ни `cat`/`head`,
  ни `Read`, ни `sed`/`grep` с последующим показом результата. Не пытаться
  маскировать его содержимое самостоятельно: нет гарантии, что маскировка
  учла все форматы значений в файле, а PEM-блоки такую гарантию ломают
  систематически, не как исключение.
- Проверить, что переменная вообще задана, не читая значение, можно только
  так: `grep -c '^export ИМЯ_ПЕРЕМЕННОЙ=' .env` — считает строки, ничего не
  печатает. Если не уверен, что метод не покажет значение — не проверяй
  файл вообще, а спроси меня напрямую.
- Значения секретов из `.env` (токен публикации, приватный ключ,
  сертификат) нигде не печатать и не выводить в чат — ни напрямую, ни
  через отладочный вывод команды. Сами переменные ты можешь передать
  Gradle через `source .env`: команда их только читает как окружение
  процесса, не показывает.
- Финальный `source .env && ./gradlew publishPlugin` — теперь твоя
  задача, а не моя. Запускай без `--info`/`--debug` (там может
  засветиться окружение) и без вывода `env`/`printenv` до или после —
  сам вывод publishPlugin секретов не печатает, но не расширяй его.

Вся процедура релиза (проверки, версия, CHANGELOG, коммиты, пуш,
публикация) живёт в скилле `/deploy` — правила выше он соблюдает, отдельно
их пересказывать не нужно.

## Где живёт Claude Code - вопрос к проекту, а не к машине IDE

Все читатели диска CLI (история и её страницы, пользовательский слой `settings.json`, личные команды и
скиллы для подсказки, расход токенов за сегодня, поисковый индекс, проверка «дошло ли сообщение до
транскрипта») спрашивают `ClaudeHome.of(project.basePath)`, а не `HostOs.configDirectory()` напрямую.
Причина - отзыв с RubyMine на Windows и проектом внутри WSL: платформа поднимает CLI внутри
дистрибутива, тот видит cwd как `/home/ivan/repo` и пишет в `/home/ivan/.claude/projects/-home-ivan-repo`,
а панель искала в `C:\Users\Ivan\.claude\projects\--wsl-localhost-Ubuntu-home-ivan-repo` - не та машина
и не то имя одновременно, и молча: отсутствие папки с транскриптами - штатное состояние.

- **Для обычного проекта ответ - ровно прежний** (`ClaudeHome.local`): дом JVM или `CLAUDE_CONFIG_DIR`
  из окружения IDE, путь проекта рядом с каноническим. WSL-классы не трогаются вовсе: до них дело
  доходит только на Windows и только для пути, начинающегося с `//` или `\\`.
- **Для WSL-проекта** - дом пользователя дистрибутива (`WSLDistribution.getUserHome`, платформа кэширует),
  его `CLAUDE_CONFIG_DIR` из окружения login-shell (`WSLDistribution.getEnvironment`; однопеременный
  `getEnvironmentVariable` помечен Internal, и верификатор на нём падает), `/etc/claude-code`, слаг из
  Linux-пути, а файлы читаются через
  ту же шару, откуда открыт проект (`WslPath.wslRoot` + Linux-путь). Сами читатели не меняются - меняются
  корень и имя.
- **Пути, напечатанные CLI, переводятся тем же местом** (`ClaudeHome.hostPath`): путь установки плагина
  внутри WSL - Linux-путь, и папку `commands` в нём иначе не открыть.
- **Первый ответ для WSL стоит процесса `wsl.exe`**, поэтому хаб греет его при открытии проекта
  (`ClaudeHome.warmUp`), ответ кэшируется по дистрибутиву, а неудача не кэшируется дольше минуты. С EDT
  спрашивать нельзя: платформа там отвечает null, не блокируя поток, и резолвер честно откатывается к
  локальному ответу с заметкой в `DiagnosticsLog` (без путей и имён - буфер уезжает наружу с отчётом).
- **Арифметика путей вынесена в чистую функцию** (`ClaudeHome.inWsl`) и держится `ClaudeHomeTest`: живьём
  на маке WSL не проверить, а ломается это молча.
- Что здесь НЕ решено и сделано осознанно: поиск исполняемого файла, `--help`/`--version` без рабочего
  каталога и чипы файлов с UNC-путями в сообщении агенту - это отдельная история про запуск в WSL, а не
  про чтение его диска.
